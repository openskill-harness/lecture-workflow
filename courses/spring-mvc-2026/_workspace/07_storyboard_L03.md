# L03 슬라이드 스토리보드 — Controller와 Service의 책임 경계

## 설계 개요

- **총 11장.** 프롬프터 잠정 마커 `[SLIDE 01]~[SLIDE 10]`(10개) 대비 **1장 증가**. 원인은 프롬프터 `[SLIDE 06]` 한 장에 (a) "트랜잭션 경계 = 유스케이스 = Service" 강조와 (b) `[비유 이탈 — 직설]` 계층도(Controller→Service→Repository→DB)라는 **서로 다른 두 메시지**가 묶여 있었기 때문. 1장 1메시지 원칙에 따라 S06(강조)·S07(계층도)로 분할한다. 원고 문장은 그대로 두고 **cue 번호만 재배열**(원고 내용 변경 아님).
- **1장 = 1메시지** 원칙 준수. 원고 7개 섹션 + 인트로/마무리 → 11장. 섹션 6(마무리)만 판단기준(S09)·두 질문(S10)으로 분리 — 프롬프터도 이미 SLIDE 08/09로 분리한 지점이라 조정 아님.
- **중심 비유 등장 궤적:** 식당 비유(홀 서버↔주방)는 S02에서 도입 → S05 책임표의 열 라벨("홀 서버"/"주방")로 유지 → S06 티켓(all-or-nothing)까지 이어감 → **S07에서 의도적으로 버림**([비유 이탈 — 직설]). S08에서 오분류 설명 시 비유를 보조로만 재사용(주문서/식재료, 홀 서버는 메뉴 확인·주방은 재고). 원고에 없는 지점에 비유를 미리 심지 않는다.
- **[비유 이탈 — 직설] = S07:** 이 장만은 식당 그림을 쓰지 않는다. 주방을 "저장창고/DB"로 오해하는 것을 끊기 위해 **Controller→Service→Repository→DB 4단 계층도**로 직설한다. 조립 시 식당 아이콘 사용 금지.
- **코드 슬라이드 없음 / SIM cue 없음.** 실행 코드 0장. 어노테이션(`@Valid`·`@Transactional`·`@NotBlank`·`@Min`)과 계층 흐름 화살표는 **실코드가 아니라 개념 칩·계층 라벨**로만 등장. L04(코드 워크스루)와 역할 분리. code_font_min_pt(22pt)는 이 개념 칩에도 동일 적용.
- **오분류(S08)는 코드 조각이 아니라 "증상 목록".** `@Transactional`을 컨트롤러에 붙임, DTO/Entity 혼용, 업무규칙 검증을 형식 검증과 동층 취급 — 세 가지를 **증상(무엇을 잘못했나) 카드**로 표기. 실제 리팩터링 코드는 L04.
- **단어 수 규칙:** 본문(제목+글머리+다이어그램/표 라벨) 어절 기준 카운트. `A·B·C`처럼 가운뎃점으로 이은 복합 토큰은 렌더 시 공백 없는 1토큰이므로 1어절로 계산. 하단 각주(출처)는 신뢰성 표기로 본문 카운트에서 제외하되 1행으로 짧게 유지.
- **비주얼 연속성:** S02(식당 2구역: 홀/주방) → S05(같은 2구역을 표의 두 열로) → S06(주방 안 "티켓" 클로즈업) → S07(주방 뒤에 Repository·DB 계층을 새로 드러냄, 비유→계층 전환). 하나의 "주방"이 형태를 유지하며 마지막에 계층도로 해체되도록 조립 지시.

## SLIDE 01 — 문제 제기: 뚱뚱한 컨트롤러 (시작 고정)

- **프롬프터 대응:** `[SLIDE 01]`
- **핵심 메시지(한 줄):** 한 메서드가 파라미터부터 응답까지 다 하는 컨트롤러 — 잘 돌지만 자꾸 손이 간다. 오늘은 그 경계를 스스로 판단한다.
- **구성 요소 명세:**
  - 제목: `동작은 하는데, 자꾸 손이 가는 컨트롤러`
  - 다이어그램: **하나의 큰 박스**(라벨 `Controller.method()`) 안에 5개 작업이 빽빽이 쌓인 스택 — `파라미터 추출` · `형식 검증` · `업무 규칙 판단` · `저장소 호출` · `응답 조립`. 박스가 터질 듯 꽉 찬 느낌(뚱뚱함 시각화).
  - 콜아웃 배지: 박스에 `"뚱뚱한 컨트롤러"(통칭 · 비공식)` 라벨.
  - 하단 목표 라벨: `오늘: 무엇이 컨트롤러의 일인가 — 경계를 스스로 판단`
  - 강조: 박스가 과부하임을 warning 컬러 테두리로. "경계"를 accent.
- **단어 수 추정:** 약 15어절 (제목 4 + 스택 라벨 5 + 배지 2 + 목표 라벨 4). **PASS (≤45)**
- **각주:** 없음 (통칭 서술 S1-4는 "비공식 통칭"임을 슬라이드 배지로 자체 명시, 외부 인용 아님)

## SLIDE 02 — 중심 비유: 홀 서버 ↔ 주방

- **프롬프터 대응:** `[SLIDE 02]`
- **핵심 메시지(한 줄):** 식당의 홀 서버와 주방으로 경계를 비유한다 — 뚱뚱한 컨트롤러는 홀 서버가 요리까지 하겠다는 식당이다.
- **구성 요소 명세:**
  - 제목: `식당으로 보는 경계 — 홀 서버 ↔ 주방`
  - 다이어그램(앵커 이미지): 좌측 **홀(서빙 공간)** 아이콘 + 라벨 `홀 서버(웨이터) = Controller`, 우측 **주방** 아이콘 + 라벨 `주방(셰프) = Service`. 둘 사이 경계선.
  - 대비 삽화: 경계선을 지운 "홀 서버가 요리까지" 상태를 작게 표시하고 `한 테이블이면 OK` 캡션.
  - 강조: 두 구역을 나누는 경계선을 accent. 이 2구역 레이아웃을 S05 표의 두 열로 이어받도록 조립 지시.
- **단어 수 추정:** 약 12어절 (제목 5 + 좌/우 라벨 4 + 캡션 3). **PASS**
- **각주:** 없음 (비유 도입, 인용 없음)

## SLIDE 03 — 깨지는 지점: 경계가 없으면 무너지는 3가지

- **프롬프터 대응:** `[SLIDE 03]`
- **핵심 메시지(한 줄):** 경계가 없으면 규칙이 복사되고, 변경이 서로를 넘어뜨리고, 검증하려면 웹을 통째로 띄워야 한다.
- **구성 요소 명세:**
  - 제목: `경계가 없을 때 깨지는 3가지`
  - 다이어그램: **3열 카드**
    - ① `규칙이 복사된다` — 같은 규칙이 컨트롤러·배치·스케줄러로 복붙되어 흩어지는 아이콘(중복 문서 3장).
    - ② `변경이 서로를 넘어뜨린다` — HTTP 코드와 업무 규칙이 한 메서드에 얽혀 도미노처럼 쓰러지는 아이콘.
    - ③ `검증하려면 웹을 통째로 띄운다` — 로직 하나 확인에 HTTP 계층 전체가 딸려오는 아이콘.
  - 비유 앵커(하단 1줄): `홀 서버가 요리까지 하면 — 자리 비우면 요리가 멈춘다` (경계가 웹 프레임워크에 묶임).
  - 강조: 세 카드 제목만 강조, 부연은 작게.
- **단어 수 추정:** 약 18어절 (제목 4 + 카드 3제목 9 + 하단 비유 5). **PASS**
- **각주:** `① Fowler, PoEAA — "Service Layer"(공통 업무 로직을 모아 진입점 간 중복 제거) · ② R.C. Martin, "SRP"(2014, 한 모듈은 바뀔 이유가 하나) · ③ Fowler, "Service Layer"(경계가 웹 프레임워크에 묶임)` — citation_required(external_case_studies). S1-1/S1-2/S1-3/S2-1 근거.

## SLIDE 04 — 분리 기준: 줄 수가 아니라 변경 이유

- **프롬프터 대응:** `[SLIDE 04]`
- **핵심 메시지(한 줄):** 나누는 기준은 "길이"가 아니라 "무엇이 어떤 이유로 바뀌는가"다 — 단, 서비스는 로직 던져 넣는 만능 창고가 아니다.
- **구성 요소 명세:**
  - 제목: `기준 — 줄 수 ❌ / 변경 이유 ⭕`
  - 다이어그램: **두 갈래 화살표**가 한 모듈로 들어오는 그림
    - `HTTP 표현이 바뀌는 이유 → 경로·상태코드·응답 포맷 (출처: API 스펙)`
    - `업무 규칙이 바뀌는 이유 → 정책·계산·트랜잭션 범위 (출처: 기획)`
    - 두 화살표가 한 박스에 꽂히며 `한쪽이 다른 쪽을 인질로 잡는다` 경고.
  - 하단 주의 배지: `⚠ 서비스 = 로직 만능 창고 아님 (→ 빈혈 도메인 모델, 다음 강의)`
  - 강조: ❌/⭕ 대비, "변경 이유"를 accent. 빈혈 도메인 모델 배지는 회색(오늘 주제 아님 신호).
- **단어 수 추정:** 약 20어절 (제목 5 + 두 갈래 라벨 10 + 주의 배지 5). **PASS**
- **각주:** `R.C. Martin, "SRP"(2014, "결국 사람에 관한 것" — 이해관계자별 변경 격리) · Fowler, "AnemicDomainModel"(로직을 모두 서비스로 몰면 빈혈 도메인)` — citation_required. S3-1/S3-2 근거.

## SLIDE 05 — 핵심 구조: 두 계층 책임 대조표 (표 슬라이드)

- **프롬프터 대응:** `[SLIDE 05]`
- **핵심 메시지(한 줄):** Controller는 HTTP 경계의 어댑터, Service는 유스케이스이자 트랜잭션 경계 — 한 표로 대조한다.
- **구성 요소 명세:**
  - 제목: `두 계층의 책임 대조표`
  - **표(한 슬라이드 한 표, S02의 홀/주방 2열 레이아웃 계승):**

    | | Controller(홀 서버) | Service(주방) |
    |---|---|---|
    | 한 문장 | HTTP↔앱 어댑터 | 유스케이스+트랜잭션 경계 |
    | 하는 일 | 매핑·바인딩·형식검증·예외→상태코드·응답조립 | 업무규칙·도메인/저장소조율·트랜잭션제어 |
    | 다루는 것 | 요청 DTO(주문서) | 업무 로직 · 티켓=all-or-nothing |
    | 바뀌는 이유 | 경로·상태코드·응답포맷 | 정책·계산·트랜잭션범위 |

  - 개념 칩(≥22pt): 표 하단에 `@Valid = 형식 검증 트리거(컨트롤러 경계) — "형식이 맞는가"이지 "업무적으로 되는가"가 아님`. 배턴 표기: `Controller → (입력 DTO) → Service.유스케이스() → (결과) → Controller 응답 표현`.
  - 강조: 왼쪽 열 전체 = 컨트롤러 책임임을 색으로 묶음. "트랜잭션 경계"만 미리 accent(다음 장 예고).
  - 조립 지시: 가운뎃점(·)으로 이은 셀은 공백 없는 단일 토큰으로 렌더(단어 수·가독성 양립). 표 셀 폰트도 22pt 이상.
- **단어 수 추정:** 약 22어절 (제목 3 + 헤더 2 + 행라벨 4 + 8셀 토큰 9 + 배턴/칩 라벨 4). **PASS** (가운뎃점 복합 토큰 규칙 적용)
- **각주:** `Spring Framework Reference, Web MVC "Annotated Controllers"(컨트롤러 = HTTP와 비즈니스 로직 사이의 다리) · Web MVC "Validation"(@Valid 형식 검증; Spring 6.1 메서드 검증 동작 변경 — 공식 문서 확인) · Fowler "Service Layer"(업무 로직 캡슐화·트랜잭션 제어·응답 조율)` — citation_required(version_specific_claims). S4-1/S4-2/S4-3/S5-1 근거.

## SLIDE 06 — 트랜잭션 경계 = 유스케이스 = Service (오늘의 핵심 · 강조)

- **프롬프터 대응:** `[SLIDE 06]`(전반부 — 강조 메시지)
- **핵심 메시지(한 줄):** 하나의 업무 단위가 전부-아니면-전무로 처리되는 자리 = 트랜잭션 경계 = 유스케이스 경계 = Service.
- **구성 요소 명세:**
  - 제목: `트랜잭션 경계 = 유스케이스 경계 = Service`
  - 중심 배지: 세 등호로 이어진 **큰 등식** `트랜잭션 경계 = 유스케이스 = Service` (오늘 한 장만 남긴다면 이 장).
  - 비유 클로즈업(S02 주방 계승): **주방 티켓 한 장** — `스테이크 + 사이드 = 한 티켓` → `둘 다 나가거나, 둘 다 안 나간다 (반쪽 서빙 없음 = all-or-nothing)`.
  - 개념 칩(≥22pt): `@Transactional → 구체 클래스(=서비스)의 메서드에 (인터페이스 아님)`.
  - 강조: 등식을 화면 중앙 최대 강조. "이 슬라이드 = 오늘의 핵심" 마킹(별표/핀).
- **단어 수 추정:** 약 16어절 (제목 5 + 티켓 라벨 6 + 칩 라벨 5). **PASS**
- **각주:** `Spring Framework Reference, Data Access "Using @Transactional"(@Transactional은 구체 클래스 메서드에 권장)` — citation_required(version_specific_claims). S4-4 근거.

## SLIDE 07 — [비유 이탈 — 직설]: 계층도 Controller → Service → Repository → DB

- **프롬프터 대응:** `[SLIDE 06]`(후반부 — 원고 `[비유 이탈 — 직설]` + `[화면: 계층 흐름]`. **분할로 신설**)
- **핵심 메시지(한 줄):** 여기서 비유를 버린다 — 주방(조리=유스케이스)은 저장창고가 아니다. 재료를 넣고 꺼내는 곳은 별개 계층 Repository이고 그 뒤에 DB가 있다.
- **구성 요소 명세:**
  - 제목: `[직설] 주방은 저장창고가 아니다`

## SLIDE 08 — 흔한 오분류 3가지 (증상 목록 · 코드 조각 아님)

- **프롬프터 대응:** `[SLIDE 07]`
- **핵심 메시지(한 줄):** 경계를 헷갈리는 세 지점 — 트랜잭션을 웹에 둠, DTO/Entity 혼용, 업무규칙 검증을 형식 검증과 같은 층 취급.
- **구성 요소 명세:**
  - 제목: `자주 틀리는 3가지`
  - **증상 카드 3개(실코드 아님 — "무엇을 잘못했나" 증상 라벨):**
    - ① `트랜잭션을 웹 계층에 둔다` — 증상: `@Transactional을 컨트롤러에` / `컨트롤러에서 저장소 여러 번 이어 호출` → 권장: `서비스 구체 클래스 메서드`.
    - ② `주문서와 식재료를 같은 것으로 — DTO/Entity 혼용` — 증상: `요청·응답 DTO와 영속 Entity를 구분 없이` → 위험: `직렬화·바인딩 관심사가 도메인으로 샘 / 필드 과다 노출`. 비유: `주문서엔 "스테이크 미디엄"이라 적지 소를 통째로 적지 않는다`.

  - 조립 지시: `class`/`{}`/메서드 본문 같은 코드 형태 금지. 어노테이션 토큰 + 자연어 증상만.
- **단어 수 추정:** 약 24어절 (제목 3 + 카드3 제목 12 + 어노테이션 칩·비유 라벨 9). **PASS** (증상 라벨은 카드별 3~4어절로 압축)
- **각주:** `① Spring Reference "Using @Transactional"(서비스 구체 클래스 메서드 권장) · ② Fowler, PoEAA "Data Transfer Object"(DTO=프로세스 경계 너머로 데이터 운반, 목적 상이) · ③ 형식/업무 규칙 검증 층 구분(S6-3)` — citation_required. S6-1/S6-2/S6-3 근거.
