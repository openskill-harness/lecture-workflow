## Slide 1. 표지

**Screen**
- 제목: 캡슐화·SOLID와 OCP
- 부제: if-else로 인한 OCP 위반을 진단하고, 변경에 닫힌 구조로 재설계한다
- 화면: 템플릿 표지 레이아웃 사용. 우측에 여러 종류의 도형(사각형·원·삼각형)이 하나의 계산기 상자로 들어가는 상징 이미지를 배치하고, 계산기 상자에는 "수정 금지" 자물쇠를 그려 변경에 닫혀 있음을 암시.

**Easy analogy**
- 잘 설계된 콘센트는 새 가전이 나와도 벽을 뜯지 않는다. 규격(약속)에 맞춰 플러그만 꽂으면 된다. 오늘 배울 개방-폐쇄 원칙은 "새 기능은 꽂아서 늘리고, 이미 있는 벽은 뜯지 않는" 설계다.

**Practical case**
- 교육용 시나리오: 지난 시간에 다형성을 손으로 확인한 3년차 개발자가 자기 팀 코드를 열어 보니, 유형이 하나 늘 때마다 거대한 if-else 블록을 계속 뜯어고치고 있었다. 이번 차시는 그 코드가 왜 유지보수에 약한지 진단하고, 무엇을 바꾸면 뜯어고치지 않아도 되는지를 배우는 시간이다.

**Visual asset**
- GPT image prompt: `여러 종류의 도형 — 사각형, 원, 삼각형 — 이 하나의 계산기 상자 속으로 흘러 들어가고, 그 상자에는 수정 금지를 뜻하는 작은 자물쇠가 달린 밝은 강의실풍 교육용 표지 일러스트, 플랫 벡터, 글자 없이, 16:9`

- 과정개요서 — 유지보수성 향상을 위한 디자인패턴(Java) ch02 차시내용.

**Narration**
- 안녕하세요. 유지보수성 향상을 위한 디자인패턴 과정의 두 번째 시간입니다. 지난 시간에는 상위 타입 참조로 하위 구현을 다루는 다형성과, 실행 시점에 실제 객체의 메서드가 선택되는 동적바인딩을 손으로 확인했습니다. 오늘은 그 원리를 "좋은 설계란 무엇인가"라는 질문으로 끌어올립니다. 이 과정 전체를 관통하는 문장이 하나 있습니다. if-else로 인한 개방-폐쇄 원칙 위반을 진단하고, 패턴으로 변경에 닫힌 구조로 재설계한다. 오늘 이 문장의 앞부분, 그러니까 "진단하는 렌즈"를 세웁니다. 앞으로 열네 개 차시 내내 우리는 어떤 코드를 만나든 이 렌즈로 먼저 들여다볼 것입니다. "이 코드는 새 유형이 생기면 어디를 뜯어고쳐야 하는가?" 이 질문에 "여러 군데"라고 답이 나오면 그 코드는 오늘 배울 원칙을 위반한 것이고, 우리가 앞으로 배울 패턴들이 바로 그 문제의 처방입니다. 오늘은 아주 익숙한 도형 넓이 계산 예제 하나로 이 진단과 처방을 끝까지 체험하겠습니다.

## Slide 2. 지난 시간 회수와 오늘의 문제: 왜 좋은 설계가 필요한가

**Screen**
- 제목: 다형성은 "도구", 오늘은 그 도구를 "왜·어디에 쓰는가"
- 짧은 문구:
  - 지난 시간: 상위 타입으로 다루고, 실행 시점에 선택된다(다형성·동적바인딩)
  - 오늘: 그 다형성으로 "수정하지 않는 코드"를 만드는 기준을 세운다
  - 진단 렌즈: 새 유형이 생기면 어디를, 몇 군데를 고쳐야 하는가?
- 화면: 좌측에 지난 차시의 추상 타입-구현 관계도를 작게, 우측에 "새 유형 추가 → 기존 코드 수정 파급" 화살표가 여러 갈래로 번지는 그림.

**Easy analogy**
- 지난 시간에 배운 것이 "망치를 쥐는 법"이라면, 오늘은 "못을 어디에 박아야 벽이 튼튼해지는가"를 배우는 시간이다. 도구를 쥘 줄 아는 것과 잘 쓰는 것은 다르다.

**Practical case**
- 실무사례형 시나리오: 결제 유형이 카드 하나였던 서비스에 계좌이체, 간편결제가 차례로 추가된다. 그때마다 결제 처리 메서드의 if-else가 길어지고, 한 유형을 고치다 다른 유형이 깨지는 회귀 버그가 반복된다. "기능이 늘수록 코드가 불안해지는" 이 현상이 바로 오늘 진단할 유지보수성 문제다.

**Visual asset**
- GPT image prompt: `두 패널을 대비한 교육용 일러스트. 왼쪽은 추상에서 구체로 이어지는 단정한 트리 형태의 타입 관계도, 오른쪽은 하나의 변경이 뒤엉킨 if-else 가지들 사이로 금이 번지듯 퍼져 나가는 모습, 깔끔한 강의 슬라이드 스타일, 글자 없이, 16:9`

**Source**
- Oracle Java Tutorials – Polymorphism: 실행 시점에 실제 객체의 재정의 메서드가 선택된다는 다형성 설명(지난 차시 회수). https://docs.oracle.com/javase/tutorial/java/IandI/polymorphism.html
- 과정개요서 — 유지보수성 향상을 위한 디자인패턴(Java) §7 관통 서사(if-else 위반 진단 → 패턴으로 재설계).

**Narration**
- 본론에 들어가기 전에 지난 시간을 짧게 회수하겠습니다. 우리는 부모 타입 변수에 자식 객체를 담고, 실행 시점에 실제 객체의 메서드가 선택되는 동적바인딩을 직접 확인했습니다. 그런데 다형성 자체는 도구일 뿐입니다. 도구를 쥘 줄 아는 것과, 그 도구를 어디에 왜 써야 하는지를 아는 것은 다른 문제입니다. 오늘은 바로 그 "왜"와 "어디"를 다룹니다. 실무에서 코드가 점점 유지보수하기 어려워지는 전형적인 장면을 떠올려 보겠습니다. 처음에는 결제 유형이 카드 하나였습니다. 그런데 계좌이체가 추가되고, 간편결제가 추가되면서, 결제를 처리하는 메서드 안의 조건 분기가 계속 길어집니다. 문제는 길어지는 것 자체가 아닙니다. 한 유형을 손보다가 옆에 있던 다른 유형이 조용히 깨지는 일이 생긴다는 것입니다. 기능이 늘어날수록 코드가 더 불안해집니다. 이것이 유지보수성이 낮은 코드의 대표적인 증상입니다. 오늘 우리는 이 증상을 정확히 진단하는 렌즈를 만들고, 그 렌즈가 가리키는 처방인 개방-폐쇄 원칙을 배웁니다. 진단의 핵심 질문은 딱 하나입니다. "새로운 유형이 생기면 나는 어디를, 몇 군데를 고쳐야 하는가?"

## Slide 3. 추상과 구체: 존재할 수 있는 것과, 그것들을 아우르는 말

**Screen**
- 제목: 존재할 수 있는 것(구체)과, 존재하지 않지만 아우르는 말(추상)
- 짧은 문구:
  - 영어엔 추상명사·물질명사 구분이 뚜렷하지만, 한국어엔 그런 문법 범주가 없다 → 초보자가 추상 타입을 어려워하는 이유
  - `가구(furniture)`는 추상명사 — 세상에 "가구"라는 물건은 없다. 존재하는 건 `의자`, `책상`이다
  - 객체(object) = 존재할 수 있는 것 / 추상(abstract) = 존재하지 않지만 그것들을 아우르는 말
  - 그래서 `new Shape()`는 불가능, `new Circle()`은 가능 — 실제로 태어나는 건 구체 클래스뿐
- 화면: 상단에 흐릿한 윤곽으로 그린 "가구", 그 아래 또렷한 실체로 놓인 의자·책상·옷장. 위(추상)는 이름표·약속, 아래(구체)는 메모리에 태어나는 실물임을 대비.

**Easy analogy**
- 가구점에 가서 "가구 하나 주세요"라고 하면 점원이 반드시 되묻는다. "의자요, 책상이요?" 가구라는 말만으로는 아무것도 건네줄 수 없다. 추상은 이름표일 뿐, 실제로 손에 쥐는 것은 언제나 구체다.

**Practical case**
- 교육용 시나리오: 우리말로 프로그래밍을 배우는 초보자는 `abstract class`를 만나면 "그럼 이건 어떻게 만들어 쓰지?"에서 막힌다. 원인은 문법이 아니라 언어 습관이다. 한국어에는 추상명사를 따로 표시하는 장치가 없어, "존재하지 않는 타입"이라는 개념 자체가 낯설기 때문이다. 이 감각을 먼저 잡아 두면 오늘의 Shape 계층이 훨씬 쉽게 읽힌다.

**Visual asset**
- GPT image prompt: `흐릿한 윤곽으로 그려진 '가구'라는 형상 아래에, 의자·책상·옷장이 또렷하고 단단한 실체로 놓여 있는 교육용 일러스트. 위쪽 윤곽은 존재하지 않는 개념을, 아래쪽 사물들은 실제로 존재하는 것을 상징한다. 깔끔한 플랫 스타일, 글자 없이, 16:9`
- Code block for slide:

```java
// 가구(추상)는 존재하지 않는다 — 존재하는 것은 의자, 책상이다.
abstract class 가구 { abstract void 놓다(); }
class 의자 extends 가구 { void 놓다() { System.out.println("의자를 놓는다"); } }
class 책상 extends 가구 { void 놓다() { System.out.println("책상을 놓는다"); } }

// 가구 f = new 가구();   // 컴파일 에러 — 추상은 존재할 수 없다
가구 f = new 의자();       // 가능 — 존재할 수 있는 것만 태어난다
```

**Source**
- Oracle Java Tutorials – Abstract Methods and Classes: 추상 클래스는 인스턴스화할 수 없고, 하위 클래스가 구현을 제공한다는 설명. https://docs.oracle.com/javase/tutorial/java/IandI/abstract.html
- 과정개요서 — 유지보수성 향상을 위한 디자인패턴(Java) ch02 차시내용(추상 타입 이해).

**Narration**
- 오늘 본격적인 코드로 들어가기 전에, 초보자들이 가장 많이 걸려 넘어지는 감각 하나를 먼저 잡고 가겠습니다. 바로 추상과 구체의 구분입니다. 영어에는 추상명사와 물질명사를 가르는 문법이 뚜렷하지만, 한국어에는 그런 문법 범주가 없습니다. 그래서 우리말로 프로그래밍을 배우는 분들은 추상 타입을 유독 어려워하시는 경우가 많습니다. 쉬운 예를 들어 보겠습니다. 가구라는 말을 떠올려 보세요. 영어로는 퍼니처입니다. 그런데 세상 어디에도 가구라는 물건 자체는 존재하지 않습니다. 여러분의 방에 있는 것은 의자이고, 책상이고, 옷장입니다. 가구라는 이름의 실물은 없습니다. 가구는 의자와 책상과 옷장을 한꺼번에 아우르는 말일 뿐입니다. 바로 이것이 추상입니다. 정리하면 이렇습니다. 객체, 즉 오브젝트는 실제로 존재할 수 있는 것입니다. 추상은 존재하지는 않지만 그것들을 아우르는 말입니다. 이 감각을 코드로 옮기면 아주 또렷해집니다. 화면의 코드를 보시죠. 가구를 abstract로 선언했습니다. 그리고 의자와 책상이 가구를 상속받습니다. 여기서 가구 f는 new 가구로 만들 수 없습니다. 존재하지 않는 것을 메모리에 태어나게 할 수는 없기 때문입니다. 대신 new 의자는 됩니다. 존재할 수 있는 것만 실제로 태어납니다. 가구점에 가서 가구 하나 주세요라고 하면 점원이 반드시 되묻습니다. 의자를 드릴까요, 책상을 드릴까요? 가구라는 말만으로는 아무것도 건네줄 수 없기 때문입니다. 추상 타입은 이렇게 이름표이자 약속입니다. 실제로 메모리에 태어나는 것은 언제나 구체 클래스뿐입니다. 이 감각이 한번 잡히면, 오늘 뒤에서 만들 abstract class Shape와 그것을 상속한 Circle, Rectangle의 구조가 아주 자연스럽게 읽히실 겁니다. new Shape는 안 되고 new Circle은 되는 이유가 곧바로 보이니까요.

## Slide 4. 오늘의 학습 목표

**Screen**
- 제목: 오늘은 "고치지 않고 늘리는 설계"를 손으로 증명한다

  1. 추상과 구체를 구분하고, 추상 타입이 왜 `new`될 수 없는지 설명할 수 있다.

**Practical case**

## Slide 5. 캡슐화: 상태는 행위를 통해서만 바꾼다

**Screen**
- 제목: 캡슐화 = 상태는 숨기고, 오직 행위를 통해서만 바꾼다
- 짧은 문구:
  - 앨리스는 토끼굴로 떨어져 이상한 나라에 들어간다 — 그곳의 애벌레 버섯은 한쪽을 먹으면 커지고 반대쪽을 먹으면 작아진다
  - 키(상태)를 밖에서 아무나 아무 값으로 바꾸면 세계가 망가진다(음수 키가 된 앨리스)
  - 키는 `private`으로 숨기고, 오직 "버섯을 먹는다"는 행위로만 바뀐다 — 이것이 캡슐화
- 화면: 좌측에 버섯을 든 앨리스(왼쪽 먹으면 커진 실루엣, 오른쪽 먹으면 작아진 실루엣). 우측에 `public int 키`(밖에서 아무 값이나) vs `private int 키` + 버섯 먹기 행위를 대비한 미니 코드 카드.

**Easy analogy**
- 은행 금고와 창구의 관계와 같다. 고객은 금고 안 현금 다발을 직접 만질 수 없고(private 필드), 입금·출금이라는 정해진 창구 절차(행위)를 통해서만 잔액이 바뀐다. 앨리스의 키가 버섯을 먹는 행위로만 바뀌는 것과 똑같다.

**Practical case**
- 실무사례형 시나리오: 회원의 포인트 필드를 public으로 열어 두면, 여러 곳에서 제각기 값을 더하고 빼다가 "왜 포인트가 음수가 됐지?" 같은 추적 불가능한 버그가 생긴다. 앨리스의 키가 음수가 되어 버리는 것과 같은 사고다. 필드를 private으로 닫고 정해진 행위 메서드로만 바꾸게 하면, 검증과 로그를 한곳에 모을 수 있어 상태가 망가지는 경로 자체가 사라진다.

**Visual asset**
- GPT image prompt: `이상한 나라의 앨리스가 토끼굴 아래 세계에서 애벌레의 버섯을 손에 든 장면. 버섯 한쪽을 먹으면 키가 커지고 반대쪽을 먹으면 작아지는 변화를, 키가 커진 앨리스와 작아진 앨리스의 실루엣으로 나란히 보여 준다. 키라는 상태가 오직 버섯을 먹는 행위로만 바뀐다는 것을 암시하는 교육용 동화풍 일러스트, 부드러운 색감, 글자 없이, 16:9`
- Code block for slide:

```java
// 나쁜 예 — 상태가 밖에 열려 있다
class 앨리스나쁜예 {
    public int 키 = 150;
}
// alice.키 = -999;   // 누구든 아무 값이나 넣는다. 앨리스가 음수 키가 된다.

// 좋은 예 — 상태는 숨기고, 행위를 통해서만 바뀐다
public class Alice {
    private int 키 = 150;

    public void 버섯왼쪽을먹다() { 키 += 30; }
    public void 버섯오른쪽을먹다() { 키 -= 30; }
    public int 키재기() { return 키; }
}
```

**Source**
- Oracle Java Tutorials – Controlling Access to Members of a Class: 필드는 가능한 한 private으로 두고 메서드로 접근하도록 권장한다는 설명. https://docs.oracle.com/javase/tutorial/java/javaOO/accesscontrol.html
- 이상한 나라의 앨리스(애벌레의 버섯 — 한쪽은 커지고 반대쪽은 작아진다): https://en.wikipedia.org/wiki/Alice%27s_Adventures_in_Wonderland

**Narration**
- 오늘의 첫 번째 설계 주제는 캡슐화입니다. 이번에는 이상한 나라의 앨리스 이야기로 풀어 보겠습니다. 앨리스는 토끼를 쫓다가 토끼굴로 떨어져 이상한 나라에 들어갑니다. 그 세계에서 앨리스는 애벌레가 앉아 있던 버섯을 만납니다. 이 버섯은 한쪽을 먹으면 키가 커지고, 반대쪽을 먹으면 키가 작아집니다. 자, 여기서 앨리스의 키를 하나의 상태라고 생각해 보겠습니다. 만약 이 키라는 값을 세계의 누구나, 아무 때나, 아무 값으로나 바꿀 수 있다면 어떻게 될까요? 어떤 이가 앨리스의 키를 마이너스 구백구십구로 만들어 버릴 수도 있습니다. 음수 키를 가진 앨리스라니, 이야기의 세계가 그대로 망가집니다. 화면 위쪽의 나쁜 예가 정확히 그 상황입니다. 키가 public으로 열려 있어서, 바깥의 누구든 앨리스 점 키에 아무 숫자나 대입할 수 있습니다. 이제 아래쪽 좋은 예를 보시죠. 키를 private으로 숨겼습니다. 바깥에서는 이 값을 직접 만질 수 없습니다. 키가 바뀌는 길은 오직 두 가지 행위뿐입니다. 버섯 왼쪽을 먹으면 키가 삼십 늘고, 버섯 오른쪽을 먹으면 키가 삼십 줄어듭니다. 그리고 키재기라는 행위로 지금 키가 얼마인지 확인만 할 수 있습니다. 실제로 왼쪽 버섯을 먹으면 키는 백팔십이 되고, 이어서 오른쪽 버섯을 먹으면 다시 백오십으로 돌아옵니다. 상태는 반드시 정해진 행위를 통해서만 바뀝니다. 이것이 바로 캡슐화입니다. 상태를 숨기고, 오직 행위를 통해서만 그 상태가 바뀌도록 통제하는 것입니다. 이 코드는 개념을 설명하기 위한 예시이고, 오늘의 실습은 도형 예제로만 진행합니다. 다만 한 가지만 미리 이어 두겠습니다. 잠시 뒤 우리가 재설계할 Circle 클래스의 private double radius도 정확히 같은 규율 위에 서 있습니다. 반지름을 숨기고 넓이라는 행위로만 자신을 드러내는 것, 그것이 앨리스의 키를 버섯이라는 행위로만 바꾸는 것과 완전히 같은 이야기입니다.

## Slide 6. 유지보수성이 낮은 코드의 특징

**Screen**
- 제목: 이런 코드는 기능이 늘수록 더 위험해진다
- 짧은 문구:
  - 하나의 변경이 여러 곳으로 번진다(수정 파급)
  - 유형이 늘 때마다 같은 if-else를 계속 뜯어고친다
  - 서로 관계없는 유형들이 한 메서드에 뭉쳐 있다(강한 결합)
  - 새 기능 추가가 곧 기존 기능의 회귀 위험이 된다
- 화면: 하나의 거대한 메서드 블록 안에 서로 다른 색의 유형들이 뒤엉켜 있고, 한 곳을 건드리자 다른 색 블록에 금이 가는 그림.

**Easy analogy**
- 방 하나에 모든 살림을 쌓아 둔 창고와 같다. 겨울옷 하나를 꺼내려고 해도 여름 이불부터 다 들어내야 하고, 물건 하나를 옮기면 옆의 탑이 무너진다. 칸을 나눠 두지 않은 대가는 물건이 늘수록 커진다.

**Practical case**
- 실무사례형 시나리오: 알림 발송 메서드 하나가 이메일·SMS·푸시·카카오톡을 전부 if-else로 처리하고 있다. 새 채널을 붙이려고 분기 하나를 추가했더니, 위쪽 분기에서 쓰던 공용 변수를 건드리는 바람에 기존 이메일 발송이 멈췄다. 배포 후에야 발견된 이 회귀 버그가 유지보수성 낮은 코드의 전형적 청구서다.

**Visual asset**
- GPT image prompt: `하나의 거대한 메서드 블록 안에 서로 다른 색의 유형들이 뒤엉켜 있고, 한 곳을 건드리자 관계없는 다른 색 블록에 금이 가는 교육용 일러스트. 변경 파급과 강한 결합을 상징한다. 깔끔한 플랫 강의 스타일, 글자 없이, 16:9`

**Source**
- 개방-폐쇄 원칙(Meyer·Martin): 하나의 변경이 연쇄 수정을 부르는 구조를 개방-폐쇄 원칙으로 완화한다는 배경 설명. https://en.wikipedia.org/wiki/Open%E2%80%93closed_principle
- refactoring.guru 디자인패턴 카탈로그: 패턴이 반복되는 설계 문제(변경 파급·강한 결합)의 검증된 해법 모음이라는 설명. https://refactoring.guru/design-patterns/catalog

**Narration**

## Slide 7. SOLID 5원칙 개관

**Screen**
- 제목: SOLID — 변경에 강한 객체지향 설계의 다섯 기준
- 짧은 문구:
  - S: 단일 책임 원칙(SRP) — 클래스는 하나의 변경 이유만
  - O: 개방-폐쇄 원칙(OCP) — 확장에 열리고 수정에 닫힌다 ← 재설계로 가장 깊게
  - L: 리스코프 치환 원칙(LSP) — 하위 타입은 상위 타입을 대체할 수 있어야
  - I: 인터페이스 분리 원칙(ISP) — 필요 없는 계약을 강요하지 않는다
  - D: 의존 역전 원칙(DIP) — 구체가 아니라 추상에 의존한다
- 화면: SOLID 다섯 글자를 세로 배지로 세우고, O 배지만 크게 강조. 하단에 "다섯 원칙을 한 장씩 — O는 재설계로 가장 깊게" 라벨.

**Easy analogy**
- SOLID는 건축의 안전 수칙 다섯 줄과 같다. 다섯 줄 전체가 튼튼한 건물을 만들지만, 오늘은 그중 "증축할 때 기존 벽을 허물지 않는다"는 한 줄(O)을 도형 예제로 끝까지 파고든다.

**Practical case**
- 실무사례형 시나리오: 코드 리뷰나 기술 면접에서 SOLID는 단골 주제다. 다섯 원칙을 낱낱이 외우는 것보다, 각 원칙이 "어떤 변경을 견디게 해 주는가"로 묶어 이해하면 실제 코드에 적용할 때 흔들리지 않는다. 특히 O와 D는 오늘 예제 안에서 함께 작동한다.

- Robert C. Martin, "The Open Closed Principle" (Clean Coder Blog, 2014): OCP가 다섯 원칙 중에서도 확장성의 중심축이라는 설명. http://blog.cleancoder.com/uncle-bob/2014/05/12/TheOpenClosedPrinciple.html

**Narration**
- 이제 SOLID를 개관하겠습니다. SOLID는 로버트 마틴이 정리하고 마이클 페더스가 약어로 이름 붙인, 변경에 강한 객체지향 설계의 다섯 가지 원칙입니다. 하나씩 짧게 보겠습니다. S는 단일 책임 원칙입니다. 한 클래스는 바뀌어야 할 이유가 하나여야 한다는 뜻입니다. O는 오늘의 주인공, 개방-폐쇄 원칙입니다. 확장에는 열려 있고 수정에는 닫혀 있어야 한다는 원칙입니다. L은 리스코프 치환 원칙입니다. 하위 타입은 언제나 상위 타입을 대신할 수 있어야 한다는 것으로, 지난 시간에 배운 다형성이 안전하게 작동하기 위한 조건이라고 보시면 됩니다. I는 인터페이스 분리 원칙입니다. 쓰지도 않는 기능까지 억지로 구현하게 만들지 말라는 뜻입니다. 마지막 D는 의존 역전 원칙으로, 구체적인 구현이 아니라 추상에 의존하라는 원칙입니다. 이 다섯 가지를 이제 한 장씩 이어서 짚어 보겠습니다. 각 원칙마다 쉬운 비유와 아주 짧은 예시 코드로 감을 잡을 것입니다. 그중에서도 O, 개방-폐쇄 원칙은 오늘 도형 예제를 직접 재설계하면서 가장 깊이 파고들 원칙입니다. 다섯 줄짜리 건축 안전 수칙 중에서도 증축할 때 기존 벽을 허물지 않는다는 그 한 줄이 오늘의 중심입니다. 그리고 흥미롭게도, 오늘 예제를 재설계하면 O를 지키는 과정에서 D, 즉 의존 역전 원칙까지 자연스럽게 함께 지켜지는 것을 보게 됩니다. 정답 소스의 주석에도 각 도형이 스스로 넓이를 책임지게 한다, 이건 DIP다라고 적혀 있습니다.

## Slide 8. S — 단일 책임 원칙: 클래스는 하나의 변경 이유만

**Screen**
- 제목: 단일 책임 — 하나의 클래스는 하나의 이유로만 바뀐다
- 짧은 문구:
  - 도형은 "넓이"만 책임진다
  - 출력 방식이 바뀌어도 도형은 고치지 않는다 — 출력은 `AreaPrinter`가 맡는다
  - 한 클래스에 서로 다른 변경 이유가 몰리면, 어느 쪽이 바뀌든 그 클래스가 흔들린다
- 화면: 좌측에 요리와 회계를 혼자 떠안은 요리사(변경 이유 두 개가 겹침), 우측에 요리사와 회계사로 나뉘어 각자 하나의 일만 하는 그림.

**Easy analogy**
- 요리사가 회계까지 맡으면, 메뉴가 바뀔 때도 그 사람을 부르고 세법이 바뀔 때도 그 사람을 불러야 한다. 서로 다른 두 변화의 이유가 한 사람에게 몰려 있으니 어느 쪽이 바뀌든 흔들린다.

**Practical case**
- 실무사례형 시나리오: 주문 클래스 하나가 주문 계산도 하고, 그 결과를 화면에 출력도 하고, 파일로 저장까지 한다. 출력 양식이 바뀔 때도, 저장 포맷이 바뀔 때도, 계산 규칙이 바뀔 때도 이 한 클래스를 연다. 세 가지 변경 이유가 한 곳에 묶여 있어, 하나를 고치다 나머지가 깨진다.

**Visual asset**
- GPT image prompt: `요리사 한 명이 요리와 회계 장부를 동시에 떠안아 힘들어하는 모습과, 요리는 요리사가 회계는 회계사가 나눠 맡아 각자 하나의 일에만 집중하는 모습을 좌우로 대비한 교육용 일러스트. 하나의 책임만 진다는 단일 책임 원칙을 상징한다. 깔끔한 플랫 스타일, 글자 없이, 16:9`

```java

abstract class Shape { public abstract double 넓이(); }
class AreaPrinter { void 출력(Shape s) { System.out.println("넓이 : " + s.넓이()); } }
```

**Source**
- SOLID 5원칙 개관·단일 책임 원칙: 클래스는 하나의 변경 이유만 가져야 한다는 설명. https://en.wikipedia.org/wiki/SOLID

**Narration**
- 이제 SOLID를 하나씩 짚어 보겠습니다. 첫 글자 S는 단일 책임 원칙입니다. 한 클래스는 바뀌어야 할 이유가 하나여야 한다는 뜻입니다. 화면의 코드를 보시죠. 도형 Shape는 오직 자기 넓이만 책임집니다. 넓이를 어떻게 화면에 출력할지는 도형이 아니라 AreaPrinter라는 별도의 존재가 맡습니다. 이렇게 나눠 두면, 출력 방식이 바뀌어도 도형 클래스는 손댈 필요가 없고, 넓이 계산식이 바뀌어도 출력 담당은 흔들리지 않습니다. 비유하자면 요리사가 요리만이 아니라 회계 장부까지 맡고 있는 식당을 떠올려 보세요. 메뉴가 바뀔 때도 이 사람을 부르고, 세법이 바뀔 때도 이 사람을 불러야 합니다. 한 사람에게 서로 다른 두 가지 변화의 이유가 몰려 있으니, 어느 쪽이 바뀌든 그 사람이 흔들립니다. 책임을 하나로 좁히는 것이 단일 책임 원칙입니다.

## Slide 9. O — 개방-폐쇄 원칙: 확장에는 열리고, 수정에는 닫힌다

**Screen**
- 제목: 개방-폐쇄 원칙 — 새 기능은 "추가"로, 기존 코드는 "그대로"
- 짧은 문구:
  - Meyer(1988): 모듈은 확장에는 열려 있고(open), 수정에는 닫혀 있어야(closed) 한다
  - Martin의 폴리모픽 OCP: 추상 타입에 의존하고, 새 동작은 새 구현으로 더한다
  - 판정법: 새 유형 추가에 기존 코드 수정이 필요하면 OCP 위반
- 화면: 좌측에 "열림 = 새 클래스 추가"를 뜻하는 플러스 블록, 우측에 "닫힘 = 기존 코드 자물쇠"를 뜻하는 잠긴 블록. 가운데 추상 타입이 둘을 잇는다.

**Easy analogy**
- 잘 만든 멀티탭과 같다. 새 가전(확장)은 빈 구멍에 꽂기만 하면 된다. 그렇다고 이미 꽂혀 돌아가는 냉장고 배선을 뜯지는 않는다(수정에는 닫힘). 확장의 통로와 기존의 안정, 둘 다 지키는 설계다.

**Practical case**
- 실무사례형 시나리오: 신규 결제 수단을 붙이는 스프린트에서, A팀은 결제 처리 메서드의 if-else를 또 뜯어고쳐 회귀 테스트를 전부 다시 돌린다. B팀은 결제 인터페이스를 구현한 새 클래스 하나만 추가하고 기존 코드는 건드리지 않아, 기존 결제의 테스트를 다시 검증할 필요가 없다. 같은 요구사항인데 변경 비용과 위험이 완전히 다르다.

**Visual asset**
- GPT image prompt: `왼쪽에는 새 클래스를 더하는 플러스 모양의 열린 블록, 오른쪽에는 자물쇠가 걸린 기존 코드 블록, 그리고 가운데 추상 타입이 둘을 잇는 개방-폐쇄 원칙 다이어그램. 확장에는 열리고 수정에는 닫힘을 상징한다. 깔끔한 플랫 스타일, 글자 없이, 16:9`
- Code block for slide:

```java
// 새 도형은 '추가'로 끝난다. 순회하는 App은 한 줄도 고치지 않는다.
class Triangle extends Shape {
    private double base, height;
    Triangle(double b, double h) { base = b; height = h; }
    public double 넓이() { return base * height / 2; }
}
```

**Source**
- 개방-폐쇄 원칙(Meyer 원전·Martin의 폴리모픽 재정의): Meyer가 1988년 제시하고 Martin이 추상 타입에 대한 다형적 재정의로 다시 정식화했다는 설명. https://en.wikipedia.org/wiki/Open%E2%80%93closed_principle
- Robert C. Martin, "The Open Closed Principle" (Clean Coder Blog, 2014): 추상에 의존하고 새 동작을 새 구현으로 추가한다는 폴리모픽 OCP 설명. http://blog.cleancoder.com/uncle-bob/2014/05/12/TheOpenClosedPrinciple.html

**Narration**
- 두 번째 글자 O는 오늘의 주인공, 개방-폐쇄 원칙입니다. 이 원칙은 1988년 버트란드 마이어가 처음 제시했습니다. 소프트웨어 모듈은 확장에는 열려 있어야 하고, 수정에는 닫혀 있어야 한다는 것입니다. 처음 들으면 모순처럼 들립니다. 열려 있으면서 동시에 닫혀 있으라니요. 그런데 두 가지가 서로 다른 대상을 가리킨다는 것을 알면 풀립니다. 열려 있어야 하는 것은 확장, 즉 새로운 기능을 더하는 일입니다. 닫혀 있어야 하는 것은 수정, 즉 이미 잘 돌아가는 기존 코드를 뜯어고치는 일입니다. 새 기능은 추가로 늘리되, 기존 코드는 그대로 둔다. 이것이 개방-폐쇄 원칙입니다. 이후 로버트 마틴은 이 원칙을 객체지향의 언어로 다시 정식화했습니다. 이른바 폴리모픽 개방-폐쇄 원칙입니다. 핵심은 코드가 구체 클래스가 아니라 추상 타입에 의존하게 만들고, 새로운 동작이 필요하면 그 추상 타입을 구현한 새 클래스를 더하는 것입니다. 화면의 코드가 그 모습입니다. Triangle이라는 새 도형은 Shape를 상속해 넓이만 채웁니다. 이렇게 추가만 하면, 도형들을 순회하는 App은 한 줄도 고칠 필요가 없습니다. 지난 시간에 배운 다형성과 동적바인딩이 바로 이것을 가능하게 하는 엔진입니다. 그래서 우리는 아주 간단한 판정법을 쓸 수 있습니다. 새로운 유형을 추가할 때 기존 코드를 고쳐야 하는가? 고쳐야 한다면 그 코드는 개방-폐쇄 원칙을 위반하고 있는 것입니다. 멀티탭을 떠올리시면 됩니다. 새 가전은 빈 구멍에 꽂기만 하면 되고, 이미 꽂혀 돌아가는 냉장고 배선은 뜯지 않습니다. 이 원칙을 오늘 도형 예제로 끝까지 파고들 것입니다.

**Practice**
- 없음.

**Assessment**
- 없음.

## Slide 10. L — 리스코프 치환 원칙: 부모 자리에 자식을 넣어도 옳아야 한다

**Screen**
- 제목: 리스코프 치환 — 자식은 부모의 약속을 깨지 않는다
- 짧은 문구:
  - 부모 타입이 있어야 할 자리에 자식을 넣어도 프로그램이 옳게 동작해야 한다
  - `합계()`는 어떤 자식 도형이 와도 `넓이()`만 제대로 돌려주면 문제없이 작동한다
  - 위반 — `점`처럼 넓이가 없다며 예외를 던지면 부모의 약속을 깨고 프로그램이 멈춘다
- 화면: 좌측에 대타 선수가 규칙을 지켜 경기를 이어 가는 그림, 우측에 규칙을 어겨 경기가 중단되는 그림.

**Easy analogy**
- 대타로 나간 선수가 경기 규칙을 지키면 경기는 그대로 이어진다. 그런데 그 대타가 규칙을 안 지키면 경기 자체가 중단된다. 자식이 부모의 약속을 지켜야 다형성이 안전하게 굴러간다.

**Practical case**
- 실무사례형 시나리오: 결제 인터페이스를 구현한 새 결제 수단이, 정작 결제 메서드에서 "지원하지 않는다"며 예외를 던진다. 겉으로는 같은 타입이라 목록에 섞여 들어오지만, 실행하는 순간 터진다. 부모 자리를 안전하게 대신하지 못하는 자식은 다형성을 무너뜨린다.

**Visual asset**
- GPT image prompt: `야구 경기에서 대타로 들어온 선수가 원래 선수의 자리를 그대로 대신해 규칙대로 경기를 이어 가는 모습과, 규칙을 어겨 경기가 멈추는 모습을 대비한 교육용 일러스트. 부모 자리에 자식을 넣어도 프로그램이 옳게 동작해야 한다는 리스코프 치환 원칙을 상징한다. 깔끔한 플랫 스타일, 글자 없이, 16:9`
- Code block for slide:

```java
// 부모 자리에 자식을 넣어도 프로그램이 옳게 동작해야 한다.
double 합계(List<Shape> shapes) {
    double sum = 0;
    for (Shape s : shapes) sum += s.넓이();   // 어떤 자식이 와도 넓이를 돌려준다
    return sum;
}

// 위반 — 부모의 약속을 자식이 깬다
class 점 extends Shape {
    @Override public double 넓이() { throw new UnsupportedOperationException("점은 넓이가 없다"); }
}
```

**Source**
- 리스코프 치환 원칙: 하위 타입은 상위 타입을 대체할 수 있어야 하며, 프로그램의 정확성을 깨지 않아야 한다는 원칙. https://en.wikipedia.org/wiki/Liskov_substitution_principle

**Narration**
- 세 번째 글자 L은 리스코프 치환 원칙입니다. 부모 타입이 있어야 할 자리에 자식 타입을 넣어도 프로그램이 여전히 옳게 동작해야 한다는 원칙입니다. 화면 위쪽의 합계 메서드를 보시죠. Shape들의 목록을 받아 각자의 넓이를 더합니다. 여기에 어떤 자식 도형이 들어오든, 넓이를 제대로 돌려주기만 하면 이 메서드는 아무 문제 없이 동작합니다. 그런데 아래쪽 점 클래스를 보시죠. 점은 넓이가 없다면서 예외를 던집니다. 겉으로는 Shape의 자식이지만, 부모가 한 약속, 즉 넓이를 돌려준다는 약속을 깨 버립니다. 이런 자식이 목록에 섞여 들어오면 합계 메서드는 그 순간 터집니다. 부모 자리를 자식이 안전하게 대신하지 못한 것입니다. 야구로 비유하면, 대타로 나간 선수가 경기 규칙을 지키지 않으면 경기 자체가 중단되는 것과 같습니다. 지난 시간에 배운 다형성이 안전하게 작동하려면, 자식이 부모의 약속을 반드시 지켜야 합니다. 그 조건이 바로 리스코프 치환 원칙입니다.

## Slide 11. I — 인터페이스 분리 원칙: 안 쓰는 계약을 강요하지 않는다

**Screen**
- 제목: 인터페이스 분리 — 필요한 계약만 지키게 한다
- 짧은 문구:
  - 넓이만 필요한 쪽에 그리기를 강요하지 않는다
  - 큰 인터페이스 하나 대신, `넓이계산가능`·`그리기가능`으로 잘게 나눈다
  - `통계도형`은 넓이만 구현하면 된다 — 그리기를 억지로 채울 필요가 없다
- 화면: 좌측에 버튼이 수십 개 달린 복잡한 리모컨, 우측에 꼭 필요한 버튼만 남긴 단순한 리모컨.

**Easy analogy**
- 리모컨에 안 쓰는 버튼이 40개 달려 있으면, 버튼 하나 바뀔 때마다 설명서를 다시 읽어야 한다. 필요한 버튼만 남긴 리모컨은 배우기도, 바뀔 때 대응하기도 쉽다.

**Practical case**
- 실무사례형 시나리오: "기기"라는 하나의 큰 인터페이스에 인쇄·스캔·팩스를 전부 몰아넣으면, 인쇄만 하는 단순 프린터도 스캔과 팩스 메서드를 억지로 구현해야 한다. 결국 "지원 안 함" 예외로 채워진 빈 껍데기 메서드가 늘어난다. 인터페이스를 기능별로 쪼개면 각 기기가 자기에게 필요한 계약만 구현한다.

**Visual asset**
- GPT image prompt: `버튼이 수십 개 달려 복잡한 리모컨과, 꼭 필요한 버튼만 남긴 단순한 리모컨을 좌우로 대비한 교육용 일러스트. 필요 없는 기능을 강요하지 않는 인터페이스 분리 원칙을 상징한다. 깔끔한 플랫 스타일, 글자 없이, 16:9`
- Code block for slide:

```java
// 넓이만 필요한 쪽에 그리기를 강요하지 않는다.
interface 넓이계산가능 { double 넓이(); }
interface 그리기가능 { void 그리기(); }

class 화면도형 implements 넓이계산가능, 그리기가능 {
    public double 넓이() { return 1; }
    public void 그리기() { System.out.println("그린다"); }
}
class 통계도형 implements 넓이계산가능 {   // 그리기를 구현할 필요가 없다
    public double 넓이() { return 2; }
}
```

**Source**
- 인터페이스 분리 원칙: 클라이언트는 자신이 사용하지 않는 인터페이스에 의존하도록 강요받지 않아야 한다는 원칙. https://en.wikipedia.org/wiki/Interface_segregation_principle

**Narration**
- 네 번째 글자 I는 인터페이스 분리 원칙입니다. 어떤 대상에게, 그가 쓰지도 않는 기능까지 억지로 구현하게 만들지 말라는 원칙입니다. 화면의 코드를 보시죠. 넓이 계산과 그리기를 하나의 큰 인터페이스로 묶지 않고, 넓이계산가능과 그리기가능이라는 두 개의 작은 인터페이스로 나눴습니다. 화면에 그려지는 도형은 두 가지를 다 구현하면 됩니다. 그런데 통계용으로만 쓰이는 도형은 넓이만 있으면 충분합니다. 그리기를 억지로 구현할 필요가 없습니다. 인터페이스를 잘게 나눠 두었기 때문에, 이 통계 도형은 자기에게 필요한 계약만 지키면 됩니다. 만약 넓이와 그리기가 하나로 묶여 있었다면, 통계 도형도 쓰지도 않는 그리기 메서드를 억지로 채워야 했을 것입니다. 리모컨에 안 쓰는 버튼이 사십 개나 달려 있다고 생각해 보세요. 버튼 하나가 바뀔 때마다 두꺼운 설명서를 다시 읽어야 합니다. 필요한 것만 담은 작은 계약이 그래서 편합니다. 이것이 인터페이스 분리 원칙입니다.

## Slide 12. D — 의존성 역전 원칙: 구체가 아니라 추상에 의존한다

**Screen**
- 제목: 의존성 역전 — App은 구체를 모른 채 추상만 바라본다
- 짧은 문구:
  - `App`은 구체(`Circle`)가 아니라 추상(`Shape`)에 의존한다
  - 배열에 무엇이 들어 있든 순회 코드는 `Shape`만 바라본다 — 구체 클래스를 몰라도 된다
  - 새 도형이 아무리 늘어도 상위 코드는 그 구체를 알 필요가 없다
- 화면: 좌측에 벽의 표준 콘센트, 우측에 규격만 맞추면 그대로 꽂히는 여러 가전(선풍기·충전기). 상위 코드가 구체를 모른 채 추상 규격에만 의존함을 표현.

**Easy analogy**
- 벽의 콘센트 규격(추상)에 맞추면 어떤 가전이든 꽂힌다. 콘센트는 어떤 가전이 올지 미리 알지 못해도 된다. 가전마다 벽을 새로 뚫지 않는다.

**Practical case**
- 실무사례형 시나리오: 주문 서비스가 특정 결제사(구체 클래스)를 직접 import 해서 호출하면, 결제사가 하나 늘 때마다 서비스 코드를 고쳐야 한다. 반대로 결제라는 추상 타입에만 의존하게 만들면, 새 결제사는 그 추상을 구현한 새 클래스로 더할 뿐 서비스는 그대로다. 의존의 방향이 구체에서 추상으로 뒤집힌다.

**Visual asset**
- GPT image prompt: `벽면의 표준 콘센트 규격에 맞추기만 하면 어떤 가전이든 그대로 꽂히는 모습을 보여 주는 교육용 일러스트. 구체가 아니라 추상(규격)에 의존한다는 의존성 역전 원칙을 상징한다. 깔끔한 플랫 스타일, 글자 없이, 16:9`
- Code block for slide:

```java
// App은 구체(Circle)가 아니라 추상(Shape)에 의존한다.
Shape[] shapes = { new Rectangle(4, 5), new Circle(3) };
for (Shape shape : shapes) {
    System.out.println("넓이 : " + shape.넓이());   // Circle을 몰라도 된다
}
```

**Source**
- 의존성 역전 원칙: 상위 모듈은 하위 모듈이 아니라 추상에 의존해야 한다는 원칙. https://en.wikipedia.org/wiki/Dependency_inversion_principle

**Narration**
- 마지막 글자 D는 의존성 역전 원칙입니다. 구체적인 구현이 아니라 추상에 의존하라는 원칙입니다. 화면의 코드를 보시죠. App은 Shape 배열을 순회하며 넓이를 호출합니다. 배열 안에 Rectangle이 들어 있든 Circle이 들어 있든, App은 그것이 무엇인지 알 필요가 없습니다. App이 바라보는 것은 오직 Shape라는 추상 타입뿐입니다. 그래서 새로운 도형이 아무리 많이 생겨도 App은 그 구체 클래스들을 몰라도 됩니다. 이것이 의존의 방향을 뒤집는다는 뜻입니다. 보통은 상위 코드가 하위의 구체 구현들을 하나하나 알아야 할 것 같지만, 추상에 의존하게 만들면 상위 코드가 구체를 몰라도 되도록 방향이 역전됩니다. 콘센트 규격을 떠올리시면 됩니다. 벽의 콘센트는 어떤 가전이 올지 미리 알지 못합니다. 그저 표준 규격, 즉 추상만 지키면 선풍기든 노트북 충전기든 다 꽂힙니다. 가전마다 벽을 새로 뚫지 않습니다. 흥미롭게도 오늘 재설계할 도형 예제는 개방-폐쇄 원칙을 지키는 과정에서 이 의존성 역전까지 자연스럽게 함께 지켜지게 됩니다.

## Slide 13. 문제 코드 진단: if-else로 짠 넓이 계산 (step2)

**Screen**
- 제목: 나쁜 예 — 넓이계산() 하나가 모든 도형을 떠안는다
- 화면: `App.java`(step2) 전체 코드를 크게 표시하고, `넓이계산(String type, ...)` 메서드 안의 `if (type.equals("사각형"))` / `else if (type.equals("원"))` 분기에 하이라이트. 우측 하단에 실행 결과 두 줄("넓이 : 20.0" / "넓이 : 28.26").
- 진단 라벨: "이 메서드가 모든 도형 종류를 안다 = 강한 결합 + OCP 위반 예약석"

**Easy analogy**
- 식당의 단 한 명뿐인 요리사가 모든 메뉴의 조리법을 머릿속 if-else로 외우고 있는 상황이다. 신메뉴가 생길 때마다 이 요리사의 머리(넓이계산 메서드)를 열어 조리법을 새로 심어야 한다.

**Practical case**
- 실무사례형 시나리오: 이 코드는 도형이 사각형과 원, 둘뿐일 때는 아무 문제 없이 잘 돈다. 문제는 "잘 돈다"는 사실이 위험을 가린다는 점이다. 유형이 둘일 때 멀쩡하기 때문에, 셋째·넷째 유형이 붙기 시작하는 6개월 뒤에야 이 구조의 비용이 청구된다.

**Visual asset**
- Code block for slide:

```java
package ex02;

/**
 * 문제 : 도형 종류가 늘어날 때마다 이 계산 로직의 if-else를 계속 고쳐야 한다.
 */
public class App {
    public static void main(String[] args) {
        String[] types = {"사각형", "원"};
        double[][] values = {{4, 5}, {3, 0}}; // 사각형: 가로/세로, 원: 반지름/(안씀)

        for (int i = 0; i < types.length; i++) {
            System.out.println("넓이 : " + 넓이계산(types[i], values[i][0], values[i][1]));
        }

        // 삼각형이 필요하면? 아래 넓이계산() 안에 else if를 또 추가해야 한다.
    }

    static double 넓이계산(String type, double a, double b) {
        if (type.equals("사각형")) {
            return a * b;
        } else if (type.equals("원")) {
            return a * a * 3.14;
        } else {
            throw new IllegalArgumentException("모르는 도형 : " + type);
        }
    }
}
```

**Source**
- 실습 정답 소스(패턴 미적용 step2): `code/design-pattern-start/src/ex02/App.java`
- 개방-폐쇄 원칙(Meyer·Martin): 조건 분기 기반 구현이 새 유형마다 수정을 요구해 OCP를 위반한다는 진단 근거. https://en.wikipedia.org/wiki/Open%E2%80%93closed_principle

**Narration**
- 이제 진단할 환자를 데려오겠습니다. 화면의 코드는 도형의 넓이를 계산하는 프로그램입니다. main을 보면 도형의 종류를 문자열 배열로, 값을 이차원 배열로 준비해 두고, 넓이계산이라는 메서드에 종류와 값을 넘겨 호출합니다. 넓이계산 메서드 안을 보시죠. 종류가 사각형이면 가로 곱하기 세로를 반환하고, 원이면 반지름 곱하기 반지름 곱하기 삼점일사를 반환합니다. 둘 다 아니면 모르는 도형이라며 예외를 던집니다. 실행하면 넓이 이십점영, 넓이 이십팔점이육이 잘 출력됩니다. 코드가 짧고 결과도 정확합니다. 그런데 바로 이 "잘 돈다"가 함정입니다. 조금 전에 배운 판정법을 여기에 들이대 보겠습니다. "새로운 도형을 추가하면 어디를 고쳐야 하는가?" 답은 명확합니다. 넓이계산 메서드 안으로 들어가서 else if 한 줄을 또 심어야 합니다. 이 메서드 하나가 세상의 모든 도형 종류를 다 알고 있어야 하는 구조인 것입니다. 도형이 늘어날수록 이 메서드는 계속 뚱뚱해지고, 한 도형의 계산식을 고치다 다른 도형의 분기를 실수로 건드릴 위험도 함께 커집니다. 식당에 요리사가 딱 한 명 있는데, 그 요리사 머릿속에 모든 메뉴의 조리법이 if-else로 들어 있는 셈입니다. 신메뉴가 생길 때마다 이 요리사의 머리를 열어 조리법을 새로 심어야 합니다. 정답 소스의 주석마저 친절하게 예고하고 있습니다. "삼각형이 필요하면 아래 넓이계산 안에 else if를 또 추가해야 한다." 이 코드는 개방-폐쇄 원칙 위반의 예약석에 앉아 있습니다. 다음 슬라이드에서 실제로 삼각형을 추가하며 그 비용을 눈으로 확인하겠습니다.

**Practice**
- 없음. 다음 슬라이드부터 이 코드를 직접 실행·수정한다.

**Assessment**
- 없음.

## Slide 14. 확장 비용 비교: 삼각형을 추가하면 무슨 일이 벌어지는가

**Screen**
- 제목: 새 도형 하나 = 기존 메서드 수정 + 회귀 위험
- 화면: 좌우 비교 패널.
  - 왼쪽(if-else 방식): 삼각형 추가 → `넓이계산()` 내부에 `else if` 삽입 → 기존 사각형·원 로직과 한 메서드에서 재컴파일·재검증
  - 오른쪽(추상화 방식, 예고): 삼각형 추가 → `Triangle` 클래스만 신규 생성 → `App`은 한 줄도 수정 없음
- 하단 라벨: "같은 요구사항, 다른 비용"

**Easy analogy**
- 벽에 못을 더 박는 두 가지 방법과 같다. 하나는 벽을 헐고 다시 쌓으며 못을 넣는 방식(if-else 수정), 다른 하나는 미리 뚫어 둔 규격 구멍에 못을 꽂는 방식(새 클래스 추가)이다. 결과는 같아 보여도 위험과 시간이 다르다.

**Practical case**
- 실무사례형 시나리오: 유형이 열 개를 넘는 실제 서비스에서 if-else 방식은 새 유형 추가 때마다 그 거대한 메서드 전체를 다시 읽고 검증해야 한다. 반면 추상화 방식은 새 클래스의 단위 테스트만 통과하면 되고, 기존 유형들은 손대지 않았으므로 회귀 테스트 범위가 극적으로 줄어든다.

**Visual asset**
- GPT image prompt: `좌우 비교 일러스트. 왼쪽은 삼각형을 추가하려고 하나의 거대한 공용 메서드 안을 뜯어고쳐 경고의 금이 가는 모습, 오른쪽은 삼각형을 별도의 새 클래스로 추가하고 기존 앱 코드에는 자물쇠가 걸려 손대지 않는 모습. 깔끔한 교육용 플랫 스타일, 글자 없이, 16:9`
- Code block for slide:

```java
// [if-else 방식] 삼각형을 넣으려면 기존 넓이계산() 메서드를 뜯어고쳐야 한다
static double 넓이계산(String type, double a, double b) {
    if (type.equals("사각형")) {
        return a * b;
    } else if (type.equals("원")) {
        return a * a * 3.14;
    } else if (type.equals("삼각형")) {   // ← 새 유형마다 여기를 계속 수정 (OCP 위반)
        return a * b / 2;
    } else {
        throw new IllegalArgumentException("모르는 도형 : " + type);
    }
}
```

**Source**
- 실습 정답 소스(패턴 미적용 step2): `code/design-pattern-start/src/ex02/App.java`
- Robert C. Martin, "The Open Closed Principle" (Clean Coder Blog, 2014): 새 요구사항을 수정이 아니라 추가로 흡수하는 것이 OCP의 목표라는 설명. http://blog.cleancoder.com/uncle-bob/2014/05/12/TheOpenClosedPrinciple.html

**Narration**
- 이제 같은 요구사항을 두 방식이 각각 얼마의 비용으로 처리하는지 비교하겠습니다. 요구사항은 하나입니다. "삼각형 넓이도 계산하게 해 주세요." 먼저 if-else 방식입니다. 화면을 보시면 넓이계산 메서드 안에 삼각형 분기를 하나 더 끼워 넣었습니다. 밑변 곱하기 높이 나누기 이, 이렇게요. 코드로는 단 세 줄입니다. 그런데 이 세 줄이 어디에 들어갔는지가 중요합니다. 사각형과 원의 계산 로직이 살고 있는 바로 그 메서드 안입니다. 즉 이미 잘 돌아가던 기존 코드를 열어 수정한 것입니다. 개방-폐쇄 원칙의 관점에서 이것은 명백한 위반입니다. 수정에는 닫혀 있어야 하는데 열어 버렸으니까요. 실무적으로도 대가가 따릅니다. 이 메서드를 건드렸으니, 사각형과 원이 여전히 잘 계산되는지까지 다시 검증해야 합니다. 유형이 두 개일 때는 사소하지만, 열 개를 넘는 실제 서비스에서는 새 유형 하나 추가에 그 거대한 메서드 전체를 다시 읽고 회귀 테스트를 다시 돌리는 일이 됩니다. 반대로 오른쪽, 잠시 뒤에 만들 추상화 방식을 미리 보겠습니다. 여기서는 삼각형을 추가할 때 Triangle이라는 클래스 하나만 새로 만듭니다. 기존의 App 코드는 한 줄도 고치지 않습니다. 미리 뚫어 둔 규격 구멍에 새 못을 꽂는 것과 같습니다. 같은 요구사항인데 한쪽은 벽을 헐고, 다른 한쪽은 꽂기만 합니다. 이 차이가 바로 유지보수성의 실체입니다. 그러면 이제 그 규격 구멍을 뚫는 재설계로 넘어가겠습니다.

**Practice**
- 없음. 실습 단계에서 직접 이 수정을 해 보며 비용을 체감한다.

**Assessment**
- 없음.

## Slide 15. 재설계 1: 약속을 만든다 — abstract class Shape

**Screen**
- 제목: 모든 도형이 지켜야 할 약속을 추상 타입으로
- 짧은 문구:
  - `abstract class Shape` — "도형이라면 넓이()가 있어야 한다"는 약속
  - `public abstract double 넓이();` — 몸통 없이 계약만 선언
  - Shape는 `new` 불가 — 약속만 있고 내용이 없으므로
- 화면: 상단에 점선으로 그린 도형 설계도(Shape), "new 금지" 표시. 아래로 화살표가 사각형·원·삼각형 자리로 내려가는 예고 구도.

**Easy analogy**
- 콘센트 규격 표준과 같다. "구멍은 이 모양, 전압은 이 값"이라는 약속만 정해 두면, 실제 플러그(구현)는 제조사마다 자유롭게 만들되 규격만 지키면 다 꽂힌다. Shape는 도형 세계의 콘센트 규격이다.

**Practical case**
- 실무사례형 시나리오: 사내 공통 모듈에서 `NotificationSender`, `PaymentGateway` 같은 추상 타입에 "보낸다", "결제한다"는 계약만 정의해 두는 설계를 자주 본다. 계약을 먼저 세워 두면, 구체 구현은 나중에 팀별로 병렬로 채워도 호출부는 흔들리지 않는다.

**Visual asset**
- GPT image prompt: `상단에 점선으로 그린 도형의 설계도(추상 계약)와 인스턴스화 금지를 뜻하는 작은 금지 표시, 그 아래로 구체적인 도형들이 들어갈 빈 자리를 가리키는 화살표. 깔끔한 교육용 다이어그램 스타일, 글자 없이, 16:9`
- Code block for slide:

```java
package ex02;

// 모든 도형이 지켜야 할 약속
public abstract class Shape {
    public abstract double 넓이();
}
```

**Source**
- 실습 정답 소스(패턴 적용 final): `code/design-pattern-end/src/ex02/Shape.java`
- Oracle Java Tutorials – Abstract Methods and Classes: 추상 클래스는 인스턴스화할 수 없고, 추상 메서드는 몸통 없이 선언만 하며 하위 클래스가 구현을 제공한다는 설명. https://docs.oracle.com/javase/tutorial/java/IandI/abstract.html

**Narration**
- 이제 재설계를 시작합니다. 개방-폐쇄 원칙을 지키는 첫걸음은, 코드가 구체 클래스가 아니라 추상 타입에 의존하게 만드는 것이라고 했습니다. 그래서 가장 먼저 할 일은 "약속"을 만드는 것입니다. 화면의 코드를 보시죠. 딱 세 줄입니다. abstract class Shape, 그 안에 public abstract double 넓이. 이것이 전부입니다. 이 코드가 말하는 것은 단 하나입니다. "이 세상의 도형이라면, 자기 넓이를 구할 줄 알아야 한다." 다만 어떻게 구하는지는 여기 적혀 있지 않습니다. 넓이 메서드에 몸통이 없기 때문입니다. 약속만 있고 내용은 비어 있는 상태, 그래서 Shape는 abstract이고 new로 직접 만들 수 없습니다. 넓이를 어떻게 구할지 모르는 막연한 "도형"이라는 객체는 성립할 수 없으니까요. 앞서 가구는 존재하지 않고 의자·책상만 존재한다고 했던 그 감각과 정확히 같은 구조입니다. 콘센트 규격 표준을 떠올리시면 됩니다. 구멍 모양과 전압이라는 약속만 표준으로 정해 두면, 실제 플러그는 제조사가 자유롭게 만들되 규격만 지키면 다 꽂힙니다. Shape는 도형 세계의 콘센트 규격입니다. 이 약속 하나를 세워 두는 것이, 앞으로 어떤 도형이 와도 꽂아 쓸 수 있는 규격 구멍을 뚫는 일입니다. 다음 슬라이드에서 이 규격에 맞는 실제 도형들을 채워 보겠습니다.

## Slide 16. 재설계 2: 약속을 채운다 — Rectangle과 Circle

**Screen**
- 제목: 각 도형이 자기 넓이를 스스로 책임진다
- 짧은 문구:
  - `Rectangle extends Shape` — `private width, height`, `넓이()`는 `width * height`
  - `Circle extends Shape` — `private radius`, `넓이()`는 `radius * radius * 3.14`
  - 상태(필드)는 private, 계산 로직은 각자 자기 안에 캡슐화
- 화면: Shape 설계도 아래에 사각형·원 두 구현 카드. 각 카드에 private 필드와 `@Override 넓이()`를 표시.

**Easy analogy**
- 프랜차이즈 본사 매뉴얼(Shape) 아래, 실제로 문을 연 지점들(Rectangle·Circle)과 같다. 각 지점은 본사 규격을 지키되, 자기 주방 사정에 맞게 조리 방식을 스스로 책임진다. 본사는 각 지점 주방에 일일이 개입하지 않는다.

**Practical case**
- 실무사례형 시나리오: 넓이 계산식이 도형마다 다르다는 것은 자연스럽다. 문제는 그 서로 다른 식들을 어디에 둘 것인가였다. if-else 방식은 한 메서드에 다 몰아넣었고, 추상화 방식은 각 도형 클래스 안으로 흩어 담았다. 각자 자기 것만 알면 되니, 원의 계산식을 고쳐도 사각형은 존재조차 모른다 — 결합이 끊어진 것이다.

**Visual asset**
- GPT image prompt: `추상 도형 계약 아래에 놓인 두 개의 구현 카드 — 사각형 카드와 원 카드 — 가 각각 자물쇠가 걸린 private 필드와 자신만의 넓이 계산 메서드를 지닌 모습. 각 도형이 자기 계산을 스스로 책임진다는 것을 강조한다. 깔끔한 플랫 교육용 스타일, 글자 없이, 16:9`
- Code block for slide:

```java
package ex02;

public class Rectangle extends Shape {

    private double width;
    private double height;

    public Rectangle(double width, double height) {
        this.width = width;
        this.height = height;
    }

    @Override
    public double 넓이() {
        return width * height;
    }
}
```

```java
package ex02;

public class Circle extends Shape {

    private double radius;

    public Circle(double radius) {
        this.radius = radius;
    }

    @Override
    public double 넓이() {
        return radius * radius * 3.14;
    }
}
```

**Source**
- 실습 정답 소스(패턴 적용 final): `code/design-pattern-end/src/ex02/Rectangle.java`, `code/design-pattern-end/src/ex02/Circle.java`
- Oracle Java Tutorials – Controlling Access to Members of a Class: 필드를 private으로 두고 동작을 메서드로 노출하는 캡슐화 권장. https://docs.oracle.com/javase/tutorial/java/javaOO/accesscontrol.html

**Narration**
- 약속을 세웠으니 이제 그 약속을 실제로 채우겠습니다. 화면에 두 클래스가 있습니다. 먼저 Rectangle입니다. Shape를 extends 하고, 가로와 세로를 private 필드로 가집니다. 생성자로 값을 받아 두고, 넓이 메서드를 재정의해서 가로 곱하기 세로를 반환합니다. 다음은 Circle입니다. 마찬가지로 Shape를 extends 하고, 반지름을 private 필드로 가지며, 넓이 메서드에서 반지름 곱하기 반지름 곱하기 삼점일사를 반환합니다. 여기서 두 가지를 짚겠습니다. 첫째, 앞서 배운 캡슐화가 그대로 살아 있습니다. 가로, 세로, 반지름은 전부 private입니다. 바깥에서 이 값을 직접 만질 수 없고, 각 도형이 세상에 내놓는 것은 오직 넓이라는 행위뿐입니다. 상태가 행위 뒤에 숨어 있습니다. 앨리스가 키를 숨기고 버섯 먹는 행위로만 키를 바꾸던 것과 똑같습니다. 둘째, 그리고 이것이 재설계의 핵심인데, 넓이 계산식이 이제 각 도형 클래스 안으로 흩어져 들어갔다는 점입니다. if-else 방식에서는 사각형 식과 원 식이 한 메서드 안에 나란히 붙어 있었습니다. 지금은 사각형 식은 Rectangle 안에만, 원 식은 Circle 안에만 있습니다. 원의 계산식을 고쳐도 사각형은 그런 일이 있었는지조차 모릅니다. 강하게 묶여 있던 결합이 끊어진 것입니다. 프랜차이즈로 비유하면, 본사 매뉴얼은 Shape이고 실제로 문을 연 지점들이 Rectangle과 Circle입니다. 각 지점은 규격을 지키되 자기 주방은 스스로 책임지고, 본사는 지점 주방에 일일이 개입하지 않습니다. 이렇게 책임을 각자에게 나눠 준 덕분에, 다음 슬라이드에서 볼 계산기 코드는 놀랄 만큼 단순하고 안정적으로 바뀝니다.

## Slide 17. 재설계 3: App은 Shape[]만 순회한다 — 무수정 확장의 완성

**Screen**
- 제목: 계산기는 도형의 종류를 모른다 — 그래서 안 고쳐도 된다
- 짧은 문구:
  - `Shape[] shapes = { new Rectangle(4,5), new Circle(3) };`
  - `for (Shape shape : shapes) ... shape.넓이()` — 추상 타입에만 의존
  - 삼각형이 필요하면? `Triangle extends Shape` 클래스만 추가, App은 한 줄도 안 고친다
- 화면: 좌측에 `App`이 `Shape` 배열만 바라보는 그림. 우측에 새 `Triangle` 블록이 배열에 "꽂히기만" 하고 App 코드에는 자물쇠가 걸린 그림.

**Easy analogy**
- 리모컨 하나로 어느 회사 TV든 켜는 것과 같다. 리모컨(App)은 "TV라면 전원 버튼이 있다"는 약속만 누른다. 새 브랜드 TV(새 도형)가 나와도 리모컨을 새로 사지 않는다 — 약속만 지키면 그대로 켜진다.

**Practical case**
- 실무사례형 시나리오: 정답 소스 App.java의 주석이 이 원리를 그대로 선언한다. "삼각형이 필요하면 Triangle extends Shape 클래스만 새로 만들면 끝. 아래 App 코드는 전혀 고칠 필요가 없다. 이게 바로 OCP." 이 한 문장이 오늘 배운 모든 것의 결론이다.

**Visual asset**
- Code block for slide:

```java
package ex02;

/**
 * 목표 : SOLID 중 OCP (개방-폐쇄 원칙)
 *
 * 핵심 : 새 도형이 생겨도, 계산기(App) 코드는 "수정하지 않는다".
 * (확장에는 열려있고 O, 수정에는 닫혀있다 X)
 */
public class App {
    public static void main(String[] args) {

        Shape[] shapes = {
                new Rectangle(4, 5),
                new Circle(3)
        };

        for (Shape shape : shapes) {
            System.out.println("넓이 : " + shape.넓이());
        }

        // 삼각형이 필요하면? '삼각형(Triangle) extends Shape' 클래스만 새로 만들면 끝!
        // 아래 App 코드는 전혀 고칠 필요가 없다. ← 이게 바로 OCP
    }
}
```

**Source**
- 실습 정답 소스(패턴 적용 final): `code/design-pattern-end/src/ex02/App.java`
- Oracle Java Tutorials – Polymorphism: 상위 타입 참조로 순회하며 각 실제 객체의 재정의 메서드가 실행 시점에 선택된다는 설명. https://docs.oracle.com/javase/tutorial/java/IandI/polymorphism.html

**Narration**
- 재설계의 마지막 조각, 계산기 App입니다. 화면을 보시죠. Shape 배열을 만들고 그 안에 Rectangle과 Circle 객체를 담습니다. 그리고 향상된 for문으로 배열을 돌면서 각 도형의 넓이를 호출합니다. 여기서 딱 한 줄에 오늘의 모든 것이 들어 있습니다. for문의 변수 타입이 Shape라는 점입니다. App은 지금 자기가 다루는 것이 사각형인지 원인지 전혀 모릅니다. 그저 "Shape라면 넓이를 구할 줄 안다"는 약속만 믿고 넓이를 호출할 뿐입니다. 실제로 어떤 넓이 계산이 실행될지는, 지난 시간에 배운 동적바인딩이 실행 시점에 실제 객체를 보고 선택해 줍니다. 이제 개방-폐쇄 원칙의 판정법을 다시 들이대 보겠습니다. "삼각형을 추가하면 App의 어디를 고쳐야 하는가?" 답은, 고칠 곳이 없다, 입니다. Triangle이라는 클래스를 하나 새로 만들어 Shape를 extends 하고 넓이만 채우면, 배열에 그 객체를 담는 순간 for문은 아무것도 바뀌지 않은 채 삼각형의 넓이까지 계산해 냅니다. 정답 소스의 주석이 이것을 그대로 선언합니다. "삼각형이 필요하면 Triangle extends Shape 클래스만 새로 만들면 끝. 아래 App 코드는 전혀 고칠 필요가 없다. 이게 바로 OCP." 리모컨 하나로 어느 브랜드 TV든 켜는 것과 같습니다. 새 브랜드 TV가 나와도 리모컨을 새로 사지 않습니다. 전원 버튼이라는 약속만 지키면 그대로 켜집니다. 조금 전 if-else 방식은 삼각형을 넣으려고 기존 메서드를 뜯어고쳤습니다. 지금 이 구조는 삼각형 클래스를 꽂기만 합니다. 확장에는 열려 있고, 수정에는 닫혀 있는, 개방-폐쇄 원칙이 코드로 완성된 모습입니다.

**Practice**
- 없음. 실습 단계에서 직접 이 구조로 재설계하고 Triangle을 추가한다.

public class App {
    public static void main(String[] args) {
        String[] types = {"사각형", "원"};
        double[][] values = {{4, 5}, {3, 0}};

        for (int i = 0; i < types.length; i++) {

        }

        } else {

        }
    }
}

- 이미 완성해 벽에 건 그림에 새 인물을 넣으려고 그림 전체를 다시 붓질하는 것과 같다. 새 인물 하나 때문에 이미 그린 부분까지 다시 건드리게 된다.

**Practical case**
- 실무사례형 시나리오: 실제로는 이 "몇 군데"가 훨씬 많다. 유형에 따라 입력 형식이 다르면 검증 로직도, 예외 처리도 함께 늘어난다. 한 유형 추가가 서너 곳의 수정으로 번지는 것을 지금 두 곳으로 축소해 체험하는 것이다.

**Visual asset**
- Code block for slide:

```java
// [실습 2] 문제 코드에 삼각형을 추가 — 기존 코드를 여러 군데 뜯어고쳐야 한다
String[] types = {"사각형", "원", "삼각형"};        // ← main 배열 수정 (1)
double[][] values = {{4, 5}, {3, 0}, {6, 4}};      // ← main 배열 수정

static double 넓이계산(String type, double a, double b) {
    if (type.equals("사각형")) {
        return a * b;
    } else if (type.equals("원")) {
        return a * a * 3.14;
    } else if (type.equals("삼각형")) {              // ← 기존 메서드 수정 (2)
        return a * b / 2;
    } else {
        throw new IllegalArgumentException("모르는 도형 : " + type);
    }
}
```

**Narration**
- 두 번째 실습입니다. 이제 방금 만든 문제 코드에 삼각형을 추가해 보겠습니다. 삼각형 넓이는 밑변 곱하기 높이 나누기 이입니다. 화면을 따라 두 곳을 고쳐 주세요. 먼저 넓이계산 메서드 안으로 들어가서, 원 분기 다음에 삼각형 분기를 else if로 하나 더 추가합니다. 그다음 main으로 올라가서 types 배열에 삼각형을 넣고, values 배열에도 밑변 육, 높이 사 같은 값을 추가합니다. 다 고치셨으면 실행해서 삼각형 넓이 십이가 새 줄로 출력되는지 확인합니다. 잘 나올 것입니다. 그런데 여기서 잠깐 멈추고 세어 보겠습니다. 삼각형이라는 도형 하나를 추가하려고 우리가 몇 군데를 고쳤나요? 최소 두 군데입니다. 넓이계산 메서드 안, 그리고 main의 배열입니다. 그리고 이 두 곳은 모두 이미 잘 돌아가던 기존 코드였습니다. 우리는 기존 코드를 열어서 수정한 것입니다. 조금 전에 배운 판정법 그대로, 새 유형 추가가 기존 코드 수정을 강제했으니 이것은 개방-폐쇄 원칙 위반입니다. 완성해서 벽에 건 그림에 새 인물을 넣겠다고 그림 전체를 다시 붓질하는 것과 같습니다. 지금은 두 곳이라 견딜 만합니다. 하지만 실무에서는 유형마다 입력 형식과 검증, 예외 처리가 달라서 한 유형 추가가 서너 곳으로 번지기 일쑤입니다. 이 불편함을 손끝으로 기억해 두세요. 다음 실습에서 우리는 바로 이 통증을 없애는 재설계를 합니다.

**Practice**

  - 관점 2(동작 전달): 계산 로직을 람다/함수로 넘기는 함수형 표현
  - 무엇을 쓰든 뿌리는 오늘의 다형성·OCP: "구체가 아니라 추상/계약에 의존"
- 화면: 좌측에 sealed 계층 트리(허용된 하위 타입만) + switch 분기, 우측에 함수를 인자로 넘기는 람다 화살표. 하단에 "선택 기준: 확장이 잦으면 다형성, 종류가 고정이면 sealed+switch".

**Easy analogy**
- 같은 목적지에 가는 두 교통편과 같다. 버스(전통적 다형성)는 정류장을 늘리기 쉽고, 지하철(sealed+switch)은 노선이 고정된 대신 빠짐없이 관리된다. 목적지(변경에 강한 설계)는 같고, 상황에 따라 고른다.

**Practical case**
- 실무사례형 시나리오: 도형 종류가 앞으로도 계속 늘어난다면 오늘 배운 추상 클래스 다형성이 유리하다 — 새 클래스만 꽂으면 되니까. 반대로 종류가 딱 정해져 더 늘 일이 없다면(예: 신호등 색 3가지), sealed로 하위 타입을 봉인하고 switch 패턴 매칭으로 처리하면 컴파일러가 누락 케이스를 잡아 준다. from-gof-to-lambda 예제들은 전략·템플릿 같은 행동 패턴을 람다로 간결화하는 갈래를 보여 준다.

**Visual asset**
- GPT image prompt: `좌우 비교 교육용 일러스트. 왼쪽은 허용된 하위 타입만 가지를 뻗는 sealed 클래스 계층 트리가 switch로 이어지는 모습, 오른쪽은 동작을 함수로 넘기는 람다 화살표. 둘 다 같은 다형성 원리의 현대적 표현임을 나타낸다. 깔끔한 플랫 스타일, 글자 없이, 16:9`

**Source**
- Modern Java Language Features: Records, Sealed Classes, Pattern Matching (Java Code Geeks): sealed 클래스와 switch 패턴 매칭으로 종류가 고정된 계층을 안전하게 처리한다는 설명. https://www.javacodegeeks.com/2025/12/modern-java-language-features-records-sealed-classes-pattern-matching.html
- mariofusco/from-gof-to-lambda (GitHub): 고전 행동 패턴을 람다/함수 전달로 현대화한 예제 모음. https://github.com/mariofusco/from-gof-to-lambda

**Narration**
- 오늘 배운 추상 클래스 기반 다형성이 개방-폐쇄 원칙을 지키는 정석입니다. 다만 현대 Java에서는 같은 목적을 다른 방식으로 표현하는 갈래도 있으니, 시야를 넓히는 차원에서 두 가지를 짚어 두겠습니다. 첫 번째 관점은 닫힌 계층입니다. 도형처럼 종류가 앞으로 계속 늘어나는 경우에는 오늘처럼 추상 타입에 의존하는 다형성이 유리합니다. 새 클래스만 꽂으면 되니까요. 그런데 반대로 종류가 딱 정해져 있고 더 늘어날 일이 없는 경우도 있습니다. 예를 들어 신호등 색은 빨강, 노랑, 초록 세 가지로 고정입니다. 이럴 때는 sealed 클래스로 허용되는 하위 타입을 봉인하고, switch 패턴 매칭으로 처리하는 방식이 깔끔합니다. sealed로 하위 타입을 못 박아 두면, switch에서 어떤 종류를 빠뜨렸을 때 컴파일러가 그 누락을 잡아 줍니다. 두 번째 관점은 동작 전달입니다. 계산 로직 자체를 람다나 함수로 넘기는 함수형 표현입니다. from-gof-to-lambda라는 저장소를 보시면, 전략이나 템플릿 같은 패턴을 클래스 대신 람다로 간결하게 표현한 예제들이 정리되어 있습니다. 여기서 꼭 기억하실 것은, 이 모든 표현이 결국 오늘 배운 같은 뿌리 위에 있다는 사실입니다. 구체적인 것이 아니라 추상, 즉 계약에 의존한다는 원리 말입니다. 버스와 지하철이 같은 목적지로 가듯, 확장이 잦으면 다형성, 종류가 고정이면 sealed와 switch를 고르면 됩니다. 목적지인 "변경에 강한 설계"는 같습니다. 이 과정에서는 고전 구현을 중심에 두되, 이렇게 현대적 표현을 병기해 여러분이 상황에 맞게 오갈 수 있도록 안내하겠습니다.

## Slide 25. 평가하기 1: 사지선다형

**Screen**
- 제목: 평가하기
- 문제: 다음 코드에 삼각형(Triangle)을 추가해야 할 때, 개방-폐쇄 원칙(OCP)을 지키는 방법으로 가장 적절한 것은?

```java
Shape[] shapes = { new Rectangle(4, 5), new Circle(3) };
for (Shape shape : shapes) {
    System.out.println("넓이 : " + shape.넓이());
}
```

- 보기:
  1. for문 안에 `if (shape instanceof Triangle)` 분기를 추가해 삼각형만 따로 계산한다.
  2. `Triangle extends Shape` 클래스를 새로 만들어 `넓이()`를 재정의하고, 배열에 객체만 추가한다. 순회 코드는 고치지 않는다.
  3. `넓이()`를 호출하는 for문을 삼각형 전용 로직으로 통째로 교체한다.
  4. Shape를 abstract가 아닌 일반 클래스로 바꿔 삼각형 계산을 Shape 안에 직접 넣는다.

**Easy analogy**
- 콘센트에 새 가전을 쓰려고 집 안 배선을 다시 까는 사람은 없다. 규격에 맞는 플러그를 만들어 빈 구멍에 꽂는다 — 2번이 그 방식이다.

**Practical case**
- 실무사례형 시나리오: 새 유형을 instanceof 분기로 처리하기 시작하면, 그 분기가 곧 문자열 if-else와 똑같은 OCP 위반의 씨앗이 된다. 추상 타입에 재정의를 맡기는 2번만이 순회 코드를 수정에 닫힌 채로 유지한다.

**Visual asset**
- 화면은 문제 중심. 우측에 작은 아이콘: 새 클래스 블록 → 배열에 꽂힘 → 순회부 자물쇠.

**Source**
- Robert C. Martin, "The Open Closed Principle" (Clean Coder Blog, 2014): 새 동작을 추상 타입의 새 구현으로 추가한다는 폴리모픽 OCP. http://blog.cleancoder.com/uncle-bob/2014/05/12/TheOpenClosedPrinciple.html
- 실습 정답 소스(패턴 적용 final): `code/design-pattern-end/src/ex02/App.java`

**Narration**
- 첫 번째 평가는 오늘의 핵심인 개방-폐쇄 원칙을 코드로 적용하는 문제입니다. 정답은 2번입니다. Triangle 클래스를 새로 만들어 Shape를 상속받고 넓이를 재정의한 뒤, 배열에 객체만 추가하면 됩니다. 순회하는 for문은 Shape라는 추상 타입에만 의존하고 있으므로 한 줄도 고칠 필요가 없습니다. 이것이 확장에는 열리고 수정에는 닫힌, 개방-폐쇄 원칙의 정확한 모습입니다. 나머지를 보겠습니다. 1번은 for문 안에 instanceof 분기를 넣자는 것인데, 이것은 문자열 if-else와 똑같은 조건 분기의 부활입니다. 유형이 늘 때마다 그 분기를 또 고쳐야 하므로 오히려 위반입니다. 3번은 순회 코드 자체를 통째로 교체하자는 것이니, 수정에 닫혀 있어야 할 코드를 정면으로 뜯어고치는 것입니다. 4번은 Shape를 일반 클래스로 바꿔 계산을 한곳에 몰아넣자는 것인데, 이것은 각 도형이 자기 계산을 책임지던 구조를 다시 한 메서드로 뭉치는, 재설계 이전으로의 후퇴입니다. 새 유형을 추가할 때 기존 코드를 고치지 않아도 되는 선택지는 오직 2번뿐입니다.

**Practice**
- 없음.

**Assessment**
- 유형: 사지선다형
- 정답: 2
- 난이도: 보통
- 해설: 추상 타입 Shape에 의존하는 순회 코드는 그대로 두고, 새 구현 클래스(Triangle)를 추가하는 것이 폴리모픽 OCP의 확장 방식이다.

## Slide 26. 평가하기 2: 진위형

**Screen**
- 제목: 평가하기
- 문제: 캡슐화는 필드를 private으로 은닉하고, 객체의 상태를 public 메서드라는 정해진 통로(행위)를 통해서만 바꾸도록 통제하는 설계 규율이다. O/X

**Easy analogy**
- 은행 금고의 현금을 고객이 직접 만질 수 없고 입출금 창구 절차로만 잔액이 바뀌는 것과 같다. 앨리스의 키도 버섯을 먹는 행위로만 바뀐다.

**Practical case**
- 실무사례형 시나리오: 오늘 재설계한 Circle의 radius는 private이었고, 그 상태는 넓이() 행위로만 드러났다. 필드를 public으로 열어 두었다면 여러 곳에서 값이 제각기 바뀌어 상태를 추적할 수 없었을 것이다.

**Visual asset**
- 간단한 캡슐화 이미지: private 필드를 감싼 캡슐과 그 표면의 단 하나의 메서드 통로.

**Source**
- Oracle Java Tutorials – Controlling Access to Members of a Class: 필드는 private으로 두고 메서드로 접근하도록 권장한다는 설명. https://docs.oracle.com/javase/tutorial/java/javaOO/accesscontrol.html

**Narration**

## Slide 27. 평가하기 3: 진위형

**Screen**
- 제목: 평가하기
- 문제: 개방-폐쇄 원칙(OCP)에서 "닫혀 있다"는 것은 새로운 기능을 절대 추가하지 못하도록 코드를 잠근다는 뜻이다. O/X

**Easy analogy**
- 멀티탭은 이미 꽂힌 냉장고 배선은 건드리지 않지만(수정에 닫힘), 빈 구멍에 새 가전은 얼마든지 꽂을 수 있다(확장에 열림). "닫힘"은 확장 금지가 아니다.

**Practical case**
- 실무사례형 시나리오: OCP를 "코드를 잠가 못 늘리게 하는 것"으로 오해하면, 오히려 확장을 두려워하는 경직된 설계로 흐른다. 닫혀 있어야 하는 대상은 기존 코드의 "수정"이지 기능의 "추가"가 아니다.

**Visual asset**
- 확장(열림)과 수정(닫힘)을 두 화살표로 구분한 미니 다이어그램.

**Source**
- 개방-폐쇄 원칙(Meyer·Martin): 확장에는 열려 있고 수정에는 닫혀 있어야 한다는 원칙의 정의. https://en.wikipedia.org/wiki/Open%E2%80%93closed_principle

**Narration**
- 세 번째 문제의 정답은 X입니다. 개방-폐쇄 원칙에서 열림과 닫힘은 서로 다른 대상을 가리킵니다. 열려 있어야 하는 것은 확장, 즉 새로운 기능을 더하는 일입니다. 닫혀 있어야 하는 것은 수정, 즉 이미 잘 돌아가는 기존 코드를 뜯어고치는 일입니다. 그러니까 이 문제처럼 "새 기능을 절대 추가하지 못하게 잠근다"는 것은 정반대의 오해입니다. 오히려 개방-폐쇄 원칙은 새 기능을 아주 쉽게 추가할 수 있게 하되, 그 추가가 기존 코드를 건드리지 않도록 만드는 설계입니다. 오늘 도형 예제가 정확히 그랬습니다. 삼각형이라는 새 기능은 클래스 추가로 얼마든지 늘릴 수 있었고, 그 대신 계산기 코드는 손대지 않았습니다. 멀티탭을 떠올리시면 됩니다. 이미 꽂힌 냉장고 배선은 건드리지 않지만, 빈 구멍에 새 가전은 얼마든지 꽂습니다. 닫힘은 확장 금지가 아니라 기존 코드 보호라는 것을 기억해 주세요.

**Practice**
- 없음.

**Assessment**
- 유형: 진위형
- 정답: X
- 난이도: 보통
- 해설: OCP에서 닫혀 있어야 하는 대상은 기존 코드의 수정이며, 확장(새 기능 추가)에는 오히려 열려 있어야 한다.
- 관련학습보기: Slide 9, Slide 14
