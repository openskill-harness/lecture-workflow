# reader-panel — 설계 문서

출판 업계의 "베타 리더"를 AI로 자동화한 스킬(구 book-workflow `beta-reader`를 이 하네스 구조에 맞게 개명·재작성).
한 명이 아니라 **10명이 동시에** 읽고 각자 관점에서 피드백한다.

## 왜 만들었나

- 저자 혼자 읽으면 자기 글의 문제를 못 본다
- 한 명이 리뷰하면 그 사람의 배경에 편향된다
- 10명의 다양한 배경이 동시에 읽으면 **특정 수준에만 맞춰진 차시**가 바로 드러난다

## 성격 — 비차단 온디맨드 옵션

`manuscript-verify`와 같은 성격이다.

- 파이프라인 단계가 아니다 — `course-pipeline`이 호출하지 않는다.
- status.md에 열/칸을 만들지 않는다.
- 하드 게이트가 아니다 — 어떤 단계도 이 스킬의 실행을 전제하지 않는다.
- 원고·책을 자동 수정하지 않는다 — 근거부 리포트만 낸다. 반영은 사용자가 `manuscript-final`(원고) 또는 `book-build`(책)로 직접 판단해 수행한다.

리포트 경로의 `12_독자패널`은 파이프라인 12단계라는 뜻이 아니라 **리포트 네임스페이스**다. `11_검증`은 이미 `manuscript-verify`가 쓰고 있어 충돌을 피하려고 다음 번호를 썼을 뿐, 두 스킬 모두 파이프라인 단계 번호 체계 밖에 있다.

## 설계 흐름

```
0. 실행 기준 확인
   사용자가 지정한 기준(원고/책)을 확인. 지정 없으면 되묻는다.
   - 원고 기준: outputs/02_원고/chNN.md (전제: 원고확정 ✅)
   - 책 기준: outputs/10_책/chNN.pdf (전제: 책 ✅)

1. 컨텍스트 로드
   outputs/01_과정개요서.md(대상자·선수지식·과정목표) + 대상 원고/책 + 실습 코드(있으면) + 이전 리포트(있으면)

2. 페르소나 자동 생성
   과정개요서의 대상자·기술스택 읽기 → 10명 페르소나 생성(고정 목록 아님, 과정마다 새로 생성)

3. 10명 병렬 디스패치
   Agent 도구로 10명 동시 실행 → 각자 독립 평가

4. 평가 (체크리스트 4개 영역)
   이야기 / 기술 / 실습 / 전체

5. 종합 리포트 생성
   outputs/12_독자패널/chNN_reader.md에 저장
```

## 페르소나 분배 규칙

10명을 아래 비율로 생성한다. 과정개요서의 대상자·기술스택에 맞게 구체적인 배경을 채운다.

| 유형 | 인원 | 왜 이 비율인가 |
|------|------|--------------|
| 주제와 가까운 배경 | 2명 | 기술적 정확성 검증 |
| 주제와 먼 배경 | 2명 | 설명이 충분한지 검증 |
| 비개발 배경 | 2명 | 용어 장벽, 접근성 검증(PM/기획자, 비전공 전직자) |
| 숙련자 | 2명 | 아키텍처/확장성/실무 관점(리드, 시니어) |
| 초보 | 1명 | 최소 수준에서 따라갈 수 있는지(부트캠프 수료) |
| 학생 | 1명 | 이론↔실무 연결 검증 |

각 페르소나 필드: 이름(역할) · 배경 · 코드 수준 · 관점(막히는 포인트).

## 평가 체크리스트

### 이야기 파트 — 글의 품질

| 항목 | 보는 것 |
|------|--------|
| 몰입 | 빠져드는가, 지루한 구간은 |
| 비유 | 내 배경에서 와닿는가, 억지스러운 비유는 |
| 톤 | AI스러운 문장("이것이야말로", "기억하십니까?") |
| 용어 도입 | 갑자기 나오지 않는가, 비유→정의 순서 |
| 등장인물 | 대사가 자연스러운가 |

### 기술 파트 — 학습 효과

| 항목 | 보는 것 |
|------|--------|
| 용어 연결 | 이야기 비유 → 기술 정의 연결 |
| 코드 설명 | 내 수준에서 이해 가능한가 |
| 데이터 시각화 | 추상 설명에 실제 데이터(JSON/출력/다이어그램)가 있는가 |
| 파일 트리 | [실습]/[설명]/[참고] 분류가 명확한가 |

### 실습 — 실제로 따라할 수 있는가(코드 있는 차시만)

| 항목 | 보는 것 |
|------|--------|
| 환경 구축 | 막히는 지점 |
| 실행 결과 | 원고/책 설명과 실제 결과 일치 |
| TODO | 힌트가 충분한가 |
| 에러 대응 | 에러 시 해결법이 본문에 있는가 |

### 전체 — 차시의 흐름

| 항목 | 보는 것 |
|------|--------|
| 학습 곡선 | 이전 차시 대비 난이도 점프 |
| 분량 | 길다/적당하다/짧다 |
| 다음 예고 | 흥미 유발 여부 |

## 리포트 구조

```
페르소나 목록표
  ↓
요약 (N/10 통과)
  ↓
공통 피드백 (3명 이상 동일 의견 = 진짜 문제)
  ↓
심각도별 이슈 (높음/중간/낮음)
  ↓
페르소나별 상세 (각자 [이야기]/[기술]/[실습]/[총평]/[점수])
  ↓
수정 제안 (우선순위순, 위치 포함, 관련 페르소나)
```

### 핵심: "3명 이상 동일 의견" 규칙

1명만 지적한 건 그 페르소나의 특수 사정일 수 있다.
**3명 이상**이 같은 걸 지적하면 원고/책 자체의 문제다.
이걸 "공통 피드백"으로 올려서 저자가 먼저 보게 한다.

## 범용성

| 항목 | 설계 |
|------|------|
| 과정 경로 | `courses/{course-id}/` 아래 자동 감지, 하드코딩 없음 |
| 페르소나 | 과정개요서 대상자에 맞게 매번 새로 생성 |
| 코드 없는 차시 | 실습 평가 건너뛰고 이야기+기술만 |
| 이전 리포트 | 있으면 "지적 사항이 개선되었는가" 확인 |
| 실행 기준 | 원고/책 두 기준을 분리 유지(조기 리딩과 최종 리딩의 목적이 다름) |

## 사용

```
독자 패널 (원고 기준) chNN
독자 패널 (책 기준) chNN
```

리포트 저장 위치: `outputs/12_독자패널/chNN_reader.md`
