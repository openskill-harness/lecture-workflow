# L02 프롬프터 나레이션 — Controller와 Service의 책임 경계

---

[SLIDE 01]

Spring Boot로 CRUD API 한 번 만들어 보셨다면,
이런 컨트롤러 써 보셨을 겁니다.
메서드 하나 안에서 파라미터 꺼내고,
값이 이상한지 확인하고,
업무 규칙까지 판단하고,
저장소를 부르고,
응답까지 조립하죠.

잘 돌아갑니다. 테스트도 통과하고요.
그런데 시간이 지날수록,
꼭 그 메서드에만 자꾸 손이 갑니다.

이렇게 컨트롤러 하나가 모든 일을 떠안은 모양,
현장에선 흔히 "뚱뚱한 컨트롤러"라고 부릅니다.
공식 용어는 아니고, 그냥 통칭이에요.
오늘 목표는 이 이름을 외우는 게 아닙니다.
무엇이 컨트롤러의 일이고 무엇이 아닌지,
그 경계를 스스로 판단하는 겁니다.

[SLIDE 02]

경계를 식당 하나로 비유해 볼게요.
손님을 응대하는 홀 서버, 그러니까 웨이터가 있고,
안쪽에서 요리하는 주방, 셰프가 있습니다.
뚱뚱한 컨트롤러는,
홀 서버가 주문도 받고 요리까지 직접 하겠다는 식당이에요.
한 테이블일 땐 됩니다.
문제는 그 다음입니다.

[SLIDE 03]

경계가 없으면 세 가지가 무너집니다.

첫째, 규칙이 복사됩니다.
같은 가입 규칙, 같은 재고 차감 규칙을
다른 컨트롤러나 배치, 스케줄러에서 또 써야 할 때,
규칙이 컨트롤러에 박혀 있으면 복붙돼서 흩어집니다.
마틴 파울러는 이런 공통 업무 로직을 한곳에 모으는 자리를
"서비스 계층"이라고 불렀습니다.

둘째, 변경이 서로를 넘어뜨립니다.
HTTP 코드하고 업무 규칙이 한 메서드에 섞이면,
응답 포맷 바꾸려다 규칙을 건드리고,
규칙 손보다 엔드포인트를 깨뜨립니다.
로버트 마틴의 단일 책임 원칙 그대로예요.
"한 모듈은 바뀌어야 할 이유가 오직 하나여야 한다."

셋째, 검증하려면 웹을 통째로 띄워야 합니다.
로직이 컨트롤러 안에 있으면,
그거 하나 확인하려고 HTTP 계층 전체를 세워야 해요.
서비스의 평범한 객체에 있으면 웹 없이 확인할 수 있고요.
빠르고 느리고의 문제가 아니라,
검증에 무엇까지 딸려 오느냐의 문제입니다.

식당으로 치면,
홀 서버가 요리까지 하는 식당은
그가 자리를 비우면 요리 자체가 멈춥니다.
파울러 식으로 말하면,
애플리케이션의 경계가 웹 프레임워크에 묶여버린 거죠.

[SLIDE 04]

여기서 오해 하나 끊고 가겠습니다.
나누는 기준은 "컨트롤러가 길어서"가 아닙니다.
기준은, 무엇이 어떤 이유로 바뀌는가예요.

HTTP 표현이 바뀌는 이유는,
경로나 상태코드, 응답 포맷이고, 이건 API 스펙에서 옵니다.
업무 규칙이 바뀌는 이유는,
정책이나 계산, 트랜잭션 범위고, 이건 기획에서 오죠.
출처가 다른 두 변경을 한 모듈에 두면,
한쪽이 다른 쪽을 인질로 잡습니다.
마틴은 이 원칙을 "결국 사람에 관한 것"이라고 했어요.
서로 다른 이해관계자의 변경이 서로를 깨지 않게 격리하라는 뜻입니다.

단, "서비스로 옮기면 끝"은 아닙니다.
모든 로직을 서비스에 몰고
도메인을 게터·세터 껍데기로 두면,
"빈혈 도메인 모델"이라는 또 다른 안티패턴이 됩니다.
그 얘기는 뒤 강의에서 더 다루고요,
오늘은 "서비스는 로직 던져 넣는 만능 창고가 아니다",
이 정도만 붙잡고 가겠습니다.

[SLIDE 05]

이제 두 계층의 책임을 표 하나로 정리해 보죠.

컨트롤러, 홀 서버는 HTTP 경계의 어댑터입니다.
매핑하고, 바인딩하고, 형식 검증을 트리거하고,
예외를 상태코드로 바꾸고, 응답을 조립하죠.
표 왼쪽 열이 전부 여기입니다.
Spring 레퍼런스도 컨트롤러를
"HTTP 요청과 비즈니스 로직 사이의 다리"라고 설명합니다.

검증은 한 겹만 짚을게요.
`@Valid` 같은 형식·제약 검증은 컨트롤러 경계에서 트리거됩니다.
참고로, Spring 6.1부터는 내장 메서드 검증을 쓰려면
클래스 레벨 `@Validated`를 빼야 하는 등
버전마다 동작이 갈리니 공식 문서를 확인하세요.
중요한 건, 여기서의 검증은 "형식이 맞는가"이지
"업무적으로 되는가"가 아니라는 점입니다.

서비스, 주방은 유스케이스이자 트랜잭션 경계입니다.
파울러의 정의로 서비스 계층은
"업무 로직을 캡슐화하고, 트랜잭션을 제어하며, 응답을 조율"합니다.

한 요청이 이 둘을 지나는 지점만 짚겠습니다.
컨트롤러가 요청을 받아 입력 DTO로 바꿔서
서비스의 유스케이스 메서드에 넘기고,
서비스가 결과를 돌려주면
컨트롤러가 그걸 응답 표현으로 바꿉니다.
딱 이 배턴 주고받는 한 지점이 오늘의 무대예요.
DispatcherServlet이 여기까지 어떻게 오는지는
L01에서 봤으니 반복하지 않겠습니다.

[SLIDE 06]

오늘 한 장만 남긴다면 이 슬라이드입니다.

주방 티켓을 떠올려 보세요.
스테이크하고 사이드가 한 티켓이면,
둘 다 나가거나 둘 다 안 나갑니다.
반쪽짜리 서빙은 없죠.
하나의 업무 단위가 전부 아니면 전무로 처리되는 것,
이게 트랜잭션이고,
그 단위를 정의하는 자리가 서비스의 유스케이스 메서드입니다.

Spring 팀도 명시적으로 권장합니다.
"`@Transactional`은 인터페이스가 아니라
구체 클래스의 메서드에 붙여라."
실무에서 그 구체 클래스가 서비스죠.
그래서 트랜잭션 경계가 곧 유스케이스 경계고,
그게 곧 서비스입니다.

[비유 이탈 — 직설]
여기서 비유 하나는 일부러 버리겠습니다.
주방을 "재료 창고"나 "데이터베이스"로 생각하면 안 됩니다.
주방은 조리하는 곳,
즉 업무를 조율하는 유스케이스예요.
재료를 넣고 꺼내는 저장창고는 별개 계층, Repository고,
그 뒤에 DB가 있습니다.

[SLIDE 07]
[화면: 계층 흐름 — Controller → Service → Repository → DB]

서비스가 저장소를 호출하긴 해도,
서비스가 곧 저장소는 아닙니다.
이 층이 흐려지면 다음 오분류가 시작됩니다.

[SLIDE 08]

경계를 헷갈리는 세 지점, 자주 틀리는 것들이에요.

첫째, 트랜잭션을 웹 계층에 둡니다.
`@Transactional`을 컨트롤러에 붙이거나,
컨트롤러에서 저장소를 여러 번 이어 호출해서
업무 단위 경계를 웹에 만드는 거죠.
권장은 서비스 구체 클래스 메서드입니다.

둘째, 주문서와 식재료를 같은 걸로 씁니다.
DTO하고 Entity를 혼용하는 거예요.
요청·응답용 DTO와 도메인·영속 Entity를 구분 없이 쓰죠.
파울러의 정의로 DTO는
"프로세스 경계를 넘어 데이터를 나르는 객체"라
목적 자체가 다릅니다.
주문서엔 "스테이크 미디엄"이라고 적지,
소가 통째로 적히진 않잖아요.
엔티티를 그대로 노출하면
직렬화나 바인딩 관심사가 도메인으로 새거나,
필드가 과하게 드러날 수도 있습니다.
경계에서 데이터 모양을 바꾸는 변환,
그게 컨트롤러의 일입니다.

셋째, 업무 규칙 검증을 형식 검증과 같은 층으로 봅니다.
`@NotBlank`나 `@Min` 같은 형식 검증은 컨트롤러 경계지만,
"이미 가입된 이메일인가", "잔액이 부족한가",
이런 업무 규칙 검증은 서비스입니다.
홀 서버는 "메뉴에 있는 주문인지"는 확인해도,
"재료가 남았는지"는 주방이 알죠.

[SLIDE 09]

그럼 무조건 서비스를 만들어야 할까요?
아닙니다.
서비스가 저장소를 1대1로 넘기기만 하는,
규칙 없는 순수 통과형 CRUD에서는
로직 없는 서비스가 상용구만 늘린다는
실무 논쟁이 있습니다.
정답이 정해진 규칙이 아니라 판단의 문제라,
"서비스를 없애라"가 아니라
이렇게 물어야 합니다.
"이 계층은 무엇을 위해 있는가?"

그래서 오늘의 결론은,
외울 규칙이 아니라 두 개의 질문입니다.

[SLIDE 10]

첫째, "이 변경은 어떤 이유로 오는가?"
HTTP 표현이면 컨트롤러,
업무 규칙이면 서비스입니다. 단일 책임 원칙이죠.

둘째, "이 로직을 다른 진입점에서도 재사용해야 하는가?"
경계가 필요하면 서비스입니다. 서비스 계층이죠.

이 둘에 답할 수 있으면,
새 코드를 어디에 둘지 스스로 판단할 수 있습니다.
그게 오늘의 목표였습니다.

[IDE 예고 — L03]
다음 레슨에선 회원 가입 API를 만들면서,
일부러 규칙을 컨트롤러에 뭉쳐 뚱뚱하게 만들었다가
서비스로 분리하는 과정을 코드로 봅니다.
오늘 말로 그린 경계가,
화면에서 코드가 자리를 옮기는 걸로 다시 확인될 겁니다.

[SLIDE 11]
