# Educational Simulator Builder (교육용 인터랙티브 시뮬레이터)

어려운 개념을 **"직접 만져보며 배우는"** 단일 HTML 시뮬레이터로 만든다. 이 분야의 이름은
*explorable explanations*(Bret Victor, Nicky Case)이고, 핵심은 "글로 설명"이 아니라
"플레이로 발견"하게 만드는 것이다.

이 스킬은 통합 강의 제작 파이프라인(`docs/superpowers/specs/2026-07-05-unified-lecture-pipeline-design.md`
§3 표, §8)의 **9단계**다. 파이프라인 안에서 호출되면 확정 원고를 입력으로 받는 **원고 연동**
모드로 동작하고, 파이프라인 밖에서 단독 호출되면 기존처럼 사용자 요청만으로 동작한다.

결과물은 **항상 의존성 없는 단일 `.html` 파일** (외부는 폰트 CDN만 허용). **라이트 테마가 기본값**
이다(§3 "라이트 테마" 참고). 한국어, 초보자 대상, 내용은 전문적.

## 산출물

- **파이프라인 호출**: `courses/{course-id}/simulators/chNN_{주제}.html` (주제는 다룬 슬라이드
  내용을 담은 한글/영문 슬러그, 예: `ch03_어텐션.html`).
- **단독 호출**(파이프라인 밖): 작업 폴더에 내용을 담은 파일명으로 저장, 경로 규약 없음(기존과
  동일).

## 0. 입력 계약 (파이프라인 연동)

호출 맥락을 먼저 구분한다.

- **파이프라인 호출** (대상 과정/차시가 이미 지정된 상태로 불렸을 때):
  1. 대상 과정 `courses/{course-id}/status.md`를 읽는다. 해당 차시 `원고확정`이 ✅가 아니면
     사용자에게 알리고 중단한다(시뮬레이터는 확정 원고 없이 만들지 않는다). **하드 게이트**: `시각자산`이
     ✅도 `deferred`도 아니면(⬜/🔄/`partial`/`stale`) 중단하고 먼저 `visual-assets`(4단계)를 완료(또는
     명시적 보류)하도록 안내한다.
  2. `manuscripts/chNN.md`를 읽어 `## Slide N. 제목` 블록 전체 목록을 사용자에게 제시하고
     **"어떤 슬라이드를 시뮬레이터로 만들까요?"** 라고 묻는다. `storyboards/chNN.html`이 있으면
     화면 미리보기 참고 링크로 함께 안내한다(§1 참고). 여러 슬라이드를 골라 하나의 시뮬레이터로
     묶어도 된다 — 단, §2-3(범위 확정)에서 반드시 경계를 좁힌다.
  3. 사용자가 고른 `## Slide N.` 블록에서 다음을 읽어 시뮬레이터 설계에 그대로 반영한다:
     - **Easy analogy** → 이 시뮬레이터의 **중심 은유**로 채택한다. 원고와 다른 비유를 새로
       창작하지 않는다(원고 화면과 시뮬레이터가 다른 비유를 쓰면 학습자가 같은 개념을 두 번
       다르게 배우는 꼴이 된다). 단, `references/pedagogy.md`의 "비유에 갇히지 마라" 원칙에
       따라 이 비유가 핵심을 왜곡하는 지점이 발견되면 그 지점만 보강하거나 직설적 그림으로
       바꾸되, 반드시 원고 담당자(사용자)에게 왜 바꿨는지 한 줄로 알린다.
     - **Narration** → 단계별 설명 문안의 근거로 삼는다. 강사가 어떤 순서로 개념을 풀어가는지,
       어떤 표현으로 강조하는지를 시뮬레이터의 단계 설명 패널(§4의 ⑤) 문구에 반영한다.
     - **Visual asset**(있으면) → 참고 도식/이미지 구도로 삼는다(그대로 베끼지 않고 구조만
       추출 — `references/pedagogy.md`의 "표준 도식" 원칙과 동일).
  4. 이후 절차(교육 설계 → 내용 검증 → 빌드 → 검증 → 전달)는 §2의 순서를 그대로 따르되, 시나리오
     한 문단(`pedagogy.md` "시나리오 한 문단")을 원고의 Easy analogy를 기점으로 작성한다.
  5. 완료 후 `status.md`의 해당 차시 `시뮬` 칸을 갱신한다: 사용자가 확인하면 ✅ + "산출물 인덱스"에
     `- chNN 시뮬레이터: simulators/chNN_{주제}.html (확정 YYYY-MM-DD)` 추가. 사용자가 지금 만들지
     않고 미루기로 하면 ➖ + `## 보류/누락`에 사유·날짜 기록(예: "사용자가 3차시 이후로 보류").
- **단독 호출** (파이프라인 밖, 사용자가 바로 개념 설명을 요청): 기존 방식 그대로 — `references/requesting.md`
  체크리스트로 부족한 정보(한 줄 질문/비유/상호작용)만 1~2개 질문하고 진행한다. `status.md` 갱신은
  하지 않는다(대상 과정이 없으므로).

## 1. 대상 선정 흐름 (파이프라인 호출 시)

- 슬라이드 목록은 번호+제목으로 짧게 나열한다(예: "3. 어텐션이 왜 필요한가", "4. 내적과 유사도").
  원고 전문을 다시 보여줄 필요는 없다 — 제목만으로 사용자가 고를 수 있으면 충분하다.
- `storyboards/chNN.html`이 이미 있으면 "스토리보드 N번 카드가 이 슬라이드예요"처럼 대조해 안내하면
  사용자가 더 빠르게 고른다(필수는 아님).
- 사용자가 슬라이드 여러 개를 걸쳐 하나의 개념을 고르면(예: "4~6번을 한 시뮬레이터로") 허용하되,
  §2-3에서 다룰 범위를 명확히 좁힌다.
- 사용자가 "지금은 만들지 말자"고 하면 §0의 보류 처리로 넘어간다.

## 2. 전체 흐름 (이 순서를 지킬 것)

1. **요청 해석 + 부족하면 1~2개만 질문.** 파이프라인 호출이면 §0에서 이미 비유/나레이션을
   확보했으므로 대개 추가 질문이 필요 없다. 단독 호출이면 `references/requesting.md`의 체크리스트로
   빠진 정보를 채운다. 참고 스케치/스크린샷이 있으면 그대로 따른다(이미지는 말 100줄보다 정확하다).
2. **교육 설계를 먼저 한다 (코드 X).** `references/pedagogy.md`를 읽고, 어떤 질문으로 시작해
   어떤 단계로 올라가 어떤 반전으로 끝낼지 *시나리오*를 한 문단으로 잡는다. 이야기 → 문제 →
   해결(여러 개면 하나씩)의 형태여야 한다. **하나의 구체적 예시(스레드)를 끝까지 끌고 간다**
   (`pedagogy.md`의 "예시 연속성"). 파이프라인 호출이면 이 스레드는 원고의 Easy analogy에서
   출발한다(§0-3).
2-1. **내용(개념)이 사실인지 먼저 검증한다 (코드 X).** 시나리오에서 *단정하는 문장*을 모두 뽑아
   한 줄씩 "이게 사실인가?"를 따진다. 흔한 오개념(folk model)을 그대로 그리지 않는다. 확신이
   안 서면 권위 있는 출처(1차 문서·논문)로 확인한다. `references/verification.md` E절을 따른다.
   — **개념이 틀리면 그리지 않는다.**
2-2. **표준 도식이 있는 주제면 웹에서 1~2개 조사한다 (해당될 때만).** 어텐션·트랜스포머·역전파·
   RAG처럼 *널리 쓰이는 표준 그림*이 있는 주제는, 코드 전에 그 도식을 찾아 **구조(입력→연산→
   출력, 흐름 방향)** 를 맞춘 뒤 비유로 옷을 입힌다. 그림을 베끼는 게 아니라 **불변 구조만 추출**
   한다. 표준과 어긋나면 학습자가 다른 자료와 충돌한다.
2-3. **다룰 범위·층위를 먼저 못 박는다.** 한 시뮬에 섞으면 안 되는 경계를 빌드 전에 정한다. (예:
   *추론(forward)* vs *학습(역전파)* — 둘을 한 화면에 섞으면 오개념.) 무엇을 넣고 무엇을 뺄지 정하고,
   필요하면 사용자에게 한 줄로 확인한다.
2-4. **과정 전체를 열거한다.** 파이프라인/알고리즘이면 그리기 전 체크: ① 입구 변환에 **역변환**이
   있는가(예: 임베딩↔언임베딩)? ② 전체가 **반복(루프)** 되는가(예: 자기회귀)? ③ **한계/엣지**에
   닿으면? — 빠뜨리기 쉬운 '되돌아오는·반복되는' 단계를 미리 잡는다.
3. **수학/좌표를 먼저 검증한다.** 시각화(특히 SVG 벡터·정사영·그래프류)는 **숫자가 틀리면
   무의미**하다. 화면을 그리기 전에 `references/verification.md`의 방식으로 좌표를 계산하고
   viewBox 안에 들어오는지, 의도한 승자/값이 나오는지 node로 확인한다.
4. **빌드한다.** §3(라이트 테마)의 팔레트와 `references/build-recipe.md`(구조·애니메이션 패턴)를
   따른다. §4(표준 구성 요소)를 빠짐없이 내장한다. `assets/template.html`은 구조·상호작용 패턴
   참고용으로 쓸 수 있으나 **색 토큰은 §3의 라이트 팔레트로 교체**한다(다크가 기본이던 시절 자산 —
   사용자가 다크를 명시적으로 요청한 경우에만 그대로 쓴다).
5. **다시 검증한다.** node `--check` 문법 검사 + 좌표/수학 재확인 + (가능하면) jsdom으로 버튼
   클릭 런타임 오류 0건 확인 + **내용(개념) 재확인**(화면의 단정 문장이 여전히 사실인가, 비유의
   성립 조건을 어기지 않았는가 — verification.md E절). `references/verification.md` 참고.
   기술 검증을 통과해도 개념이 틀리면 미완성이다. 통과 전엔 전달하지 않는다. §5(확정 체크리스트)로
   최종 확인한다.
6. **전달 + 확인.** 사용자가 브라우저에서 새로고침해 확인하게 하고, 더 다듬을 곳을 묻는다.
   사용자가 확정하면 §0-5(파이프라인 호출 시 status.md 갱신)를 수행한다.

## 3. 라이트 테마 (기본값)

골든 팔레트(`templates/golden/*`가 쓰는 톤)와 통일한다. **다크는 사용자가 명시적으로 요청할 때만**
`references/design-system.md`의 다크 네이비 토큰을 그대로 쓴다 — 그 외에는 아래 라이트 토큰이
기본이다.

```css
:root{
  --ink:#17202a; --muted:#5d6875; --line:#d9dee7; --soft:#f5f7fa;
  --bg:#ffffff; --surface:#ffffff; --surface-2:#f5f7fa;
  --blue:#2f6fcb; --blue-deep:#1f4f9c;
  --green:#5aa05a; --green-deep:#3f7a3f;
  --amber:#c98a1a; --rose:#c0435a;
  --mono:'JetBrains Mono',monospace;
}
```

- 배경은 흰색(`--bg`), 카드/표면은 흰색 또는 아주 옅은 회색(`--soft`) — 다크 시절의 `rgba(255,255,255,0.04)`
  같은 반투명 오버레이 대신 **실선 보더**(`1px solid var(--line)`)로 카드를 구분한다.
- 의미 색 관례는 유지하되 라이트 톤으로 대응한다: **blue**=중립/기본 요소·벡터(구 indigo),
  **green**=좋음·성공·정답(구 emerald), **rose**=나쁨·충돌·오답, **amber**=질문/강조 —
  단, amber는 흰 배경에서 저채도(`#c98a1a`)로 써야 가독성이 유지된다(원색 노랑 금지).
- 폰트: Pretendard(본문) + JetBrains Mono(숫자/코드) — `references/design-system.md`의 CDN
  링크를 그대로 쓴다. 폰트 CDN은 라이트/다크 공통.
- 레이아웃(넓은 폭 `.wrap{max-width:1500px}`, 좌 무대 + 우 사이드카드 2단, 모바일 1단)은 다크
  시절과 동일하게 유지한다 — 바뀌는 건 색뿐, 구조는 그대로다.
- 카드/버튼/뱃지 등 컴포넌트의 **모양**(border-radius, 여백, 그림자 없는 flat 스타일)은
  `references/design-system.md`를 그대로 따르되 색만 위 라이트 토큰으로 교체한다.

## 4. 표준 구성 요소 (필수 내장)

파이프라인 호출·단독 호출 모두 아래 5개를 반드시 내장한다. 하나라도 빠지면 미완성이다.

1. **단계별 시나리오 진행** — "이전 / 다음" 버튼 + 진행 표시(예: 점 인디케이터 `● ● ○ ○` 또는
   "2/4" 텍스트). 상태는 `step` 변수 하나로 관리하고, 이전/다음은 그 값을 ±1 한 뒤 화면을
   `render(step)` 한 번으로 갱신한다(개별 DOM을 흩어서 건드리지 않는다 — 동기화 실수를 줄인다).
2. **비유 뷰 ↔ 실제 개념 뷰 토글** — 같은 `step`을 두 가지 표현(비유 삽화/문구 vs 실제 개념
   용어·수식·다이어그램)으로 렌더링한다. 토글은 `view` 상태(`'analogy'|'concept'`) 하나로 관리하고,
   `step`은 토글해도 **그대로 유지**한다(토글 후 다른 단계로 튀면 안 된다 — §5 체크리스트).
3. **애니메이션 속도 조절** — 슬라이더 또는 배속 버튼(예: 0.5x/1x/2x)으로 트랜지션 지속시간·
   `setTimeout` 간격에 곱해지는 배율 변수(`speed`)를 하나 두고 모든 애니메이션 타이밍이 이 변수를
   참조하게 한다.
4. **리셋** — `step`/`view`/`speed`/진행 중이던 타이머(`clearTimeout`/`clearInterval`)를 전부
   초기값으로 되돌리고 `render()`를 다시 부른다. 리셋 후 화면이 최초 로드 상태와 시각적으로
   동일해야 한다(§5 체크리스트).
5. **각 단계 한 줄 설명 패널** — 무대 아래 또는 옆에 현재 `step`의 설명을 한 줄(또는 2~3줄 이내)로
   보여주는 고정 위치 패널(`references/design-system.md`의 `flow-msg` 패턴 재사용). 파이프라인
   호출이면 이 문구는 원고 Narration을 근거로 쓴다(§0-3).

구현 시 `references/build-recipe.md`의 "버튼 → 데이터 흐름 애니메이션", "고정 좌표계" 원칙과
결합한다 — 5개 구성 요소를 추가한다고 화면 전체를 다시 그리지 않는다.

## 5. 확정 체크리스트

전달 전에 아래를 모두 확인한다. 하나라도 실패하면 **repair 규칙**을 따른다.

- [ ] **버튼 전부 동작**: 이전/다음/토글/속도조절/리셋 버튼을 전부 클릭해(가능하면 jsdom, 아니면
  브라우저 육안) 콘솔 에러 0건을 확인했다.
- [ ] **리셋 시 상태 꼬임 없음**: 리셋 직후 `step`/`view`/`speed`가 초기값이고, 진행 중이던
  타이머가 모두 정리되어(잔여 애니메이션이 뒤늦게 실행되지 않음) 화면이 최초 로드와 동일하다.
- [ ] **토글 후 단계 동기화**: 비유 뷰 ↔ 개념 뷰를 전환해도 같은 `step` 번호를 가리키고, 진행
  표시(점/숫자)가 토글 전후로 어긋나지 않는다.
- [ ] **태블릿 폭 대응**: 뷰포트 768~1024px에서 레이아웃이 2단→1단 등으로 깨지지 않고 버튼이
  가려지지 않는다(미디어 쿼리로 확인).
- [ ] **외부 의존 0**: 폰트 CDN 1건(Pretendard/JetBrains Mono) 예외를 제외하면 스크립트·
  스타일시트·이미지 등 외부 리소스 참조가 없다.
- [ ] **(내용) 개념 검증**: `references/verification.md` E·F절 — 단정 문장이 사실이고, 애니메이션이
  실제 연산/메커니즘을 반영한다(느낌만 흉내내지 않는다).
- [ ] **(파이프라인 호출 시) 비유 일치**: 화면의 중심 비유가 원고 `## Slide N.`의 **Easy analogy**와
  같다(임의로 새 비유를 만들지 않았다).

## repair 규칙

체크리스트 중 하나라도 실패하면 전체를 다시 만들지 않는다.

- **버튼/상태 결함**(리셋 꼬임, 토글 후 단계 어긋남, 콘솔 에러)은 §4에서 지정한 상태 변수
  (`step`/`view`/`speed`) 관리 방식으로 되돌려 그 버튼의 핸들러만 고친다. 다른 패널·단계는
  건드리지 않는다.
- **레이아웃 결함**(태블릿 폭 깨짐)은 해당 미디어 쿼리 구간만 조정한다.
- **외부 의존 위반**(폰트 CDN 외 리소스 유입)은 그 리소스만 인라인화하거나 제거한다.
- **개념/비유 결함**(단정 문장 오류, 원고 Easy analogy와 불일치, 메커니즘이 느낌만 흉내)은 해당
  단계(`step`) 하나만 시나리오부터 다시 잡아 재생성한다. 다른 단계는 유지한다. 원고와 다른 비유를
  썼다면 §0-3의 예외 조건(왜곡 지점 보강)에 해당하는지 먼저 확인하고, 아니라면 원고의 Easy
  analogy로 되돌린다.
- **좌표/수학 결함**(viewBox 밖 이탈, 값 불일치)은 `references/verification.md` A절 방식으로
  좌표를 재계산해 그 SVG 요소만 고친다.
- 큰 파일 쓰기/읽기 관련 이상은 `references/verification.md` C절(샌드박스 마운트 주의, 34KB
  쓰기 잘림 등)을 따른다.
