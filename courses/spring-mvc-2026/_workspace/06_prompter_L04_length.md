### 총량 판정
- 밴드 상한 3,600 대비: **+964자 (+26.8%)** — 허용 ±10%를 크게 초과.
- 밴드 중앙 3,300 대비: +1,264자 (+38.3%).
- 낭독 실소요: 15.2~16.6분 = 12분 대비 **+27~38% 초과**. 어떤 밴드 내 발화속도로도 12분에 담기지 않음.

### 코드 워크스루 특수성 분리 산정 (task 3 지시)
- **순수 슬라이드 구간 = 0자.** L04는 전 구간 `[IDE 화면: …]` — 슬라이드가 하나도 없다. 따라서 "슬라이드만 보며 듣는 발화"로 밴드에 맞는 하위 구간을 분리해 낼 여지가 없다(전량이 코드-가시 발화).
- 이는 특례 판단에 양날: 화면이 정보를 분담한다는 논거가 성립하는 동시에, **특례를 통째로 인정하면 이 레슨은 길이 게이트에서 전면 면제**되어 게이트가 무의미해진다.

## 4. 권고안

**압축 필요 + 제한적 특례(전면 면제 아님).**

1. **C1~C6 중복 압축 적용(~580자)** → ~3,980자. (승인 시 해당 구간만 재변환)
2. **코드 워크스루 특례를 "발화속도·무음 비트" 한정으로 인정:**
   밴드 상단 300자/분으로 낭독 + 아래 2개 구간을 의도적 근-무음 화면 비트(합 ~0.6~0.8분)로 운용
   - step-03→04 "코드 블록이 파일을 건너 이사" 리빌 (화면이 설명)
   - step-05 실행 로그(alice/alice/bob 201·409·201) — validation_log 실측, 화면이 증명
   이로써 12분 내 실효 수용량이 ~3,600~3,800자로 상향.
3. 결과: **~3,980 → 목표 ~3,600~3,800**. 잔여 초과 필요 시 C 후보 추가 축약(사용자 승인).

**특례를 "전면 인정(4,564 유지)"으로 권고하지 않는 이유:**
- 물리적으로 4,564자는 어떤 발화속도로도 15분+ (12분 불가). 화면-가시 시간은 낭독시간에 **가산**되지 감산되지 않음.
- 슬라이드 0 구간 = 특례 전면 인정 시 게이트 완전 무력화.
- 따라서 특례는 "속도 상단 + 2개 무음 비트"까지만 정당하며, 그래도 **약 ~600자 압축은 불가피.**
