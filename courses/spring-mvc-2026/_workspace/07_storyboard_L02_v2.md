# L02 슬라이드 스토리보드 (v2) — Controller와 Service의 책임 경계

> **승계 개정판.** 구 L03 G4 승인본(`_workspace/07_storyboard_L03.md`, S01~S11)의 슬라이드 구성·핵심 메시지·단어 수·각주를 **그대로 승계**한다. 이 개정의 목적은 두 가지뿐이다 — (1) v1.7 레슨 재편에 따른 **레슨 참조 갱신**(레슨번호 L03→L02, 다음 레슨 예고 L04→L03, 회상 참조 L02→L01), (2) 원고 `scripts/L02.md`에 소급된 **시드 블록(d2 ×2 / [IMG] ×1 / [비유] ×1)의 소비 명세 추가**. 도형 구도 자체는 변경하지 않는다(시드가 승인본 구도와 일치하도록 소급되었다).

## 설계 개요

- **총 11장.** 프롬프터 `L02_prompter.md`가 `[SLIDE 01]~[SLIDE 11]` **11마커를 이미 보유**하며 S01~S11과 **1:1 대응**한다. (구 승인본 시점에는 프롬프터가 10마커여서 "SLIDE 06을 S06/S07로 분할"하는 조정을 제안했는데, 그 분할이 프롬프터 v2에 이미 실현되었다. 따라서 이번 개정에서는 **추가 remap 없음**.)
- **1장 = 1메시지** 원칙 준수. 원고 7개 섹션 + 인트로/마무리 → 11장. 원고 `[비유 이탈 — 직설]` 지점(§4)에서 (a) "트랜잭션 경계 = 유스케이스 = Service" 강조와 (b) 계층도(Controller→Service→Repository→DB)라는 **서로 다른 두 메시지**를 S06/S07 두 장으로 나눈 것이 유일한 장 분할이며, 이는 원고 문장은 그대로 두고 슬라이드 경계만 나눈 것이다.
- **중심 비유 등장 궤적:** 식당 비유(홀 서버↔주방)는 S02에서 도입 → S05 책임표의 열 라벨("홀 서버"/"주방")로 유지 → S06 티켓(all-or-nothing)까지 이어감 → **S07에서 의도적으로 버림**([비유 이탈 — 직설]). S08에서 오분류 설명 시 비유를 보조로만 재사용(주문서/식재료, 홀 서버는 메뉴 확인·주방은 재고). 원고에 없는 지점에 비유를 미리 심지 않는다.
- **[비유 이탈 — 직설] = S07:** 이 장만은 식당 그림을 쓰지 않는다. 주방을 "저장창고/DB"로 오해하는 것을 끊기 위해 **Controller→Service→Repository→DB 4단 계층도**로 직설한다. 조립 시 식당 아이콘 사용 금지.
- **코드 슬라이드 없음 / SIM cue 없음.** 실행 코드 0장. 어노테이션(`@Valid`·`@Transactional`·`@NotBlank`·`@Min`)과 계층 흐름 화살표는 **실코드가 아니라 개념 칩·계층 라벨**로만 등장. L03(코드 워크스루)와 역할 분리. code_font_min_pt(22pt)는 이 개념 칩에도 동일 적용.
- **오분류(S08)는 코드 조각이 아니라 "증상 목록".** `@Transactional`을 컨트롤러에 붙임, DTO/Entity 혼용, 업무규칙 검증을 형식 검증과 동층 취급 — 세 가지를 **증상(무엇을 잘못했나) 카드**로 표기. 실제 리팩터링 코드는 L03.
- **원고 시드 우선 소비(v1.6).** 아키텍처/관계 도형은 원고의 `d2`·`[IMG]`·`[비유]` 시드에서 소비한다. 이 레슨의 아키텍처 도형 2장(S05 책임 대조 / S07 계층 흐름)은 원고 §3·§4의 `d2` 시드를, S01 앵커 일러스트는 §0 `[IMG]` 시드를, S02 비유 도해는 §0 `[비유]` 시드를 각각 소비한다. **시드 없이 새로 창작해야 하는 아키텍처 도형은 0건**(→ 원고 개정 신호 없음). 상세는 하단 "원고 시드 소비 매핑" 참조.
- **단어 수 규칙:** 본문(제목+글머리+다이어그램/표 라벨) 어절 기준 카운트. `A·B·C`처럼 가운뎃점으로 이은 복합 토큰은 렌더 시 공백 없는 1토큰이므로 1어절로 계산. 하단 각주(출처)는 신뢰성 표기로 본문 카운트에서 제외하되 1행으로 짧게 유지. 시드 소비 명세는 조립 지시(메타)이며 렌더 텍스트가 아니므로 단어 수에 불포함.
- **비주얼 연속성:** S02(식당 2구역: 홀/주방) → S05(같은 2구역을 표의 두 열로) → S06(주방 안 "티켓" 클로즈업) → S07(주방 뒤에 Repository·DB 계층을 새로 드러냄, 비유→계층 전환). 하나의 "주방"이 형태를 유지하며 마지막에 계층도로 해체되도록 조립 지시.

## SLIDE 01 — 문제 제기: 뚱뚱한 컨트롤러 (시작 고정)

- **프롬프터 대응:** `[SLIDE 01]`
- **핵심 메시지(한 줄):** 한 메서드가 파라미터부터 응답까지 다 하는 컨트롤러 — 잘 돌지만 자꾸 손이 간다. 오늘은 그 경계를 스스로 판단한다.
- **구성 요소 명세:**
  - 제목: `동작은 하는데, 자꾸 손이 가는 컨트롤러`
  - **앵커 일러스트(원고 §0 [IMG] 시드 소비 — 활용 = YES):** 과부하 웨이터 일러스트(양손 가득 접시 + 프라이팬 + 입에 문 주문 패드, 배경에 밀린 테이블·쌓인 티켓)를 S01의 **1차 히어로 비주얼**로 쓴다. "뚱뚱한 컨트롤러 = 홀도 주방도 혼자 떠안은 웨이터"를 한 장면으로 각인시키는 시드다.
  - **책임 스택 오버레이(승인본 구도 유지):** 히어로 일러스트 위/옆에 5개 작업을 촘촘한 스택 라벨로 겹쳐 표기 — `파라미터 추출` · `형식 검증` · `업무 규칙 판단` · `저장소 호출` · `응답 조립`. (승인본의 "터질 듯 꽉 찬 박스"를 **추상 박스를 새로 그리지 않고 [IMG] 시드 위 주석 스택으로** 표현 — 시드 소비. 메시지·단어수·각주 동일.)
  - 콜아웃 배지: `"뚱뚱한 컨트롤러"(통칭 · 비공식)` 라벨.
  - 하단 목표 라벨: `오늘: 무엇이 컨트롤러의 일인가 — 경계를 스스로 판단`
  - 강조: 과부하를 warning 컬러로. "경계"를 accent.
  - 조립 지시: [IMG] 시드는 다크 테마 일러스트(원고 명시)로 덱 라이트/다크 정책상 **manifest visual_style=다크 테마와 일치** — 별도 팔레트 변환 없이 그대로 앵커로 배치. 5-작업 스택은 22pt 이상.
- **단어 수 추정:** 약 15어절 (제목 4 + 스택 라벨 5 + 배지 2 + 목표 라벨 4). **PASS (≤45)**
- **각주:** 없음 (통칭 서술 S1-4는 "비공식 통칭"임을 슬라이드 배지로 자체 명시, 외부 인용 아님)

## SLIDE 02 — 중심 비유: 홀 서버 ↔ 주방

- **프롬프터 대응:** `[SLIDE 02]`
- **핵심 메시지(한 줄):** 식당의 홀 서버와 주방으로 경계를 비유한다 — 뚱뚱한 컨트롤러는 홀 서버가 요리까지 하겠다는 식당이다.
- **구성 요소 명세:**
  - 제목: `식당으로 보는 경계 — 홀 서버 ↔ 주방`
  - **다이어그램(앵커 이미지, 원고 §0 [비유] 시드 소비):** 좌측 **홀(서빙 공간)** 아이콘 + 라벨 `홀 서버(웨이터) = Controller`, 우측 **주방** 아이콘 + 라벨 `주방(셰프) = Service`. 둘 사이 경계선. (시드 사상: 홀=HTTP 경계 응대·전달 / 주방=업무 로직 조리. `DTO=주문서·Entity=식재료·트랜잭션=한 티켓 all-or-nothing`은 이 시드의 대응표로, S05·S06·S08에서 순차 사용 — 이 장에선 홀/주방 2구역만 심는다.)
  - 대비 삽화: 경계선을 지운 "홀 서버가 요리까지" 상태를 작게 표시하고 `한 테이블이면 OK` 캡션.
  - 강조: 두 구역을 나누는 경계선을 accent. 이 2구역 레이아웃을 S05 표의 두 열로 이어받도록 조립 지시.
- **단어 수 추정:** 약 12어절 (제목 5 + 좌/우 라벨 4 + 캡션 3). **PASS**
- **각주:** 없음 (비유 도입, 인용 없음)

## SLIDE 03 — 깨지는 지점: 경계가 없으면 무너지는 3가지

- **프롬프터 대응:** `[SLIDE 03]`
- **핵심 메시지(한 줄):** 경계가 없으면 규칙이 복사되고, 변경이 서로를 넘어뜨리고, 검증하려면 웹을 통째로 띄워야 한다.
- **구성 요소 명세:**
  - 제목: `경계가 없을 때 깨지는 3가지`
  - 다이어그램: **3열 카드** (개념 도해 — 아키텍처 시드 대상 아님, 조립 창작)
    - ① `규칙이 복사된다` — 같은 규칙이 컨트롤러·배치·스케줄러로 복붙되어 흩어지는 아이콘(중복 문서 3장).
    - ② `변경이 서로를 넘어뜨린다` — HTTP 코드와 업무 규칙이 한 메서드에 얽혀 도미노처럼 쓰러지는 아이콘.
    - ③ `검증하려면 웹을 통째로 띄운다` — 로직 하나 확인에 HTTP 계층 전체가 딸려오는 아이콘.
  - 비유 앵커(하단 1줄): `홀 서버가 요리까지 하면 — 자리 비우면 요리가 멈춘다` (경계가 웹 프레임워크에 묶임).
  - 강조: 세 카드 제목만 강조, 부연은 작게.
- **단어 수 추정:** 약 18어절 (제목 4 + 카드 3제목 9 + 하단 비유 5). **PASS**
- **각주:** `① Fowler, PoEAA — "Service Layer"(공통 업무 로직을 모아 진입점 간 중복 제거) · ② R.C. Martin, "SRP"(2014, 한 모듈은 바뀔 이유가 하나) · ③ Fowler, "Service Layer"(경계가 웹 프레임워크에 묶임)` — citation_required(external_case_studies). S1-1/S1-2/S1-3/S2-1 근거.

## SLIDE 04 — 분리 기준: 줄 수가 아니라 변경 이유

- **프롬프터 대응:** `[SLIDE 04]`
- **핵심 메시지(한 줄):** 나누는 기준은 "길이"가 아니라 "무엇이 어떤 이유로 바뀌는가"다 — 단, 서비스는 로직 던져 넣는 만능 창고가 아니다.
- **구성 요소 명세:**
  - 제목: `기준 — 줄 수 ❌ / 변경 이유 ⭕`
  - 다이어그램: **두 갈래 화살표**가 한 모듈로 들어오는 그림 (개념 도해 — 조립 창작)
    - `HTTP 표현이 바뀌는 이유 → 경로·상태코드·응답 포맷 (출처: API 스펙)`
    - `업무 규칙이 바뀌는 이유 → 정책·계산·트랜잭션 범위 (출처: 기획)`
    - 두 화살표가 한 박스에 꽂히며 `한쪽이 다른 쪽을 인질로 잡는다` 경고.
  - 하단 주의 배지: `⚠ 서비스 = 로직 만능 창고 아님 (→ 빈혈 도메인 모델, 다음 강의)`
  - 강조: ❌/⭕ 대비, "변경 이유"를 accent. 빈혈 도메인 모델 배지는 회색(오늘 주제 아님 신호).
- **단어 수 추정:** 약 20어절 (제목 5 + 두 갈래 라벨 10 + 주의 배지 5). **PASS**
- **각주:** `R.C. Martin, "SRP"(2014, "결국 사람에 관한 것" — 이해관계자별 변경 격리) · Fowler, "AnemicDomainModel"(로직을 모두 서비스로 몰면 빈혈 도메인)` — citation_required. S3-1/S3-2 근거.

## SLIDE 05 — 핵심 구조: 두 계층 책임 대조표 (표 슬라이드)

- **프롬프터 대응:** `[SLIDE 05]`
- **핵심 메시지(한 줄):** Controller는 HTTP 경계의 어댑터, Service는 유스케이스이자 트랜잭션 경계 — 한 표로 대조한다.
- **원고 시드 소비(§3 `d2` — 책임 대조 구도):** 이 장의 2계층 대조 구조와 배턴 화살표는 원고 §3의 `d2` 시드에서 소비한다. **구도는 구 승인본(표 슬라이드) 유지** — 시드가 승인본 2열 대조와 일치하도록 소급되었다. 시드→슬라이드 사상:
  - 시드 `controller { r1 요청 매핑 · r2 입력 바인딩→DTO 변환 · r3 형식 검증 트리거(@Valid) · r4 예외→상태코드/응답 조립 }` → 표 "하는 일" 컨트롤러 셀(`매핑·바인딩·형식검증·예외→상태코드·응답조립`)의 도형적 근거.
  - 시드 `service { s1 업무 규칙 실행 · s2 도메인/저장소 조율 · s3 트랜잭션 제어(@Transactional) }` → 표 "하는 일" 서비스 셀(`업무규칙·도메인/저장소조율·트랜잭션제어`)의 도형적 근거.
  - 시드 화살표 `controller -> service "유스케이스 위임 (배턴)"` / `service -> controller "결과 반환"` → 하단 **배턴 표기**로 직접 소비.
  - (표의 나머지 3행 `한 문장`/`다루는 것`/`바뀌는 이유`는 §3 원고 **마크다운 표**에서 소비 — d2 시드 밖이나 원고 내 동일 섹션 소스. 원고 밖 창작 아님.)
- **구성 요소 명세:**
  - 제목: `두 계층의 책임 대조표`
  - **표(한 슬라이드 한 표, S02의 홀/주방 2열 레이아웃 계승 — 원고 §3 표 그대로):**

    | | Controller(홀 서버) | Service(주방) |
    |---|---|---|
    | 한 문장 | HTTP↔앱 어댑터 | 유스케이스+트랜잭션 경계 |
    | 하는 일 | 매핑·바인딩·형식검증·예외→상태코드·응답조립 | 업무규칙·도메인/저장소조율·트랜잭션제어 |
    | 다루는 것 | 요청 DTO(주문서) | 업무 로직 · 티켓=all-or-nothing |
    | 바뀌는 이유 | 경로·상태코드·응답포맷 | 정책·계산·트랜잭션범위 |

  - 개념 칩(≥22pt): 표 하단에 `@Valid = 형식 검증 트리거(컨트롤러 경계) — "형식이 맞는가"이지 "업무적으로 되는가"가 아님`. 배턴 표기(§3 d2 화살표 소비): `Controller → (입력 DTO) → Service.유스케이스() → (결과) → Controller 응답 표현`.
  - **회상 참조(구 레슨번호 L02 → L01):** DispatcherServlet이 이 배턴 지점까지 오는 요청 흐름은 **L01에서** 다뤘으므로 반복하지 않는다(S5-1). 이 회상은 **나레이션 전용** — 슬라이드에 요청 흐름 도해를 다시 렌더하지 않는다(중복 도해 금지 유지). *(구 승인본은 구 레슨번호로 "L02에서"였음 — v1.7 재편으로 회상 대상이 L01로 갱신됨. 슬라이드 렌더 텍스트 변화 없음, 각주/명세 참조만 갱신.)*
  - 강조: 왼쪽 열 전체 = 컨트롤러 책임임을 색으로 묶음. "트랜잭션 경계"만 미리 accent(다음 장 예고).
  - 조립 지시: 가운뎃점(·)으로 이은 셀은 공백 없는 단일 토큰으로 렌더(단어 수·가독성 양립). 표 셀 폰트도 22pt 이상.
- **단어 수 추정:** 약 22어절 (제목 3 + 헤더 2 + 행라벨 4 + 8셀 토큰 9 + 배턴/칩 라벨 4). **PASS** (가운뎃점 복합 토큰 규칙 적용)

## SLIDE 06 — 트랜잭션 경계 = 유스케이스 = Service (오늘의 핵심 · 강조)

- **프롬프터 대응:** `[SLIDE 06]`
- **핵심 메시지(한 줄):** 하나의 업무 단위가 전부-아니면-전무로 처리되는 자리 = 트랜잭션 경계 = 유스케이스 경계 = Service.
- **원고 시드 연계(§4 `d2`의 `tx` 노드):** §4 `d2` 시드의 `tx: "트랜잭션 경계\nall-or-nothing"` 노드와 `service -> tx: "@Transactional 소유"` 관계의 **의미는 이 S06에서 소비**한다(트랜잭션 경계=유스케이스=Service 등식의 도형적 근거). 계층 스파인 자체는 S07에서 그림. → 1장1메시지 유지를 위해 S06=트랜잭션 등식/S07=계층 스파인으로 시드를 두 장에 나눠 소비.
- **구성 요소 명세:**
  - 제목: `트랜잭션 경계 = 유스케이스 경계 = Service`
  - 중심 배지: 세 등호로 이어진 **큰 등식** `트랜잭션 경계 = 유스케이스 = Service` (오늘 한 장만 남긴다면 이 장).

## SLIDE 07 — [비유 이탈 — 직설]: 계층도 Controller → Service → Repository → DB

- **프롬프터 대응:** `[SLIDE 07]` (프롬프터 `[화면: 계층 흐름 — Controller → Service → Repository → DB]` 지시 지점과 일치)
- **핵심 메시지(한 줄):** 여기서 비유를 버린다 — 주방(조리=유스케이스)은 저장창고가 아니다. 재료를 넣고 꺼내는 곳은 별개 계층 Repository이고 그 뒤에 DB가 있다.
- **원고 시드 소비(§4 `d2` — 계층 흐름):** 이 장의 계층도는 원고 §4의 `d2` 시드에서 소비한다. **구도는 구 승인본(순수 4단 계층도) 유지** — 시드가 승인본 `Controller→Service→Repository→DB` 스파인과 일치하도록 소급되었다. 시드→슬라이드 사상:
  - 시드 코어 스파인 `controller("Controller\n(HTTP 경계)") → service("Service\n(유스케이스·트랜잭션)") → repository("Repository\n(저장 접근)") → db("DB\n(저장소)")` → S07 4단 박스로 **직접 소비**(승인본 구도와 동일).
  - 시드 화살표 라벨 `controller -> service "입력 DTO 전달"` · `service -> repository "조율 (coordinates)"` · `repository -> db "영속성 접근"` · `service -> controller "결과 반환"` → 4단 박스 사이 화살표 라벨로 소비.
  - 시드 `client("HTTP 클라이언트") -> controller "요청"` / `controller -> client "응답 표현"` → **선택적** 진입/반환 노드. 승인본 S07은 Controller에서 시작했으므로, 조립 시 client 노드는 좌측 얇은 진입점으로만 표기(핵심 아님) 또는 생략 가능 — 핵심 4단 스파인 강조를 해치지 않는 선에서.
  - 시드 `tx` 노드/`@Transactional 소유` → **S06에서 이미 소비**(여기서 재강조 금지). 필요 시 Service 박스에 작은 accent 태그(`@Tx 경계`)로만 S06→S07 연속성 표시.
  - **[비유 이탈] 준수:** 식당 아이콘 사용 금지 — 순수 계층 박스만.
- **구성 요소 명세:**
  - 제목: `[직설] 주방은 저장창고가 아니다`
  - **다이어그램(식당 아이콘 금지 — 순수 계층도, §4 d2 시드 소비):** 좌→우 4단 박스와 화살표

    ```
    Controller  →  Service  →  Repository  →  DB
    (HTTP 경계) (유스케이스·트랜잭션) (저장 접근)  (저장소)
    ```

    (원고 §4의 평문 계층 블록 `Controller → Service → Repository → DB / (HTTP경계)(유스케이스·트랜잭션)(저장 접근)(저장소)`와 동일 — 평문 블록 + d2 라벨 화살표를 함께 소비.)
  - 오해 차단 콜아웃: `주방 ≠ 재료 창고/DB. 주방 = 조리(유스케이스). 서비스가 저장소를 호출해도, 서비스가 곧 저장소는 아님`.
  - 강조: `Service`와 `Repository` 사이 경계선을 accent(여기가 흐려지면 다음 오분류 시작). 계층 라벨(HTTP 경계/유스케이스·트랜잭션/저장 접근/저장소)은 22pt 이상.
  - 조립 지시: 이 장은 **비유 그림 없이 계층 박스만.** S06 주방에서 이 계층도로 "전환(비유 해체)"되는 트랜지션 느낌.
- **단어 수 추정:** 약 17어절 (제목 4 + 계층 4박스 4 + 계층 라벨 4 + 콜아웃 5). **PASS**
- **각주:** `Spring Framework Reference, Data Access "Using @Transactional"(구체 서비스 = 트랜잭션 경계, Repository는 별개 저장 접근 계층)` — S4-4 연장. citation_required.
