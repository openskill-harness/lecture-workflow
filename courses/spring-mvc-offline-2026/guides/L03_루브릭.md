## 평가 방식 (G3 결정)

**현장 강사 순회 확인이 1차 채점**이다. 제출물(신규 201 / 중복 409 실행 캡처 2건 + 완성 코드)은
채점 필수가 아니라 **수업 후 마감 업로드로 갈음**한다. 각 항목의 판정은 순회 시점에 학생 앱의 실행 결과와
코드를 직접 관찰한 것을 우선 근거로 한다. 제출물은 순회에서 확인하지 못한 학생의 2차 보완 확인용이다.

각 항목의 **관찰 지점(evidence)** = 강사가 순회 중 무엇을 눈으로 확인하면 되는지.

### 1. 요청→응답 기능 동작 (실행 결과) — 35%
> 연결: goal[2] 실행 관점. **관찰 지점**: 학생 앱을 실행해 신규 가입·동일 이메일 재요청의 응답 상태/본문 확인.

- **Excellent**: 신규 가입 요청이 201 Created와 `{id, email}` 응답 본문으로 응답하고, 동일 이메일 재요청이 409 Conflict로 응답한다(두 결과가 실행으로 재현된다).
- **Good**: 신규 가입 201은 정상 응답하나 중복 재요청이 409가 아닌 다른 상태(예: 500)로 응답한다.
- **Needs improvement**: POST /members가 매핑되지 않아 404가 나거나, 신규 가입 자체가 정상 응답하지 않는다.

### 2. 요청/응답 DTO 경계 — 20%
> 연결: goal[2] 구현(Step 2). **관찰 지점**: 컨트롤러 시그니처(`@RequestBody SignUpRequest` / `SignUpResponse` 반환)와 응답에 name 미노출 확인.

- **Excellent**: `@RequestBody`로 SignUpRequest를 받고 SignUpResponse로 응답하며, 도메인 Member를 입출력에 직접 노출하지 않는다(응답에 name이 없고, id를 클라이언트가 넣지 않는다).
- **Good**: DTO를 쓰나 도메인과 일부 혼용한다(예: 응답으로 Member를 그대로 반환하거나 응답에 불필요한 필드가 섞인다).
- **Needs improvement**: 요청/응답을 도메인 Member로 처리하거나, `@RequestBody` 누락으로 email/name이 null로 저장된다.

### 3. Controller/Service 책임 분리 — 25%
> 연결: goal[1] 책임 구분의 적용 회수(Step 4, L02 이론) + goal[2] 구현. **관찰 지점**: 컨트롤러가 Repository를 직접 참조하지 않는지, 로직이 복제 아닌 이동인지.

- **Excellent**: 가입 규칙(중복 검사·저장)이 MemberService에 있고, MemberController는 MemberRepository를 직접 참조하지 않으며 요청 수신·응답 변환만 한다(로직이 복제 없이 이동됐다).
- **Good**: MemberService를 만들었으나 Controller에 Repository 참조나 중복 검사 호출이 일부 남아 있다.
- **Needs improvement**: 가입 규칙이 Controller에 그대로 있거나(fat controller 상태), Service에 복제되어 양쪽에서 이중 검사한다.

### 4. 예외 처리·상태코드 매핑 (구현 방식) — 20%
> 연결: goal[2] 구현(Step 5). **관찰 지점**: DuplicateEmailException, `@ExceptionHandler`→CONFLICT, 성공 경로 `ResponseEntity` 201 코드 확인.

- **Excellent**: 중복 시 DuplicateEmailException을 던지고 `@ExceptionHandler`가 이를 409 Conflict로 매핑하며, 성공은 ResponseEntity로 201 Created를 반환한다.
- **Good**: 중복을 예외로 처리하나 예외 타입/핸들러가 어긋나 409가 아닌 500으로 나가거나, 성공 응답이 201이 아니라 200이다.
- **Needs improvement**: 중복 시 예외 처리가 없거나, 성공/중복의 상태코드(201/409) 구분이 되지 않는다.
