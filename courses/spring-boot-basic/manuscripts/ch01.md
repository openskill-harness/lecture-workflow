# 1차시 원고: 서버 프로그램과 웹 애플리케이션 실행 환경 이해

## 차시 정보

- 과정명: 스프링 부트 기초
- 회차명: 서버 프로그램과 웹 애플리케이션 실행 환경 이해
- 차시 목표: HTTP 요청-응답 흐름에서 서버 프로그램의 역할을 이해하고, 웹 서버와 WAS 및 Spring Boot 실행 환경의 차이를 구분한 뒤, Gradle 기반 `/hello` 실습으로 요청 처리 흐름을 확인한다.
- NCS 연계: 개발환경 구축하기(`2001020211_23v6-1.1`, `2001020211_23v6-1.2`), 서버 프로그램 구현하기(`2001020211_23v6-3.1`)
- 예상 분량: 30분 이상 초안. 사용자가 추후 축약 가능하도록 풍부하게 구성한다.

## Slide 2. 최신 이슈로 학습 열기: 전자정부 표준프레임워크도 Spring Boot 흐름을 강화하고 있다

- 핵심 정의: 전자정부 표준프레임워크는 공공 정보시스템 개발에서 공통 구조와 실행환경을 제공하는 표준 개발 프레임워크이며, Spring Boot 흐름과도 연결되고 있다.

**Easy analogy**
- 예전에는 관공서마다 주방 설비와 주문 방식을 따로 맞추는 식당이 많았다면, 표준프레임워크는 공통 주방 규격을 제공하는 역할을 한다. 최근 흐름은 이 공통 주방이 API, 클라우드, 관찰가능성까지 다룰 수 있도록 확장되는 모습에 가깝다. 그래서 첫 시간에 실행 환경을 이해하는 것이 중요하다.

**Practical case**
- 실무사례형 시나리오: 전자정부 표준프레임워크 기반 프로젝트에 투입된 개발자가 기존 JSP 화면 중심 프로젝트만 경험했다. 그런데 전자정부 표준프레임워크 5.0 공지를 보니 실행환경은 SpringBoot 3.5.6을 지원하고, 예제는 Spring AI 기반 RAG와 클라우드 운영환경까지 다룬다. 심플홈페이지 BackEnd 저장소도 BackEnd와 FrontEnd를 분리한 구조를 보여준다. 이 개발자는 “서버 프로그램이 화면을 직접 그리는 것”보다 “요청을 받아 API 응답을 돌려주는 실행 환경”을 먼저 이해해야 한다.

## Slide 3. 오늘의 학습 목표

**Screen**
- 관련 학습목표: 이번 차시 학습목표
- 제목: 오늘은 “요청이 들어와 응답이 나가기까지”를 본다
- 학습목표:
  1. HTTP 요청과 응답 흐름으로 서버 프로그램의 역할을 설명할 수 있다.
  2. 웹 서버, 웹 애플리케이션 서버(WAS), Spring Boot 실행 환경의 역할 차이를 구분할 수 있다.
  3. Gradle 기반 Spring Boot 프로젝트에서 `/hello` 요청 처리 흐름을 실행하고 확인할 수 있다.
- 학습내용:
  1. HTTP 요청과 응답으로 보는 서버 프로그램의 역할
  2. 웹 서버, WAS, Spring Boot 실행 환경 이해
  3. Gradle 기반 `/hello` 서버 실습과 요청 처리 확인
- 핵심 정의: 학습목표는 수업 후 수행할 수 있어야 하는 결과이고, 학습내용은 그 목표에 도달하기 위해 수업에서 다루는 레슨 단위이다.
- 화면: 왼쪽에는 학습목표 3개, 오른쪽에는 같은 순서의 학습내용 3개를 배치한다. 각 줄은 같은 아이콘 색으로 연결하여 목표와 레슨명이 일치한다는 점을 보여준다

**Easy analogy**
- 학습목표는 목적지이고 학습내용은 그 목적지까지 가는 길이다. 내비게이션에서 목적지를 정한 뒤 경유지를 따라가듯, 오늘은 요청과 응답, 실행 환경, 실습 확인이라는 경로를 따라간다. 목표와 학습내용이 같은 순서로 연결되어 있어야 강의 흐름도 흔들리지 않는다.

**Practical case**
- 교육용 시나리오: 실무에서 장애가 났을 때 “브라우저 문제인지, 웹 서버 문제인지, 애플리케이션 코드 문제인지”를 구분하지 못하면 원인 분석이 느려진다. 오늘 내용은 나중에 장애를 분리해서 보는 기초가 된다.

## Slide 5. HTTP는 브라우저와 서버가 주고받는 약속이다

**Screen**
- 학습목표: HTTP 요청과 응답 흐름으로 서버 프로그램의 역할을 설명할 수 있다.
- 제목: HTTP 요청과 응답
- 짧은 문구:
  - Request: 브라우저가 서버에 보내는 메시지
  - Response: 서버가 브라우저에 돌려주는 메시지
- 핵심 정의: HTTP는 웹에서 클라이언트와 서버가 요청과 응답 메시지를 주고받기 위해 사용하는 통신 규칙이다.
- 화면: 브라우저 -> GET /hello -> 서버 -> 200 OK + Hello 흐름

**Easy analogy**
- HTTP는 택배 운송장 양식과 같다. 보내는 사람, 받는 곳, 요청 내용이 정해진 칸에 적혀 있어야 물건이 제대로 이동한다. 주소가 틀리면 택배가 엉뚱한 곳으로 가듯, HTTP 경로나 메서드가 틀리면 서버도 원하는 코드를 찾지 못한다.

**Practical case**
- 실무사례형 시나리오: 개발자가 API가 안 된다고 말할 때, 실제로는 서버가 죽은 것이 아니라 요청 경로가 `/hello`가 아니라 `/helo`로 잘못 들어간 경우가 많다. HTTP 요청의 경로와 응답 상태 코드를 볼 줄 알면 이런 문제를 빨리 찾는다.

## Slide 6. HTTP 메시지는 사람이 읽을 수 있는 구조를 가진다

## Slide 8. WAS는 실행 중인 애플리케이션 로직을 처리한다

Tomcat 버전, 포트, 배포 경로, 서버 설정이 맞아야 합니다. 그래서 개발 환경이 조금만 달라도 “내 PC에서는 되는데 다른 PC에서는 안 된다”는 문제가 생기기 쉽습니다. Spring Boot는 이 출발 지점을 바꾸어, 먼저 애플리케이션을 실행하고 요청 흐름을 확인할 수 있게 만들어 줍니다. 과거 방식은 틀린 방식이 아니라 비교 기준입니다. 외부 Tomcat 배포를 이해하면 Spring Boot의 내장 서버가 왜 학습과 로컬 개발을 단순하게 만들어 주는지 더 분명해집니다.

## Slide 11. 자동 설정은 “상황을 보고 기본 준비를 해주는 도우미”다

**Screen**
- 학습목표: 웹 서버, 웹 애플리케이션 서버(WAS), Spring Boot 실행 환경의 역할 차이를 구분할 수 있다.
- 제목: Auto-configuration은 기본 설정을 자동으로 잡아준다
- 짧은 문구:
  - Web MVC starter 있음
  - Spring MVC/Tomcat 설정 추정

**Easy analogy**

Spring Boot는 일단 동작하는 기본값을 제공하고, 개발자가 필요할 때 그 기본값을 바꿀 수 있게 해줍니다. 자동 설정은 마법처럼 보이지만 실제로는 근거가 있습니다. 프로젝트에 어떤 스타터와 라이브러리가 들어 있는지, 어떤 설정값이 있는지, 어떤 환경에서 실행되는지를 보고 기본 구성을 결정합니다. 개발자는 처음에는 기본값을 이용해 빠르게 시작하고, 나중에 필요해지면 설정을 바꾸면 됩니다. 초급 과정에서는 이 기본값 덕분에 코드 흐름을 먼저 배울 수 있습니다. 자동 설정은 처음 보면 “내가 직접 설정하지 않았는데 왜 동작하지”라는 느낌을 줄 수 있습니다. 하지만 스타터와 클래스패스가 단서가 됩니다. Spring Boot는 이 단서를 보고 필요한 기본 준비를 수행합니다.
