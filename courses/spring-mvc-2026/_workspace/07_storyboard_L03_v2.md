# L03 슬라이드 스토리보드 — 기본 Controller 구현 (편2) · v2 (구 L04 승계 개정판)

> 촬영 흐름: **슬라이드는 각 IDE 화면 앞의 브리지 카드**로 짧게 들어가고, 카메라가 IDE로 컷 전환된다. 실행 결과 강조 카드(S8)와 마무리 지도(S9)만 IDE 뒤에 온다. 슬라이드가 코드를 낭독하지 않는다 — diff는 IDE가 보여준다.
>
> **IDE 디렉토리 경로 주의:** 모든 `[IDE 화면: {디렉토리}]` 마커의 실경로는 `code/L04/{디렉토리}/` 기준이다 (v1.7 재편에서 코드 디렉토리명 code/L04 는 Registry 승계로 유지 — 레슨 번호만 L03).

## S1 — 편2 오프닝 / 타이틀
- **핵심 메시지:** 말로 그린 책임 경계를, 오늘은 코드가 자리를 옮기는 것으로 확인한다.
- **구성 요소 명세:**
  - 상단 라벨: `편 2`
  - 제목: **기본 Controller 구현**
  - 부제: 요청 매핑부터 응답까지
  - 본문 1줄: "지난 시간(L02) 말로 그린 책임 경계를, 오늘 코드가 자리를 옮기는 것으로 확인한다"
  - 하단 비유 회수 바(**L02** 중심 비유): `웨이터 = Controller` · `주방 = Service`
  - 코드 없음. 다크 테마 타이틀 레이아웃.
- **시드 소비 명세([비유], L03.md 31행):** 이 회수 바가 원고 0절 `[비유: 뚱뚱한 컨트롤러 ↔ 홀 서버가 주방일까지 겸하는 식당]` 시드를 소비한다. **S1에서는 시드의 매핑부(웨이터=Controller / 주방=Service)만** 시각화한다 — 타이틀 슬라이드 밀도를 낮게 유지. 시드의 성립 조건("메서드 길이가 아니라 **변경 이유**로 나눌 때만 유효")은 여기서 풀지 않고, 규칙이 실제로 이동하는 S6(step-04 브리지)에서 회수·전개한다. 비유 자체가 L02의 중심 비유이므로 이 바가 곧 L02 회수 장치다.
- **단어 수:** ~26 (≤45 PASS)
- **대응 마커:** `[IDE 화면: 00-starter]` **앞** (레슨 시작 오프닝)

## S2 — 오늘 만드는 건 딱 둘
- **핵심 메시지:** 오늘 새로 만드는 건 Controller·Service 둘뿐, 나머지는 준비돼 있고 지금은 404다.
- **구성 요소 명세:**
  - 제목: 오늘 만드는 건 딱 둘
  - 강조 2항목: `MemberController` · `MemberService`
  - 대비 회색 그룹(준비됨): 도메인 · 저장소 · DTO · 빌드 = 이미 준비됨
  - 하단 강조 배지: `POST /members → 404` — "받을 문이 아직 없다"
  - 코드 없음(식별자 토큰만). 신규 2 vs 기존 4 대비 배치.
- **단어 수:** ~21 (≤45 PASS)
- **대응 마커:** `[IDE 화면: 00-starter]` **앞** (S1 직후, starter 프로젝트 보여주기 직전)

## S3 — 브리지 step-01: 요청이 도착할 문
- **핵심 메시지:** 먼저 요청이 도착할 진입점(문)부터 만든다 — 매핑은 로직이 아니라 선언이다.
- **구성 요소 명세:**
  - 캡션: `step-01 · 요청 매핑`
  - 메시지 1줄: "먼저, 요청이 도착할 문부터 만든다"
  - 핵심 변경 1줄 **코드(폰트 ≥22pt, monospace):** `@PostMapping("/members")`
  - 뜻 풀이 1줄: "이 경로·이 방식이 오면 → 이 자바 메서드 실행 (선언)"
  - change_reason(step-01) = "진입점이 필요하다"의 슬라이드화.
- **단어 수:** ~18 (≤45 PASS)
- **대응 마커:** `[IDE 화면: 01-request-mapping]` **앞** (브리지 후 IDE로 컷)

## S4 — 브리지 step-02: 데이터 왕복

- **구성 요소 명세:**
  - 캡션: `step-02 · 요청/응답 데이터 흐름`
  - 메시지 1줄: "문으로 데이터를 받고, 결과를 돌려준다"
  - 다이어그램(도형): `SignUpRequest` → [ Controller ] → `SignUpResponse` (입구·출구 화살표)
  - 하단 1줄: "입구·출구는 도메인이 아니라 요청·응답 전용 DTO"
  - 코드 대신 식별자 라벨만. 필요 시 `@RequestBody`를 입구 화살표에 배지로(≥22pt).
- **단어 수:** ~17 (≤45 PASS)

## S5 — 브리지 step-03: 뚱뚱한 컨트롤러(일부러)
- **핵심 메시지:** 중복 금지 규칙을 일단 컨트롤러 안에 넣는다 — 동작은 하지만 컨트롤러가 규칙까지 떠안는다.
- **구성 요소 명세:**
  - 캡션: `step-03 · 뚱뚱한 컨트롤러 (일부러)`
  - 메시지 1줄: "중복 금지 규칙을, 일단 컨트롤러 안에 넣는다"
  - 경고 톤 1줄(주의색): "동작은 한다 — 하지만 컨트롤러가 규칙까지 떠안았다"
  - 시각: Controller 박스가 '요청 처리 + 가입 규칙' 두 덩어리를 동시에 안고 있는 도형(과부하 강조).
  - 코드 없음(diff는 IDE). "일부러"를 색/아이콘으로 표시.
- **단어 수:** ~17 (≤45 PASS)
- **대응 마커:** `[IDE 화면: 03-fat-controller]` **앞**

## S6 — 브리지 step-04: 책임 이동 (오늘의 핵심 장면 · 웨이터→주방 회수)
- **핵심 메시지:** 검사·저장 블록이 컨트롤러에서 서비스로 이사한다 — 홀 서버는 주문만, 주방이 요리를. 새 로직이 아니라 자리만 옮긴 것이며, 나누는 기준은 변경 이유다.
- **구성 요소 명세:**
  - 캡션: `step-04 · 책임 분리 (오늘의 핵심 장면)`
  - 메시지 1줄: "규칙 블록이 컨트롤러 → 서비스로 이사한다"
  - **비유 회수 바(L02 central_metaphor):** `홀 서버(웨이터) = 주문만` · `주방(셰프) = 요리를` — step-03의 "웨이터가 주방일까지 하던" 상태를 여기서 해소. (S1에서 유보한 [비유] 시드의 성립 조건 "변경 이유로 나눈다"를 여기서 회수.)
  - 하단 1줄: "새 로직 아님 — 자리만 옮겼다. 변경 이유로 나눈다"
  - 코드는 diff(IDE) 담당. 슬라이드는 '이사' 도형 + 비유 회수에 집중. (선택: `memberService.signUp(request)` 위임 1줄을 홀쭉해진 Controller 쪽 라벨로, ≥22pt.)
- **시드 소비 명세 — 이 슬라이드가 원고 시드 2개를 소비한다:**
  - **핵심 다이어그램 = 원고 d2 시드(L03.md 146~165행, step-03→step-04 책임 이동 diff)를 그대로 조립한다.** 자유 창작 도형이 아니라 시드를 소스로 삼는다. 시드가 규정하는 구조:
    - 좌측 `step-03 MemberController (뚱뚱)` 노드 = 3개 서브블록: ⓐ 요청 수신 / DTO 변환, ⓑ 중복 검사 `existsByEmail`, ⓒ 저장 `save`.
    - 우측 `step-04 책임 분리` 노드 = 2박스: `MemberController`(요청 수신 / DTO 변환 / 위임 한 줄) + `MemberService`(중복 검사 + 저장 = 이사 온 블록), 둘 사이 화살표 `memberService.signUp(request)`.
    - 크로스 화살표 3개: ⓑ→Service "블록 이사", ⓒ→Service "블록 이사", ⓐ→Controller "그대로 남음". `direction: right`.
    - 조립 지시: 화살표 라벨 텍스트("블록 이사"/"그대로 남음")는 다크 토큰 대비로, 노드 내 식별자(`existsByEmail`·`save`·`signUp`)는 monospace ≥22pt.
  - **일러스트 = 원고 [IMG] 시드(L03.md 138행)를 소비한다.** 좌: 과로한 웨이터가 홀에서 주문서를 받으며 프라이팬으로 요리까지(라벨 "step-03 뚱뚱한 컨트롤러"), 우: 웨이터=홀·셰프=주방으로 분리(라벨 "step-04 책임 분리"), 가운데 큰 화살표 위 "검사·저장 블록 이사". 플랫 일러스트, **다크 테마**(원고 IMG 시드 명시와 일치 — 슬라이드 덱 다크 테마와도 정합). 비유 회수 바와 중복되지 않도록: IMG는 직관 장면, d2는 코드 구조 — 두 시각을 상하 또는 좌우로 배치하되 한 메시지("자리만 옮겼다")로 수렴.
  - **주의(조립):** IMG와 d2를 동시 탑재하면 밀도가 높다. 한 슬라이드 = 한 메시지 유지를 위해, IMG(직관)와 d2(구조)는 **동일 메시지의 두 층**으로만 쓰고 상단 IMG · 하단 d2 순으로 시선 유도. 텍스트 어절은 아래 단어 수 예산 내로 억제(도형 내부 식별자 라벨은 시드 원문이라 어절 카운트 예외 — S8 각주 규칙과 동일 처리).
- **단어 수:** ~26 (본문 어절 기준; 시드 도형 내부 식별자 라벨 제외 — L03.md 시드 원문 승계) (≤45 PASS)
- **대응 마커:** `[IDE 화면: 04-service-extracted]` **앞** (이 브리지가 03→04 전환의 의미를 세운 뒤 IDE에서 실제 블록 이동 diff를 보여줌)

## S7 — 브리지 step-05: 상태 코드로 결과를 말한다
- **핵심 메시지:** "응답까지"의 마지막 조각은 상태 코드 — 성공은 201, 중복은 409.
- **구성 요소 명세:**
  - 캡션: `step-05 · 응답까지`
  - 메시지 1줄: "결과를 HTTP 상태 코드로 말한다"
  - 대비 2배지: `성공 → 201 Created` · `중복 → 409 Conflict`
  - 하단 1줄: "@ExceptionHandler = 500으로 새기 전에 낚아채는 그물"
  - 코드 없음(개념 배지). 201=성공색/409=충돌색 대비.
- **단어 수:** ~19 (≤45 PASS)
- **대응 마커:** `[IDE 화면: final]` **앞**

## S8 — 실행 결과 강조 (validation log 실측만)
- **핵심 메시지:** 실제 기동 결과가 규칙을 증명한다 — 신규 201, 중복 409, 다른 이메일 201.
- **구성 요소 명세:**
  - 캡션: `실행 결과 · 실제 기동값`
  - 결과 3줄(로그 실측, 코드 아님):
    - `alice 가입 → 201 Created · {id:1, email:alice}`
    - `alice 재시도(중복) → 409 Conflict · "이미 가입된 이메일"`
    - `bob 가입 → 201 Created · id 2로 증가`
  - 하단 강조 전환 배지: `step-03의 500  →  409` (중복이 서버 에러에서 충돌로 정정됨)
  - **데이터 출처 고정:** `_workspace/05_labcode_L04_validation.log`(TEST1 201 id:1 / TEST2 409 / TEST3 201 id:2)만 사용. 임의 값 금지. (파일명은 Registry 승계로 L04 유지 — 값은 신 L03과 동일.)
- **단어 수:** ~29 (≤45 PASS)
- **대응 마커:** `[IDE 화면: final — 실행 로그/터미널]` **뒤** (라이브 터미널 시연 직후, 세 결과를 깨끗한 카드로 프리즈·강조)

## S9 — 마무리 요약: 전체 지도
- **핵심 메시지:** 매핑→DTO→분리→상태코드로 완성했고, 말로 그린 경계를 코드가 눈으로 확인시켰다.
- **구성 요소 명세:**
  - 제목: 요청 매핑에서 응답까지 — 전체 지도
  - 5스텝 요약 라인: `매핑(01) → DTO(02) → 규칙 뭉침(03) → 서비스 분리(04) → 상태 코드(05)`
  - 마무리 1줄: "말로 그린 경계를(L02), 코드가 눈으로 확인시켰다"
  - 코드 없음(흐름도 라벨만). 편2 클로징 레이아웃.
- **시드 소비 명세(d2 최종 구조, L03.md 270~286행):** 하단 흐름도를 원고 6절 `d2` 최종 구조 시드로 조립한다. 시드가 규정하는 노드·엣지:
  - 노드 4개: `HTTP 클라이언트` · `MemberController`(매핑 · DTO · 상태코드 201/409) · `MemberService`(가입 규칙 = 중복 검사) · `MemberRepository`(저장 = 메모리 맵). `direction: right`.
  - 엣지: client →`POST /members`→ ctrl →`signUp(request) 위임`→ svc →`existsByEmail / save 조율`→ repo, 되돌아오는 `Member` → `결과 반환` → `SignUpResponse(201) / 409 Conflict`.
  - (concept_model 관계 발췌: controller -delegates_use_case-> service, service -coordinates-> repository, service -returns_result-> controller — 시드 주석 그대로.)
  - **보강 라인(시드 하단 ASCII, L03.md 288~290행):** `POST /members → Controller(매핑·DTO·상태코드) → Service(가입 규칙) → Repository(저장)` 를 d2 도형 아래 한 줄 캡션으로 병기 가능(선택). d2 도형이 있으면 ASCII는 생략 가능 — 둘 중 하나로 밀도 조절.
  - 조립 지시: 노드 식별자 monospace ≥22pt, 엣지 라벨은 다크 토큰 대비. 4노드 가로 흐름이 한 줄에 들어오도록 축소.
