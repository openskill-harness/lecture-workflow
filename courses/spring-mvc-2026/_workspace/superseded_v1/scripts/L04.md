# L04 — 기본 Controller 구현: 요청 매핑부터 응답까지 (원고)

---

## 0. 오리엔테이션 — 여기서 만드는 건 두 개뿐이다  ⏱ 1.5분

[IDE 화면: 00-starter]

지난 시간(L03)에 홀 서버와 주방으로 컨트롤러와 서비스의 책임 경계를 말로 그렸습니다. 오늘은 그 경계가 화면에서 코드가 자리를 옮기는 것으로 다시 확인되는 시간입니다. 소재는 **회원 가입**입니다. "같은 이메일로는 두 번 가입 못 한다"는 진짜 업무 규칙이 하나 있어서, 이 규칙을 어디에 두느냐로 경계를 코드로 증명하기 좋습니다.

프로젝트를 열면 파일이 이미 몇 개 있습니다. 회원 도메인 `Member`, 저장소 `MemberRepository`, 요청·응답 DTO인 `SignUpRequest`와 `SignUpResponse`, 빌드 설정까지 — **전부 미리 준비해 둔 것**입니다. 오늘 초점은 요청 매핑부터 응답까지이지 영속성이 아니라서, 저장소는 DB 대신 메모리 맵으로 단순화해 뒀습니다.

딱 하나만 봐 두세요. 저장소에서 오늘 쓸 메서드는 두 개입니다. `save`는 id를 자동으로 채워 저장하고, `existsByEmail`은 같은 이메일이 이미 있는지 참·거짓으로 답합니다. 오늘 이 두 메서드의 **시그니처만 호출**합니다. 구현은 열어보지 않습니다.

지금 상태로 애플리케이션은 컴파일도 되고 뜨기도 합니다. 그런데 `POST /members`를 보내면 어떻게 될까요? 받을 컨트롤러가 없으니 **404**입니다. 요청이 도착할 문이 아직 없는 거죠. 그래서 오늘 우리가 만드는 것은 딱 둘 — `MemberController`와 `MemberService`뿐입니다. 나머지는 이미 준비돼 있습니다. 그럼 문부터 답니다.

## 1. step-01 — 요청 매핑: 요청이 도착할 문을 만든다  ⏱ 2.0분

[IDE 화면: 01-request-mapping]

**이전 상태.** 방금 봤듯이 컨트롤러가 없어서 `POST /members`는 404였습니다. 요청을 받을 진입점, 즉 핸들러가 존재하지 않는 상태죠.

**왜 바꾸나.** 무엇을 하기 전에, 클라이언트 요청이 도착할 진입점부터 있어야 합니다. 데이터를 받는 것도, 규칙을 판단하는 것도 전부 그 다음 일입니다.

**무엇이 바뀌나.** `MemberController` 파일 하나가 새로 생겼습니다. 핵심은 딱 두 줄입니다.

```java
@RestController
public class MemberController {

    @PostMapping("/members")
    public String signUp() {
        return "회원 가입 요청이 도착했습니다.";
    }
}
```

클래스 위의 `@RestController`, 그리고 메서드 위의 `@PostMapping("/members")` — 이 두 어노테이션이 오늘의 첫 조각입니다. `@PostMapping("/members")`가 하는 말을 그대로 풀면 이렇습니다. **"POST 방식으로 /members 경로에 요청이 오면, 이 자바 메서드를 실행하라."** 요청 매핑은 로직이 아니라 **선언**입니다. "이 요청은 이 메서드가 처리한다"는 이름표를 붙이는 일이죠.

여기서 L02가 연결됩니다. 지난 시간에 모든 요청이 `DispatcherServlet` 한 곳으로 모인다고 했죠. 그 `DispatcherServlet`이 요청을 받으면, 바로 이 `@PostMapping` 선언들을 훑어서 "누가 이 URL과 메서드를 맡겠다고 했나"를 찾아 핸들러로 넘깁니다. 우리가 방금 단 이름표가, L02에서 본 그 탐색의 대상입니다.

**결과.** 이제 `POST /members`를 보내면 404가 아니라, 이 메서드가 실행되고 고정 문자열이 **200**으로 돌아옵니다. 아직 요청 본문은 거들떠보지도 않고, 무조건 같은 문장만 답합니다. 그래도 상관없습니다. 지금 확인하려는 건 딱 하나 — **요청이 이 메서드까지 도달하는가**, 문이 열렸는가입니다.

**정리(lecture_message).** 요청 매핑은 "이 URL·이 메서드가 오면 이 자바 메서드를 실행하라"는 선언입니다. L02에서 본 `DispatcherServlet`이 이 선언을 보고 핸들러를 찾습니다. 문은 열렸으니, 이제 문으로 들어온 데이터를 받아 봅니다.

## 2. step-02 — 요청/응답 데이터 흐름: 입구와 출구의 모양  ⏱ 2.5분

[IDE 화면: 02-request-response-dto]

**이전 상태.** 방금 컨트롤러는 요청 본문을 무시하고 고정 문자열만 뱉었습니다. 문은 열렸지만, 들어온 물건을 아직 안 받는 상태죠.

**왜 바꾸나.** 실제 가입은 요청으로 들어온 데이터를 받아서, 처리한 결과 데이터를 돌려줘야 합니다. 늘 같은 문장만 답하는 문은 아직 아무 일도 안 하는 겁니다.

**무엇이 바뀌나.** 같은 `signUp` 메서드인데 입구와 출구가 둘 다 바뀌었습니다. 변경점만 봅니다.

```java
@PostMapping("/members")
public SignUpResponse signUp(@RequestBody SignUpRequest request) {
    Member member = memberRepository.save(new Member(null, request.email(), request.name()));
    return new SignUpResponse(member.id(), member.email());
}
```

**입구부터.** 파라미터에 `@RequestBody SignUpRequest request`가 붙었습니다. `@RequestBody`는 요청으로 들어온 JSON 본문을 `SignUpRequest`라는 자바 객체로 바꿔서 넣어 달라는 뜻입니다. 클라이언트가 `{"email": "...", "name": "..."}`을 보내면, 그 JSON이 `request.email()`, `request.name()`으로 꺼내 쓸 수 있는 객체가 되어 손에 들어옵니다. 이 변환을 우리가 손으로 파싱하지 않습니다 — 매핑만 걸어 두면 프레임워크가 해 줍니다.

**출구.** 반환 타입이 아까 `String`에서 `SignUpResponse`로 바뀌었습니다. 저장소의 `save`를 호출하면 id가 채워진 `Member`가 돌아오는데, 이걸 그대로 내보내지 않습니다. `new SignUpResponse(member.id(), member.email())` — id와 이메일만 담은 **응답 전용 객체**로 다시 싸서 돌려줍니다.

여기서 잠깐. 왜 도메인 `Member`를 그냥 반환하지 않을까요? 이게 L03에서 "주문서와 식재료를 같은 것으로 쓰지 말라"던 그 지점입니다. `Member`에는 name도 있고, 나중엔 비밀번호나 내부 필드가 붙을 수도 있습니다. 응답에 필요한 건 id와 이메일뿐인데 도메인을 통째로 노출하면, 보여줄 생각도 없던 것까지 새어 나갑니다. 그래서 **컨트롤러의 입구와 출구는 도메인 객체가 아니라 요청·응답 전용 DTO**입니다. 들어올 땐 `SignUpRequest`, 나갈 땐 `SignUpResponse` — 경계에서 데이터의 모양을 한 번씩 바꿔 주는 거죠.

**결과.** 이제 JSON 본문이 `SignUpRequest`로 역직렬화되고, 저장 뒤 `SignUpResponse`가 JSON으로 나갑니다. 데이터가 문으로 들어와서, 저장되고, 결과가 문으로 나가는 — 왕복 흐름이 처음으로 완성됐습니다.

**정리(lecture_message).** 컨트롤러의 입구와 출구는 도메인 객체가 아니라 요청·응답 전용 DTO입니다. 경계에서 데이터의 모양을 바꾼다 — 이게 컨트롤러가 하는 일입니다. 그런데 지금은 아무 데이터나 다 받아 저장합니다. 같은 이메일로 또 보내도 그냥 저장되죠. 여기에 규칙을 하나 넣어야 합니다.

## 3. step-03 — (일부러) 뚱뚱한 컨트롤러: 웨이터가 주방일까지  ⏱ 1.5분

[IDE 화면: 03-fat-controller]

**이전 상태.** 지금 컨트롤러는 받은 데이터를 검사 없이 그대로 저장합니다. 같은 이메일로 열 번 보내면 열 번 다 가입됩니다.

**왜 바꾸나.** "같은 이메일로는 중복 가입 안 된다"는 규칙을 적용해야 합니다. 자, 그 규칙을 **일단 가장 손쉬운 자리 — 컨트롤러 안에** 넣어 보겠습니다. 일부러 그렇게 합니다.

**무엇이 바뀌나.** `signUp` 메서드 안, 저장하기 직전에 검사 한 덩어리가 들어왔습니다.

```java
@PostMapping("/members")
public SignUpResponse signUp(@RequestBody SignUpRequest request) {
    // 비즈니스 규칙이 컨트롤러 안에 들어와 있다.
    if (memberRepository.existsByEmail(request.email())) {
        throw new IllegalStateException("이미 가입된 이메일입니다: " + request.email());
    }
    Member member = memberRepository.save(new Member(null, request.email(), request.name()));
    return new SignUpResponse(member.id(), member.email());
}
```

`existsByEmail`로 이미 있는 이메일인지 묻고, 있으면 예외를 던져 저장을 막습니다. 없으면 그대로 저장하고 응답하죠. 코드는 잘 돌아갑니다. 신규는 저장되고, 중복은 막힙니다. **동작은 합니다.**

그런데 이 그림을 L03의 눈으로 보세요. **아까 웨이터가 주방일까지 하던, 바로 그 코드입니다.** 이 메서드 하나가 지금 서로 다른 두 일을 동시에 떠안았습니다. "요청을 받아 형식을 맞추는 일"은 컨트롤러, 홀 서버의 일이 맞습니다. 하지만 "이미 가입된 이메일인가를 판단하는 일"은 **가입 규칙**, 즉 주방의 일이죠. 홀 서버가 주문을 받으면서 요리까지 하고 있는 겁니다 — L03에서 "뚱뚱한 컨트롤러"라 부른 그 상태를, 일부러 코드로 재현한 겁니다.

**결과.** 중복이면 저장을 막고, 아니면 저장 후 응답합니다. 단, 이 모든 판단이 컨트롤러 한 곳에 뭉쳐 있습니다. (참고로 지금은 중복 시 예외가 그대로 500으로 나갑니다 — 이건 마지막 단계에서 손봅니다.)

**정리(lecture_message).** 지금 이 코드는 동작합니다. 하지만 컨트롤러가 "요청을 받는 일"과 "가입 규칙을 판단하는 일"을 동시에 떠안았습니다 — L03에서 말한 책임 경계가 무너진 상태입니다. 그럼 이제, 무너진 경계를 코드로 다시 세웁니다.

## 4. step-04 — 책임 분리: 규칙을 주방으로 옮긴다  ⏱ 2.5분

[IDE 화면: 04-service-extracted]

**이전 상태.** 컨트롤러 한 곳이 요청 처리와 비즈니스 규칙을 모두 짊어지고 있습니다. 홀 서버가 주방일까지 하는 그 식당이죠.

**왜 바꾸나.** L03의 핵심을 다시 꺼냅니다. 나누는 기준은 "메서드가 길어서"가 아니라 **변경 이유**입니다. 웹 형식이 바뀌는 이유 — 경로, 상태 코드, 응답 포맷 — 와 가입 규칙이 바뀌는 이유 — 정책, 중복 판단 기준 — 는 출처가 다릅니다. 한 곳에 두면 한쪽 변경이 다른 쪽을 흔듭니다. 그래서 나눕니다.

**무엇이 바뀌나 — 여기가 오늘의 핵심 장면입니다.** 파일이 하나 새로 생겼습니다. `MemberService`. 그리고 잘 보세요 — **step-03에서 컨트롤러 안에 있던 그 검사·저장 블록이, 한 줄도 바뀌지 않고 그대로 이리로 옮겨 왔습니다.**

```java
@Service
public class MemberService {

    private final MemberRepository memberRepository;

    public MemberService(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }

    public Member signUp(SignUpRequest request) {
        if (memberRepository.existsByEmail(request.email())) {
            throw new IllegalStateException("이미 가입된 이메일입니다: " + request.email());
        }
        return memberRepository.save(new Member(null, request.email(), request.name()));
    }
}
```

`existsByEmail`로 검사하고, 있으면 예외, 없으면 저장 — 아까 컨트롤러에서 봤던 바로 그 코드죠. 새 로직을 짠 게 아닙니다. **자리만 옮긴 겁니다.** 클래스 위엔 `@Service`를 붙여서 "이건 주방"이라고 표시했습니다.

이제 컨트롤러가 어떻게 홀쭉해졌는지 봅니다.

```java
public MemberController(MemberService memberService) {   // Repository → Service
    this.memberService = memberService;
}

@PostMapping("/members")
public SignUpResponse signUp(@RequestBody SignUpRequest request) {
    Member member = memberService.signUp(request);       // 검사·저장 블록이 사라지고, 한 줄 위임
    return new SignUpResponse(member.id(), member.email());
}
```

두 가지가 달라졌습니다. 첫째, 컨트롤러가 이제 `MemberRepository`를 직접 주입받지 않습니다. **`MemberService`만** 압니다. 홀 서버는 이제 창고에 직접 손대지 않고 주방에 주문서를 넘길 뿐입니다. 둘째, 아까 그 `if`-검사-저장 블록이 통째로 사라지고 `memberService.signUp(request)` 한 줄이 됐습니다. 컨트롤러의 일은 이제 셋뿐입니다 — 요청 받고, 서비스에 넘기고, 응답 DTO로 감싸 돌려주기.

**결과.** 컨트롤러는 요청 수신과 응답 변환만, `MemberService`가 중복 검사와 저장을 담당합니다. 그런데 겉으로 보이는 **동작은 step-03과 완전히 똑같습니다.** 신규는 저장, 중복은 막힘. 사용자는 아무 차이도 못 느낍니다. 바뀐 건 오직 코드의 구조 — 누가 무슨 책임을 지느냐뿐입니다.

**정리(lecture_message).** 분리는 파일을 늘리는 게 아니라 변경 이유를 나누는 것입니다. 이제부터 웹 형식이 바뀌면 Controller만, 가입 규칙이 바뀌면 Service만 고칩니다. L03에서 말로 그렸던 경계가, 방금 코드 블록이 파일을 건너 이사하는 것으로 눈앞에서 확인됐습니다.

## 5. step-05 (final) — 응답 완성: 상태 코드로 결과를 말한다  ⏱ 1.5분

[IDE 화면: final]

**이전 상태.** 지금은 성공이든 실패든 다 200으로 나가고, 중복일 때 던진 예외는 받아 주는 곳이 없어 그대로 **500 서버 에러**가 됩니다. 중복은 클라이언트 잘못인데 서버가 고장 난 것처럼 응답하는 거죠.

**왜 바꾸나.** 제목의 "**응답까지**"란, 데이터를 넘기는 걸 넘어 결과를 **HTTP 상태 코드로 표현**하는 것까지입니다. 성공과 중복은 의미가 다르니 상태도 달라야 합니다.

**무엇이 바뀌나.** 세 군데가 바뀝니다. 먼저 서비스에서, 범용 예외 대신 **도메인 예외**를 던지도록 딱 한 줄을 바꿉니다.

```java
// MemberService.signUp() 안 — IllegalStateException → DuplicateEmailException
throw new DuplicateEmailException(request.email());
```

그리고 이 예외 클래스를 새로 하나 만듭니다.

```java
public class DuplicateEmailException extends RuntimeException {
    public DuplicateEmailException(String email) {
        super("이미 가입된 이메일입니다: " + email);
    }
}
```

범용 `IllegalStateException`은 온갖 상황에서 던져질 수 있어 "중복"만 골라내기 어렵습니다. **"중복"이라는 의미가 담긴 전용 예외**여야 그것만 409로 매핑할 수 있습니다.

마지막으로 컨트롤러에 두 가지 — 성공 응답의 201과, 예외를 잡는 핸들러 — 를 답니다.

```java
// 성공: 200 → 201 Created
return ResponseEntity.status(HttpStatus.CREATED).body(response);

// 중복 예외를 409 Conflict로 매핑
@ExceptionHandler(DuplicateEmailException.class)
public ResponseEntity<String> handleDuplicateEmail(DuplicateEmailException e) {
    return ResponseEntity.status(HttpStatus.CONFLICT).body(e.getMessage());
}
```

`@ExceptionHandler`는 그 예외가 500으로 새어 나가기 전에 낚아채, 우리가 정한 상태로 응답을 만드는 그물입니다. 중복이면 **409 Conflict** — "당신 요청이 지금 상태와 충돌한다"는 뜻이죠.

**결과 — 이건 실제로 띄워서 확인한 값입니다.** [IDE 화면: final — 실행 로그/터미널]

- alice로 가입 → **201 Created**, 본문 `{"id":1,"email":"alice@example.com"}`
- 같은 alice로 다시 가입 → 500이 아니라 **409 Conflict**, 본문 "이미 가입된 이메일입니다"
- 다른 사람 bob으로 가입 → **201**, id는 2로 증가

step-03에서 500이던 그 중복 요청이, 이제 409로 정확히 바뀌었습니다. 코드가 아니라 **실행 결과**가 그걸 보여줍니다.

**정리(lecture_message).** "요청 매핑부터 응답까지"의 마지막 조각은 상태 코드입니다. 성공은 201, 중복은 409 — 응답은 데이터만이 아니라 결과의 의미를 담습니다.

## 6. 마무리 — 요청 매핑에서 응답까지, 전체 지도  ⏱ 0.5분

[IDE 화면: final — 전체 구조 한눈에]

문 하나에서 시작해 완성된 가입 API까지 왔습니다. 되짚으면 — **매핑**으로 문을 열고(01), **DTO**로 데이터를 주고받고(02), 규칙을 일부러 컨트롤러에 뭉쳤다가(03) **서비스로 분리**하고(04), **상태 코드**로 결과의 의미까지 말했습니다(05).

```
POST /members → Controller(매핑·DTO·상태코드) → Service(가입 규칙) → Repository(저장)
```

그리고 오늘 03에서 04로 넘어간 그 한 장면 — 코드 블록이 컨트롤러에서 서비스로 자리를 옮긴 것 — 이 L03에서 말로만 그렸던 책임 경계를, 눈으로 확인시켜 준 대목이었습니다. 기본 컨트롤러를 만들 줄 알고, 무엇을 컨트롤러에 두고 무엇을 서비스에 둘지 판단할 수 있으면 오늘 목표는 달성입니다.
