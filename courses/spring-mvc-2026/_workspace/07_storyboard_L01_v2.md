# L01 통합 덱 스토리보드 (v2) — Spring MVC는 요청을 왜 DispatcherServlet에 몰아주는가 (흐름 추적까지)

## 설계 개요

- **물리 13장 구성** = 파트1 이론 슬라이드 9장(SLIDE 01~09, 마지막 09는 이론→시뮬 **전환** 슬라이드로 개조) → **CUE-SIM**(모드 A 진입) → *(시뮬레이터 전체화면 — 물리 슬라이드 없음. 모드 A→B 리셋은 비-렌더 편집 마커 RESET)* → **CUE-RETURN**(종료·복귀) → **SLIDE 10**(두 경로 요약) → **SLIDE 11**(L02 책임 경계 다리).
- **잠정 번호 1:1 승계.** 프롬퍼의 `[SLIDE 01]~[SLIDE 11]` + `[SIM 실행]`/`[SIM 리셋→모드②]`/`[SIM 종료]` 마커와 1:1 대응. `[SIM STEP n]`(모드 A 11개 + 모드 B 6개)은 **시뮬레이터 내부 나레이션 큐**이므로 슬라이드를 만들지 않는다(파트2 본체는 시뮬레이터가 화면으로 말함).
- **구 승인본 재활용.** SLIDE 01~08은 구 07_storyboard_L01(이론 9장) 중 01~08을 **메시지·구성 그대로 승계**(테마만 다크→라이트). SLIDE 10·11은 구 07_storyboard_L02의 SLIDE 02·03을 승계·개조. 자세한 변경점은 하단 "구 승인본 대비 변경".
- **핵심 개조 = SLIDE 09.** 구 L01 #09("공통은 모으고 개별은 나눈다 + 예고, SIM 마커 금지")와 구 L02 도입 슬라이드(POST /members 재료 + "저 관문이 왜 거기 있는가" 관찰 프레임)를 **한 장의 전환 슬라이드로 합쳤다.** 이 장은 이제 뒤의 CUE-SIM으로 실제 진입하는 온램프다. 구 L02의 별도 도입 슬라이드는 **삭제(SLIDE 09에 흡수)**.

- **테마·엔진:** 라이트 테마(rich 프로파일). 판서 엔진(펜/`b` 판서모드/`g` 모눈/⛶/←→) 위에서 동작. 색 강조는 라이트 토큰 기준 accent/warning/dim으로 지시(다크 전제 조립 지시는 전부 라이트로 재해석). 시뮬레이터는 별도 창(다크 유지)이라 슬라이드 라이트와 충돌 없음 — 오히려 slide-rules v1.6이 "슬라이드가 시뮬레이터 팔레트를 계승하지 말 것"을 명시.

## SLIDE 04 — 등장 배경: Front Controller 패턴

- **프롬퍼 대응:** `[SLIDE 04]`
- **화면 소스:** 슬라이드 / **시드:** 없음 (구성 스키매틱)
- **핵심 메시지(한 줄):** 모든 요청을 단일 핸들러 하나로 통과시켜 — 공통은 먼저 처리하고, 고유 동작은 하위로 분배(dispatch)한다.
- **구성 요소 명세:**

  - 라벨: 우측 화살표 `dispatch`, 하위 박스 `요청별 고유 처리`. "단일"을 accent.

## SLIDE 10 — 두 경로 요약: 반환값이 출구를 가른다 (구 L02 SLIDE 02 승계)

- **핵심 메시지(한 줄, 단일 대조):** 두 경로는 STEP 6(preHandle)까지 한 몸이고, 갈린 지점은 **컨트롤러가 무엇을 반환하느냐** 하나 — 객체를 반환하면 직렬화·커밋(뷰 없음), 뷰 이름을 반환하면 ViewResolver로 View를 만들어 렌더링. 같은 데스크, 반환값에 따라 다른 출구.
- **구성 요소 명세:**

  - 공통 구간 바(좌): `STEP 0 → 6 preHandle` 라벨 `여기까진 한 몸`

  - **범위-밖 방백:** HandlerExceptionResolver "안전망"은 원고가 "오늘 흐름 바깥"으로 자기표기 → **작은 dim 각주 라벨 1행**: `예외 → HandlerExceptionResolver (오늘 흐름 밖)`. 본류 다이어그램에 넣지 않음.

- **단어 수 추정:** 약 22어절 (제목 3 + 공통바 3 + 분기 2 + A 6 + B 4 + 하단 4; 각주 라벨 제외). **PASS**

## 보고 사항 (오케스트레이터 — 임의 수정 안 함)

**① [테마/일관성 결정 필요, 준-blocker] manifest ↔ slide-rules 드리프트.**
`manifest.yaml.style.visual_style = "깔끔한 기술 교육용 (다크 테마)"`인데, slide-rules v1.6/1.7 rich 프로파일은 **라이트 테마 고정**(+ "슬라이드가 시뮬레이터 다크 팔레트를 계승하지 말 것"을 이 통합 레슨 상황에 정확히 겨냥). slide-rules 예외 조항("manifest가 명시적으로 다크를 요구할 때만 예외")상 다크도 허용되긴 하나, v1.7 재편·라이트 엔진·덱 일관성 취지는 라이트를 가리킨다. **본 스토리보드는 라이트로 설계**했다. 결정 필요:
   - (권장) 라이트로 확정 → **manifest.visual_style을 라이트로 정정**하고, L02·L03·L04 덱도 라이트로 통일(덱 간 일관성).
   - 또는 다크 유지(예외 발동) → 본 스토리보드 색 지시를 다크로 되돌림. 이 경우 시뮬레이터 팔레트 계승 금지 규칙과의 긴장을 감수.
   또한 **SLIDE 06의 [IMG] 시드가 "다크 톤"으로 기술**되어 있어, 라이트 확정 시 이미지 밝은 팔레트 재생성 권장(원고 시드 텍스트 개정 신호).

**② [시뮬레이터 산출물 범위] 시드 [비유]#2(부친 편지)는 덱 밖.**
프롬퍼 217행이 이 비유를 "**STEP 9 시뮬레이터 화면 오버레이**"로 지정 → 물리 슬라이드로 만들지 않았다. 이 비유가 실제 시뮬레이터(`시뮬레이터_MVC요청흐름.html`, 이미 완성)에 오버레이로 존재하는지는 **덱 범위 밖**. 없으면 시뮬레이터 개정 신호이므로 확인 요망(스토리보드에서 원고·시뮬레이터 임의 변경 안 함).

**③ [번호 확정 요청]** 프롬퍼 SLIDE 번호는 "잠정"이다. 본 스토리보드가 SLIDE 01~11 + CUE-SIM/RESET/CUE-RETURN로 **물리 13장(+편집 마커 1)** 확정 제안. G4 승인 시 프롬퍼 마커를 이 번호로 고정(현 프롬퍼와 이미 1:1이라 원고 개정 불필요).
