# L02 판서대본 — Controller와 Service의 책임 경계

> 대상: Spring Boot로 CRUD API를 만들어 본 경험자.
> 형식: 판서슬라이드 8컷(summary) 대응. 각 컷 = "강렬한 한 줄 → 쉬운 비유 설명 → 개념 정의".
> 중심 비유: 식당 — 홀 서버(웨이터)=Controller, 주방(셰프)=Service, 주문서=DTO, 식재료=Entity, 한 티켓 all-or-nothing=트랜잭션.
> 비유 이탈 지점: 컷 5 끝 — 주방을 '저장창고/DB'로 오해시키는 순간 비유를 버리고 계층으로 직설.

---

## 컷 1 — 동작은 하는데, 자꾸 손이 가는 컨트롤러

**강렬한 한 줄**
"잘 돌아가는데, 왜 그 메서드에만 자꾸 손이 갈까요?"

**쉬운 설명**
여러분 모두 Spring Boot로 CRUD API를 만들어 봤습니다. 그러면 이런 컨트롤러를 분명히 써 봤을 거예요. 메서드 하나 안에서 파라미터를 꺼내고, 값이 이상한지 확인하고, 업무 규칙을 판단하고, 저장소를 호출하고, 응답까지 조립합니다. 잘 돌아갑니다. 테스트도 통과해요. 그런데 프로젝트가 커질수록 이상하게 그 메서드에만 자꾸 손이 갑니다. 오늘은 그게 왜 그런지, 그리고 어떻게 그 손 가는 걸 멈추는지를 다룹니다.

경계를 식당 하나로 비유하겠습니다. 오늘 이 비유를 끝까지 끌고 갑니다. 손님을 응대하는 홀 서버와, 안쪽에서 요리하는 주방. 지금 이 컨트롤러는, 홀 서버가 주문도 받고 요리까지 직접 하겠다고 나선 식당입니다. 테이블이 하나면 그래도 됩니다. 문제는 언제나 그 다음이에요.

학생들에게 한 번 물어보세요 — "컨트롤러 메서드가 50줄, 100줄 넘어가서 스크롤하며 고쳐 본 분?" 대부분 손을 듭니다. 그 공감에서 오늘을 시작합니다.

**개념 정의**
이렇게 컨트롤러 하나가 모든 일을 떠안은 모양을 현장에서는 흔히 "뚱뚱한 컨트롤러"라고 부릅니다. 다만 이건 학계 용어나 공식 명칭이 아니라 개발자들끼리 쓰는 통칭입니다. 그러니 오늘 목표는 이 이름을 외우는 게 아닙니다. 목표는 딱 하나 — 무엇이 컨트롤러의 일이고 무엇이 아닌지, 그 경계를 스스로 판단할 수 있게 되는 것. 오늘은 판단 기준을 손에 쥐고, 다음 시간에 그 경계를 직접 코드로 긋습니다.

## 컷 2 — 경계가 없으면 무엇이 무너지나 (세 가지)

**강렬한 한 줄**
"경계를 안 그으면, 정확히 세 가지가 무너집니다."

**쉬운 설명**
하나씩 보죠.

첫째, 규칙이 복사됩니다. 회원 가입할 때 "이미 가입된 이메일인지" 확인하는 규칙이 있다고 합시다. 이 규칙을 웹 가입 말고 관리자 배치에서도, 엑셀 일괄 등록에서도 써야 한다고 해봐요. 규칙이 컨트롤러 안에 박혀 있으면 그 코드를 복붙해서 세 군데에 흩뿌리게 됩니다. 그리고 규칙이 바뀌는 날, 세 군데를 다 찾아 고쳐야 하는데 꼭 하나를 빠뜨리죠.

둘째, 변경이 서로를 넘어뜨립니다. HTTP를 다루는 코드와 업무 규칙이 한 메서드에 섞여 있으면, 응답 포맷 하나 바꾸려다 옆에 있던 가입 규칙을 실수로 건드리고, 규칙을 손보다가 엔드포인트 경로를 깨뜨립니다. 이유가 둘이면, 한 이유로 손댈 때마다 다른 이유가 인질로 잡히는 겁니다.

셋째, 검증하려면 웹을 통째로 띄워야 합니다. 가입 규칙이 컨트롤러 안에 있으면, 그 규칙 하나가 맞는지 확인하려고 HTTP 계층 전체를 세워야 해요. 규칙이 서비스의 평범한 자바 객체에 있으면 웹 없이 그것만 딱 검증할 수 있고요. 빠르다 느리다의 문제가 아니라, 검증하는 데 무엇까지 딸려 오느냐의 문제입니다.

식당으로 돌아가면, 홀 서버가 요리까지 하는 식당은 그 사람이 화장실만 가도 요리가 멈춥니다. 애플리케이션의 경계가 웹 프레임워크에 통째로 묶여버린 거예요. 웹이 아닌 다른 입구로는 같은 일을 재사용할 수가 없게 됩니다.

**개념 정의**
- 공통 업무 로직을 한곳에 모아 여러 진입점에 걸친 중복을 없애는 자리를 Martin Fowler는 "서비스 계층(Service Layer)"이라고 불렀습니다. (Fowler, *Patterns of Enterprise Application Architecture*, "Service Layer")
- "한 모듈은 바뀌어야 할 이유가 오직 하나여야 한다" — Robert C. Martin의 단일 책임 원칙(SRP). (R. C. Martin, "The Single Responsibility Principle", 2014)
- 서비스 계층이 애플리케이션의 "경계"를 정의한다는 것도 Fowler의 표현입니다. (Fowler, "Service Layer")

## 컷 3 — 나누는 기준: 줄 수가 아니라 "변경 이유"

**강렬한 한 줄**
"'컨트롤러가 길어지면 서비스로 뺀다' — 이거 틀렸습니다."

**쉬운 설명**
여기서 아주 흔한 오해 하나를 끊고 갑니다. 나누는 기준은 코드가 길어서가 아닙니다. 기준은 무엇이, 어떤 이유로 바뀌는가입니다.

생각해 보세요. HTTP 표현이 바뀌는 이유는 어디서 옵니까? 경로를 `/members`에서 `/api/v2/members`로 바꾸자, 성공 시 200 말고 201을 주자, 응답 필드를 하나 더 넣자. 이런 건 전부 API 스펙 쪽에서 옵니다. 반면 업무 규칙이 바뀌는 이유는? "이제 이메일 중복 말고 휴대폰 중복도 막자", "가입 시 포인트 1000점을 주자". 이건 기획에서 옵니다. 출처가 완전히 다르죠.

학생들에게 던지세요 — "그럼 이 두 변경을 한 메서드에 같이 두면 무슨 일이 생길까요?" 잠깐 기다렸다 받습니다. 출처가 다른 두 변경을 한 모듈에 두면, 한쪽이 다른 쪽을 인질로 잡습니다. 기획자가 규칙 하나 바꿔달라고 했을 뿐인데 API 스펙이 흔들릴 위험을 지는 거예요.

**개념 정의**
- Martin은 SRP를 두고 "결국 사람에 관한 것"이라고 못박았습니다 — 서로 다른 이해관계자의 변경 요구가 서로를 깨뜨리지 않게 격리하라는 뜻입니다. (R. C. Martin, "SRP", 2014)
- 반대 방향의 오해도 막습니다. 모든 로직을 서비스에 몰아넣고 도메인 객체를 게터·세터만 있는 빈 껍데기로 두면, 그건 "빈혈 도메인 모델(Anemic Domain Model)"이라는 또 다른 안티패턴입니다. (Fowler, "AnemicDomainModel") 오늘은 이 한 문장만 붙잡으세요 — "서비스는 로직을 아무거나 던져 넣는 만능 창고가 아니다."

## 컷 4 — 두 계층의 책임표 (홀 서버 vs 주방)

**강렬한 한 줄**
"이 표 하나면, 앞으로 코드 짤 때 계속 꺼내 쓰게 됩니다."

**쉬운 설명**
경계를 표로 정리합니다. 학생과 같이 그려두면 나중에 계속 꺼내 씁니다.

| | Controller (홀 서버) | Service (주방) |
|---|---|---|
| 한 문장 | HTTP와 애플리케이션 사이의 어댑터 | 유스케이스 + 트랜잭션 경계 |
| 하는 일 | 매핑·바인딩·형식 검증 트리거·예외→상태코드·응답 조립 | 업무 규칙 실행·도메인/저장소 조율·트랜잭션 제어 |
| 다루는 것 | 주문서(요청 DTO) ↔ 상태 전달 | 레시피(업무 로직), 티켓 하나 = 전부 아니면 취소 |
| 바뀌는 이유 | 경로·상태코드·응답 포맷 | 정책·계산·트랜잭션 범위 |

Controller는 HTTP 경계의 어댑터입니다. 손님 말을 알아듣고, 메뉴에 있는 주문인지 형식을 확인하고, 음식이 나가면 "나왔습니다" 하고 상태를 전달하는 홀 서버.

검증을 한 겹만 짚겠습니다. `@Valid` 같은 형식·제약 검증은 컨트롤러 경계에서 트리거됩니다. 참고로 이건 버전을 좀 탑니다 — Spring 6.1부터는 내장 메서드 검증을 쓰려면 클래스 레벨의 `@Validated`를 빼야 하는 등 동작이 갈리니, 실무에서 쓸 땐 반드시 그 버전의 공식 문서를 확인하세요. 여기서 진짜 중요한 건, 컨트롤러가 하는 검증은 "형식이 맞는가"이지 "업무적으로 되는가"가 아니라는 겁니다. 홀 서버는 주문서 양식이 맞는지는 보지만, 재료가 남았는지는 모릅니다.

Service는 유스케이스이자 트랜잭션 경계입니다. 주방이 실제 요리를 하는 자리죠. 한 요청이 이 둘을 지나는 지점만 딱 짚으면 — 컨트롤러가 요청을 받아 입력 DTO로 바꿔 서비스의 유스케이스 메서드에 배턴을 넘기고, 서비스가 결과를 돌려주면 컨트롤러가 그걸 응답 표현으로 바꿉니다. 이 배턴을 주고받는 한 지점이 오늘의 무대입니다. DispatcherServlet이 여기까지 어떻게 오는지는 지난 L01에서 이미 봤으니 반복하지 않습니다.

**개념 정의**
- Spring 공식 레퍼런스는 컨트롤러를 "HTTP 요청과 비즈니스 로직 사이의 다리"로 설명합니다. (Spring Framework Reference, Web MVC, "Annotated Controllers", Spring 6.x / Boot 3.4.x)
- 형식 검증의 버전 주의는 Spring Framework Reference, Web MVC "Validation" (Spring 6.1 메서드 검증) 참고.
- 서비스 계층은 "업무 로직을 캡슐화하고, 트랜잭션을 제어하며, 응답을 조율"합니다. (Fowler, "Service Layer")

## 컷 5 — 트랜잭션 경계는 왜 하필 Service인가 (오늘의 핵심)

**강렬한 한 줄**
"오늘 딱 한 장만 가져가라면, 이겁니다 — 트랜잭션 경계 = 유스케이스 경계 = Service."

**쉬운 설명**
주방 티켓을 떠올려 보세요. 스테이크랑 사이드가 한 티켓에 묶여 있으면, 둘 다 나가거나 둘 다 안 나갑니다. 스테이크만 나오고 사이드는 "아 그건 취소됐어요" 하는 반쪽짜리 서빙은 없죠. 하나의 업무 단위가 전부-아니면-전무로 처리되는 것, 이게 트랜잭션이고, 그 단위를 정의하는 자리가 바로 서비스의 유스케이스 메서드입니다.

그래서 정리하면 — 트랜잭션 경계 = 유스케이스 경계 = 서비스. 이걸 컨트롤러에 두면 안 되는 이유가 여기서 나옵니다. 트랜잭션은 업무 단위인데, 컨트롤러는 업무 단위를 정의하는 자리가 아니거든요.

**[비유 이탈 — 여기서 식당 비유를 일부러 버립니다]**
자, 여기서 오늘 끌고 온 식당 비유 하나를 의도적으로 버립니다. 학생들에게 명시적으로 경고하세요 — "지금부터 비유를 하나 내려놓겠습니다." 주방을 "재료 창고"나 "데이터베이스"로 생각하면 안 됩니다. 주방은 조리하는 곳, 즉 업무를 조율하는 유스케이스입니다. 재료를 넣고 꺼내는 저장창고는 완전히 별개의 계층인 Repository이고, 그 뒤에 DB가 있어요. 서비스가 저장소를 호출은 하지만, 서비스가 곧 저장소는 아닙니다. 이 층이 흐려지는 순간, 다음 컷에서 볼 오분류가 시작됩니다.

여기서부터는 비유가 아니라 계층으로 직설합니다:
`Controller(HTTP 경계) → Service(유스케이스·트랜잭션) → Repository(저장 접근) → DB(저장소)`
이 네 단을 판서로 왼쪽에서 오른쪽으로 크게 쓰고, Service 아래에만 밑줄을 그으며 "트랜잭션은 여기"라고 못박습니다.

**개념 정의**
- Spring 팀은 이걸 명시적으로 권장합니다 — "`@Transactional`은 인터페이스가 아니라 구체 클래스의 메서드에 붙여라." 실무에서 그 구체 클래스가 바로 서비스입니다. (Spring Framework Reference, Data Access, "Using @Transactional")

## 컷 6 — 코드로 확인 (관찰: 뚱뚱한 → 분리 → 완성)

**강렬한 한 줄**
"말로 그린 경계를, 이제 실제 코드에서 눈으로 확인합니다. 오늘은 관찰만."

**진행 방식 (IDE 전환 cue)**
이 컷은 슬라이드에 코드를 띄우지 않습니다. 슬라이드는 "실제 코드에서 확인" 한 줄만 두고, IDE(read-only)로 전환해 반입 코드 세 파일을 순서대로 띄웁니다. 빌드·실행·타이핑 없음 — 직접 구현은 다음 시간(L03)입니다.
- 관찰 대상: `courses/spring-mvc-offline-2026/code/L03` (원본: spring-mvc-2026/code/L04, read-only) — `03-fat-controller` → `04-service-extracted` → `final`

**쉬운 설명 (화면 전환하며 말할 것)**
먼저 `03-fat-controller`, 뚱뚱한 컨트롤러입니다. `signUp` 메서드 안을 보세요. `if (memberRepository.existsByEmail(...))` — 이미 가입된 이메일인지 확인하는 가입 규칙이 컨트롤러 안에 직접 들어와 있습니다. 홀 서버가 주방 일까지 하는 상태죠. 동작은 합니다. 하지만 이 규칙을 다른 데서 또 쓰려면? 복붙입니다. 컷 2의 첫 번째 문제 그대로예요. 학생들에게 물으세요 — "이 중복 검사 코드, 컨트롤러에 있는 게 편해 보이나요, 불안해 보이나요?"

다음 `04-service-extracted`. 달라진 걸 찾게 하세요. 컨트롤러에 있던 그 `if` 검사가 사라졌습니다. 대신 `MemberService`라는 새 파일이 생겼고, 규칙이 그 안의 `signUp` 메서드로 옮겨갔어요. 컨트롤러는 이제 `memberService.signUp(request)` 한 줄로 주방에 배턴을 넘길 뿐입니다. 규칙 판단은 주방이 하고요. 컷 4의 표가 코드로 그대로 나타난 겁니다.

마지막 `final`. 여기서 한 걸음 더 갑니다. 서비스는 중복일 때 범용 예외가 아니라 `DuplicateEmailException`이라는 도메인 예외를 던집니다. 그리고 컨트롤러의 `@ExceptionHandler`가 그 예외를 잡아 409 Conflict 상태 코드로 매핑하죠. 예외를 "던지는" 건 주방(서비스)이고, 그걸 "손님에게 어떤 말로 전할지"(상태 코드)는 홀 서버(컨트롤러)가 정합니다. 업무 판단과 HTTP 표현이 정확히 갈라져 있죠. 이게 오늘 표로 그린 경계의 완성형이고, 다음 시간 실습의 뼈대입니다.

**개념 정리 한 줄**
`fat-controller` → `service-extracted` → `final(도메인 예외 → 409 매핑)`. 세 단계가 곧 다음 시간에 여러분 손으로 밟을 순서입니다.

## 컷 7 — 흔히 헷갈리는 세 지점

**강렬한 한 줄**
"경계를 배웠으니, 이제 실제로 밟게 될 지뢰 세 개를 짚습니다."

**쉬운 설명**
첫째, 트랜잭션을 웹 계층에 둡니다. `@Transactional`을 컨트롤러에 붙이거나, 컨트롤러에서 저장소를 여러 번 이어 호출해 업무 단위 경계를 웹에 만드는 것. 컷 5에서 봤듯 권장은 서비스 구체 클래스 메서드입니다.

둘째, 주문서와 식재료를 같은 것으로 씁니다 — DTO와 Entity 혼용. 요청·응답용 DTO와 도메인·영속 Entity를 구분 없이 하나로 쓰는 실수예요. 주문서엔 "스테이크 미디엄"이라고 적지, 소 한 마리가 통째로 적히진 않죠. 엔티티를 그대로 응답에 노출하면 직렬화·바인딩 관심사가 도메인으로 새거나, 안 보여줘도 될 필드가 과하게 드러날 수도 있습니다. 그래서 경계에서 데이터 모양을 바꾸는 변환이 컨트롤러의 일입니다. final 코드에서 `SignUpRequest`, `SignUpResponse`가 따로 있던 게 이겁니다.

셋째, 업무 규칙 검증을 형식 검증과 같은 층으로 봅니다. `@NotBlank`, `@Min` 같은 형식 검증은 컨트롤러 경계지만, "이미 가입된 이메일인가", "잔액이 부족한가" 같은 업무 규칙 검증은 서비스입니다. 홀 서버는 "메뉴에 있는 주문인지"는 확인하지만, "재료가 남았는지"는 주방이 압니다. 이 둘을 한 층에서 처리하려 들면 경계가 무너집니다.

**개념 정의**
- 트랜잭션 위치 권장: Spring Framework Reference, Data Access "Using @Transactional".
- DTO는 "프로세스 경계를 넘어 데이터를 나르는 객체" — 목적 자체가 도메인 Entity와 다릅니다. (Fowler, *PoEAA*, "Data Transfer Object")

## 컷 8 — 언제 이 분리가 과한가 + 다음 시간 예고

**강렬한 한 줄**
"무조건 서비스를 만들어야 할까요? 아닙니다. 대신 두 질문으로 판단합니다."

**쉬운 설명**
서비스가 저장소를 그냥 1:1로 넘기기만 하는, 아무 규칙도 없는 순수 통과형 CRUD에서는, 로직 하나 없는 서비스가 상용구만 늘린다는 실무 논쟁이 있습니다. 정답이 정해진 규칙이 아니라 판단의 문제예요. 그러니 "무조건 없애라"도 "무조건 만들어라"도 아닙니다. 이렇게 물어야 합니다 — "이 계층은 대체 무엇을 위해 있는가?"

그래서 오늘의 결론은 외울 규칙 목록이 아니라 두 개의 질문입니다. 새 코드를 짜다 "이걸 컨트롤러에 둘까 서비스에 둘까" 망설여지면, 이 둘을 던지세요.
- "이 변경은 어떤 이유로 오는가?" — HTTP 표현이 바뀌면 Controller, 업무 규칙이 바뀌면 Service. (SRP)
- "이 로직을 다른 진입점에서도 재사용해야 하는가?" — 재사용 경계가 필요하면 Service. (Service Layer)

이 두 질문에 답할 수 있으면, 새 코드를 어디에 둘지 스스로 판단할 수 있습니다. 그게 오늘의 목표였어요. 규칙을 외운 게 아니라, 판단 기준을 손에 쥔 겁니다. 학생들에게 마지막으로 던지세요 — "지금 자기 프로젝트 컨트롤러 하나를 떠올려서, 이 두 질문을 통과 못 하는 코드 한 줄만 각자 찾아보세요."

**다음 시간 예고 (L03)**
오늘 말과 표로 그린 이 경계를, 다음 시간엔 여러분이 직접 코드로 긋습니다. 회원 가입 API를 만들면서, 방금 관찰한 것처럼 일부러 규칙을 컨트롤러에 뭉쳐 뚱뚱하게 만들었다가, 그걸 서비스로 분리하고, 도메인 예외로 응답까지 완성하는 과정을 손으로 타이핑하고 실행합니다. 오늘 그린 이 두 질문, 지우지 말고 그대로 가져오세요.

**개념 정의**
- 순수 통과형 서비스에 대한 상용구 비판은 실무 논쟁 사항(정답이 정해진 규칙 아님).
- 두 질문의 근거: 변경 이유 격리 = SRP / 재사용 경계 = Service Layer(Fowler).
