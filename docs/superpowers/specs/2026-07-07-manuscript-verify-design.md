# 원고 기술검증 에이전트(manuscript-verify) 설계

**작성일**: 2026-07-07
**대상**: 신규 스킬 `manuscript-verify` (파이프라인 3.5단계, 비차단 온디맨드)
**상태**: 설계 확정 대기(사용자 리뷰)

## 1. 배경 / 문제

확정 원고(`outputs/02_원고/chNN.md`)가 전 파이프라인의 **단일 진실원(SSOT)** — 7개 이상 산출물이 여기서 파생된다. 그런데:

- `manuscript-final` 확정 체크리스트는 **구조만** 본다(8필드 무결성·슬라이드 번호). 기술적 주장의 참/거짓은 검증하지 않는다.
- `Source` 필드는 있으나 품질이 제각각(URL·산문 설명·내부 문서)이고, **"그 Source가 실제로 그 주장을 지지하는지"는 아무도 확인하지 않는다.**
- 기존 검증 장치는 `practice-code`(코드 실행)·`book-build` 편집검토 ①사실성(책 vs 원고 대조)뿐 — **원고의 기술 주장을 외부 권위 근거와 대조해 참/거짓을 판정하는 독립 장치가 없다.**

원고에서 기술 주장이 틀리면 그대로 7개 산출물로 전파된다. 이를 원고 단계에서 잡는 검증 에이전트를 만든다.

## 2. 정체성 / 위치

- **이름**: `manuscript-verify`. 트리거: "원고 검증", "기술 검증", "팩트체크", "사실 확인".
- **위치**: 개념상 3.5단계 — `manuscript-final`(원고확정 ✅) 직후, `visual-assets` 언저리.
- **성격**: **비차단 온디맨드 스킬**. 파이프라인 필수 관문이 아니라, 원고 신뢰도를 높이고 싶을 때 부르는 보증 도구. 하드 게이트가 아니다(처리 방식이 "근거부 리포트"이고 LLM 검증엔 오탐이 있으므로 파이프라인을 막지 않는다).
- **전제**: 대상 차시 `원고확정` ✅. 미확정 원고는 검증하지 않는다(어차피 바뀐다).
- **입력**: `courses/{course-id}/outputs/02_원고/chNN.md`.
- **출력**: `courses/{course-id}/outputs/11_검증/chNN_verify.md`(리포트). `status.md`엔 정보성 한 줄(`원고검증: chNN 리포트 YYYY-MM-DD, 의심 N건`)만 추가 — 하드 게이트 칸 아님.
- **course-pipeline 연계**: 원고확정 후 "검증 돌려볼까요?"로 권유하되 막지 않는다(옵션).
- **원고 자동 수정 금지**: 이 스킬은 리포트만 만든다. 원고 수정은 사용자가 `manuscript-final`로 한다(사용자 확정 SSOT 보호 — `practice-code`의 "역수정은 사용자 승인 후에만" 원칙과 동일).

## 3. 검증 근거

- **주 근거**: 외부 권위 문서 웹 리서치(공식 도큐먼트·MDN·RFC·프레임워크 공식 문서 등). WebSearch/WebFetch로 페치해 대조한다.
- **보조 근거**: 슬라이드의 `Source` 필드 교차확인 — 존재하는지, 권위 있는지, **실제로 그 주장을 지지하는지**.
- **적대적 검증**: 검증자는 회의적 기본값으로 "이 주장을 반박하라"를 수행하고, 근거(인용 가능한 출처) 없이는 "지지"로 판정하지 않는다. 필요 시 독립 검증자 다수결로 검증자 자신의 환각을 억제한다.

## 4. 아키텍처 (3 컴포넌트)

데이터 흐름: `원고 → [추출기] → 주장 리스트 → [검증기 병렬] → 판정들 → [집계기] → 리포트 + 의심 요약`.

### 4.1 주장 추출기 (claim extractor)

- 확정 원고를 슬라이드별로 훑어 **검증 가능한 기술 주장**만 원자 단위로 추출한다. 추출원: Screen의 `핵심 정의`, Narration, 정의성 문장. 슬라이드의 `Source` 필드도 함께 캡처한다.
- 산출 스키마(주장별): `{slide: int, claim_text: str, source_field: str, claim_type: str}`.
- **claim_type**(포함): `정의`(definition) / `프로토콜·표준 사실` / `API·메서드 동작` / `버전·설정 값`.
- **범위 가드(필수)**: **Easy analogy(비유)·의견·교육적 서사·주관적 표현은 추출하지 않는다.** 비유는 의도적으로 단순화한 것이라 "틀렸다"고 판정하면 안 된다.

### 4.2 주장 검증기 (병렬 서브에이전트)

- 슬라이드별로 검증 서브에이전트를 파견한다(한 슬라이드의 1–3개 주장을 묶어 처리 — 에이전트 수 억제). 각 검증자는:
  1. 권위 문서를 웹 리서치해 주장과 대조한다.
  2. 슬라이드 `Source`를 교차확인한다(존재·권위·주장 지지 여부).
  3. 적대적으로 반박을 시도하고, 근거 인용이 있어야만 판정한다.
- 반환 스키마(주장별): `{claim: str, verdict: "지지"|"반박"|"검증불가", confidence: "high"|"medium"|"low", evidence_url: str, evidence_quote: str, source_supports: bool, suggested_correction: str}`.
- **오케스트레이션**: 스킬이 검증 서브에이전트를 병렬 파견하고 구조화된 판정을 수집한다(하네스 기존 서브에이전트 패턴, Workflow opt-in 불필요). 파견 수에 상한을 두고, 상한으로 일부 주장을 못 돌리면 리포트에 **명시**한다(침묵 절단 금지).

### 4.3 리포트 집계기 (report aggregator)

- 판정을 모아 `courses/{course-id}/outputs/11_검증/chNN_verify.md`를 만든다:
  - **요약**: 검증 N건 / 지지 X / 반박 Y(고확신) / 검증불가 Z(사람 판단 필요) / (상한으로) 미검증 W건.
  - **의심 주장 표**: 슬라이드 · 주장 · 판정 · 확신도 · 근거(URL + 인용) · Source 지지 여부 · 수정안.
- **분리 원칙**: "**반박(조치 대상)**"과 "**검증불가(사람 판단 필요)**"를 리포트에서 명확히 분리한다 — 오탐이 조치 목록을 오염시키지 않게. "검증불가"는 오류가 아니라 사람 판단이 필요한 항목이다.
- 의심 요약을 사용자에게 보고한다.

## 5. 수정 루프

1. 사용자가 `outputs/11_검증/chNN_verify.md` 리포트를 검토한다.
2. 고칠 주장을 정한다.
3. `manuscript-final`로 해당 주장을 수정한다(사용자 확정 SSOT 편집).
4. 필요하면 `manuscript-verify`를 다시 돌려 재검증한다(변경된 주장 중심).

## 6. 오탐·비용 가드

- **범위 제한**: 기술 주장(정의·사실·API·버전)만 검증. 비유·의견·서사는 제외(§4.1).
- **적대적 검증**: 회의적 기본값 + 근거 인용 필수 → 환각 판정 억제(§3).
- **확신도 계층**: 근거 인용이 있는 "반박(high)"만 강한 플래그. "검증불가(low)"는 오류가 아니라 사람 판단 항목으로 분리(§4.3).
- **비용**: 슬라이드 단위 배치, 파견 수 상한, 미검증분 리포트 명시(§4.2). 한 차시 주장 수가 많지 않아 Workflow급 병렬은 불필요.
- **비파괴**: 리포트는 원고를 절대 수정하지 않는다(§2).

## 7. 확정 체크리스트 (스킬 실행마다)

- [ ] **전제 게이트**: 대상 차시 `원고확정` ✅. 아니면 중단하고 사용자에게 알린다.
- [ ] **추출 범위**: 리포트에 비유·의견이 기술 주장으로 잘못 올라오지 않았다(§4.1 범위 가드 준수).
- [ ] **근거 첨부**: "반박"·"지지" 판정에는 인용 가능한 근거(URL + 인용문)가 붙어 있다. 근거 없는 판정은 "검증불가"로 내린다.
- [ ] **분리 표기**: 리포트가 "반박(조치)"과 "검증불가(사람 판단)"를 분리했다.
- [ ] **미검증 명시**: 파견 상한 등으로 못 돌린 주장이 있으면 리포트에 명시했다(침묵 절단 없음).
- [ ] **비파괴**: 원고를 수정하지 않았다.

## 8. 유지 규칙 준수

신규 스킬 추가(파이프라인 3.5단계 편입)는 하네스 구조 변경이므로, 구현 전 `docs/history/<날짜_변경>/proposal.md`에 계획을 쓰고 codex 사전검증 결과를 같은 폴더 `codex-review.md`에 저장한 뒤 반영하고 `docs/history/CHANGELOG.md`에 한 줄 추가한다(CLAUDE.md 유지 규칙 R3 · harness-maintain 스킬). CLAUDE.md 파이프라인 표·트리거 라우팅·`course-pipeline` 연계 갱신도 구현 계획에 포함한다.

## 9. 범위 밖

- **최종 산출물(책·PPTX) 검증**: 이 스킬은 원고(SSOT) 단계만 대상. 소비물 검증은 별도.
- **코드 검증 확대**: 코드·명령 동작 검증은 `practice-code`가 담당(실행 검증). 이 스킬은 개념·정의 서술이 대상.
- **원고 자동 수정**: 명시적으로 하지 않는다(§2·§5).
