# 1차시 판서 대본 — 다형성·동적바인딩 워밍업 (그대로 모드)

각 슬라이드는 화면에 이미 떠 있는 PPT프리뷰 캔버스 그대로다. "판서"는 그 위에 펜으로 덧그릴 강조·부연이고, "대본"은 실제로 할 말이다.

---

## 슬라이드 1 — 다형성·동적바인딩 워밍업 (표지)
판서:
표지 부제 "한 가지 원리"에 밑줄. 우측 자동차 이미지 위에 "하나 → 둘" 화살표를 크게 하나 그어 준다.
대본:
안녕하세요. 유지보수성 향상을 위한 디자인패턴 과정의 첫 시간입니다. 오늘 주제는 다형성과 동적바인딩입니다. "패턴 배우러 왔는데 왜 문법 복습부터 하지?" 싶으실 수 있어요. 그런데 앞으로 배울 열여섯 개 차시의 모든 패턴은 단 하나의 원리 위에 서 있습니다. 상위 타입의 참조로 하위 구현을 다루면, 실행 시점에 실제 객체의 메서드가 선택된다는 원리죠. 운전면허를 생각해 보세요. 면허 하나로 소나타도 몰고 제네시스도 몹니다. "자동차라면 이렇게 움직인다"는 공통 규격만 알면 되는 거예요. 오늘은 이 쉬운 자동차 예제로 그 원리를 완전히 소화하는 준비운동을 하겠습니다.
개념 — 다형성(Polymorphism):
같은 상위 타입의 참조로 서로 다른 하위 구현의 동작을 호출할 수 있는 성질. "운전면허 하나로 여러 차종을 몬다"가 그 비유.
참고: Oracle Java Tutorials – Polymorphism.

## 슬라이드 2 — 패턴 책이 어려운 이유는 패턴이 아니라 다형성이다
판서:
우측 이미지의 "인터페이스 → 구현" 화살표를 펜으로 굵게 덧그리고, 그 옆 물음표에 동그라미. 왼쪽 목록 "암기 과목"에 밑줄.
대본:
본격적으로 들어가기 전에, 왜 이 과정이 패턴이 아니라 워밍업으로 시작하는지 말씀드릴게요. 디자인 패턴 책이 어렵게 느껴지는 이유는 대부분 패턴 자체가 아닙니다. 다이어그램의 저 화살표, "구체 클래스가 아니라 추상에 의존한다"는 관계가 코드에서 실제로 어떻게 동작하는지 몸으로 확신하지 못하기 때문이에요. 수영으로 치면 접영을 배우기 전에 물에 뜨는 법부터 확실히 하는 것과 같습니다. 뜨는 법이 불안하면 어떤 영법도 무섭거든요. 인터페이스 타입 변수에 구현 객체를 담았을 때 어떤 메서드가 실행되는가, 그 선택은 언제 일어나는가. 여기에 즉답할 수 있으면 패턴은 암기가 아니라 추론의 대상이 됩니다.

## 슬라이드 3 — 오늘은 "한 문장"을 코드로 증명한다
판서:
목표 세 개 앞에 각각 번호 동그라미 1·2·3을 그린다. 세 번째 "직접 구현" 항목에 별표 강조.
대본:
오늘의 학습 목표는 세 가지입니다. 첫째, 다형성이 무엇인지 설명할 수 있어야 합니다. 정의를 외우는 게 아니라, 상위 타입 참조 하나로 서로 다른 하위 구현을 다룬다는 게 코드에서 어떤 모습인지 말할 수 있어야 해요. 둘째, 동적바인딩의 동작 원리를 설명할 수 있어야 합니다. 부모 타입 변수로 호출했는데 왜 자식 메서드가 실행되는지, 그 선택이 언제 일어나는지를 다룹니다. 셋째, 직접 구현할 수 있어야 합니다. 리모컨 하나로 어느 회사 TV든 켠다는 걸 말로만 아는 게 아니라, 리모컨을 직접 분해해 버튼과 신호가 어떻게 연결되는지 확인하는 거예요. 오늘은 꼭 끝까지 직접 타이핑해 보시길 권합니다.

## 슬라이드 4 — 다형성 = 하나의 타입, 여러 개의 모습
판서:
`Car s = new Sonata();`에서 왼쪽 Car에 밑줄(타입), 오른쪽 Sonata에 동그라미(실제 객체), 둘을 잇는 화살표. 이미지의 주차 구역 라벨 "Car"를 덧써 강조.
대본:
다형성은 "여러 형태를 가진다"는 뜻입니다. Java에서는 아주 구체적인 한 줄로 나타나요. `Car s = new Sonata();` 변수 s의 타입은 Car인데, 실제로 만들어진 객체는 Sonata입니다. 부모 타입 변수에 자식 객체를 담은 거죠. 소나타는 자동차의 일종이니까 자동차라고 불러도 거짓이 아니라서 Java가 허용합니다. 호텔 발레파킹을 떠올려 보세요. 주차권에는 그냥 "고객 차량"이라 적혀 있지만, 그 주차권으로 나오는 차는 손님마다 다릅니다. 주차권이 참조 변수, 실제 차가 객체예요. 실무에서 이게 중요한 이유는 변경 비용입니다. 코드가 구체 클래스가 아니라 상위 타입에 의존하면, 나중에 구현을 바꾸거나 추가할 때 호출하는 쪽을 안 건드려도 되거든요.

## 슬라이드 5 — 추상 타입은 약속만, 구현 타입은 내용을
판서:
상단 점선 설계도 Car 옆 "new 금지"에 X 표시를 덧그린다. Car에서 Sonata·Genesis로 내려오는 두 화살표를 굵게.
대본:
예제 코드를 구조부터 볼게요. Car는 abstract, 추상 클래스입니다. 그 안의 run도 abstract라 몸통이 없어요. "자동차라면 달릴 수 있어야 한다"는 약속만 있고, 어떻게 달리는지는 안 적혀 있는 상태죠. 그래서 Car는 new로 직접 만들 수 없습니다. 프랜차이즈 본사의 매장 운영 매뉴얼을 생각하시면 돼요. 매뉴얼은 규칙을 정하지만 매뉴얼 자체가 손님을 받지는 못합니다. 실제 장사는 매뉴얼대로 문을 연 매장이 하죠. 여기서 그 매장이 Sonata와 Genesis입니다. 둘은 Car를 extends 하면서 run의 내용을 각자 채웁니다. 약속은 하나인데 내용은 둘, 이 구조가 다형성의 무대 장치입니다.
개념 — 추상 클래스(abstract class):
인스턴스화할 수 없고, 추상 메서드는 선언만 두고 구현은 하위 클래스가 제공한다. "본사 매뉴얼(약속) vs 실제 매장(구현)"의 분리.
참고: Oracle Java Tutorials – Abstract Methods and Classes.

## 슬라이드 6 — @Override — 같은 서명, 새로운 내용
판서:
`@Override`에 동그라미. 이미지의 "자식 메서드가 부모 위에 도장처럼 찍히는" 부분에 아래로 향하는 화살표를 하나 덧그려 "덮어쓴다"를 강조.
대본:
다음 열쇠는 재정의, 오버라이드입니다. Sonata는 부모 Car에게 물려받은 run을 같은 이름, 같은 매개변수, 같은 반환 타입으로 다시 작성했어요. 서명이 완전히 일치하는 메서드를 자식이 다시 정의하면, 그 객체에서는 자식 버전이 부모 버전을 대신합니다. 회사 표준 근무 규정과 팀 규정의 관계를 생각하시면 쉬워요. 팀 규정이 같은 항목을 다시 정했다면 그 팀 안에서는 팀 규정이 우선하죠. 코드 위의 @Override는 동작을 바꾸지 않습니다. 대신 "이 메서드는 부모 것을 재정의한 게 맞다"고 컴파일러에게 선언해서, 철자를 틀리거나 매개변수를 다르게 써서 재정의에 실패하면 컴파일 오류로 즉시 알려 줍니다. 실무에서는 재정의 의도가 있는 메서드에 반드시 붙이는 관례입니다.
개념 — 오버라이드(Overriding):
하위 클래스가 상위와 동일한 서명의 인스턴스 메서드를 정의해 상위 메서드를 재정의하는 것. @Override로 컴파일러 검사를 받는다.
참고: Oracle Java Tutorials – Overriding and Hiding Methods.

## 슬라이드 7 — 호출할 메서드는 "실행 시점의 실제 객체"가 결정한다
판서:
`s.run()` 호출 화살표가 Car의 흐릿한 run을 지나쳐 Sonata의 run에 도착하는 흐름을 펜으로 이어 그린다. 부모 run에는 빗금(무효화), 도착점에는 동그라미.
대본:
이제 오늘의 핵심, 동적바인딩입니다. `Car s = new Sonata();` 다음 `s.run()`을 호출하면 무슨 일이 벌어질까요? 컴파일러는 변수 s의 타입 Car를 보고 "Car에 run이 선언돼 있는가"만 확인합니다. 여기까지가 컴파일 시점의 일이에요. 그런데 어떤 run을 실행할지는 이때 확정되지 않습니다. 프로그램이 실제로 돌아가는 실행 시점에, s가 가리키는 실제 객체가 무엇인지 보고 그 객체의 메서드가 선택됩니다. 지금 s가 가리키는 건 Sonata니까 Sonata의 run이 호출되죠. 대표번호 비유를 기억해 주세요. 거는 쪽은 늘 같은 번호를 누르지만 받는 사람은 그때그때의 당번 담당자입니다. 이 "늦은 결정" 덕분에 호출하는 코드는 그대로 두고 실행되는 내용만 바꿔 끼우는 설계가 가능해지고, 그게 바로 디자인 패턴이 하는 일의 전부입니다.
개념 — 동적바인딩(가상 메서드 호출):
JVM이 변수의 타입이 아니라 참조된 실제 객체에 맞는 메서드를 실행 시점에 선택하는 것. "대표번호는 같아도 받는 당번은 그때그때 다르다."
참고: Oracle Java Tutorials – Polymorphism.

## 슬라이드 8 — 한눈에 보는 전체 코드: 정의부 + 실행부
판서:
왼쪽 정의부 이미지의 `abstract void run();`에 밑줄. 오른쪽 실행부 이미지의 `s.run()`과 `g.run()`을 각각 동그라미로 묶고, 두 동그라미가 "같은 모양인데 결과가 다르다"는 걸 양쪽 화살표로 연결.
대본:
이제 실습할 파일 전체를 처음부터 끝까지 읽어 보겠습니다. 파일은 ex01 패키지에 있고 이름은 Mem02예요. 위에서부터 보면, 추상 클래스 Car가 run이라는 추상 메서드 하나를 약속하고, Sonata와 Genesis가 Car를 상속받아 각자의 run을 재정의합니다. main을 보시죠. `Car s = new Sonata();`로 부모 타입 변수에 소나타 객체를 담고 `s.run()`을 호출하면 "소나타 달린다"가, 이어서 `Car g = new Genesis();`와 `g.run()`은 "제네시스 달린다"가 출력됩니다. 여기서 주목할 점. `s.run()`과 `g.run()`은 호출 코드만 봐서는 무엇이 실행될지 구분할 수 없어요. 결과를 결정하는 건 호출 코드가 아니라 변수에 담긴 객체입니다. 같은 리모컨 버튼을 두 번 눌렀는데 첫 번째는 거실 TV가, 두 번째는 안방 TV가 켜진 상황이죠. 스물다섯 줄짜리 이 작은 파일이 이후 모든 패턴의 원리를 전부 담고 있습니다.

## 슬라이드 9 — 패턴 = "다형성을 어디에 쓸 것인가"에 대한 검증된 답
판서:
신전 이미지의 주춧돌 "다형성·동적바인딩"에 밑줄. 그 위 기둥들(전략·프록시·옵저버…)을 아래 주춧돌과 잇는 화살표를 하나씩 그어 "모두 같은 뿌리"를 강조.
대본:
이제 오늘 내용과 과정 전체를 연결해 볼게요. 디자인 패턴이란 무엇일까요? 저는 이렇게 정의하고 싶습니다. "다형성을 어디에, 어떻게 쓸 것인가"라는 질문에 선배 개발자들이 검증해 둔 답안지입니다. 전략 패턴은 자주 바뀌는 행위를 추상 타입 뒤로 분리해 갈아 끼우는 답이고, 프록시 패턴은 같은 추상 타입 뒤에 대리자를 세워 접근을 제어하는 답이에요. 옵저버, 팩토리, 데코레이터도 모두 "구체가 아니라 추상에 의존하고, 실행 시점에 실제 구현이 선택된다"는 오늘의 원리를 각자의 문제에 적용한 겁니다. 콘센트 비유가 정확해요. 규격이 통일돼 있으니 어떤 가전이든 꽂을 수 있고, 멀티탭이나 타이머 콘센트 같은 응용 상품도 그 규격 위에서 성립하죠. 요즘 Java는 전략 클래스를 따로 안 만들고 람다로 동작을 바로 넘기기도 하는데, "호출부를 고정하고 동작을 바꿔 끼운다"는 발상의 뿌리는 여전히 다형성입니다.

## 슬라이드 10 — 16차시 전체 지도 — 오늘은 출발선이다
판서:
로드맵 이미지의 출발점(ch01)에 크게 동그라미와 "여기!" 표시. 마지막 봉우리(리플렉션)에 깃발을 하나 그려 목적지 강조.
대본:
오늘이 준비운동이라고 했으니, 앞으로 어떤 산을 오를지 지도를 함께 볼게요. 다음 시간에는 캡슐화와 SOLID, 특히 개방-폐쇄 원칙으로 "좋은 설계란 무엇인가"의 기준을 세웁니다. 그다음부터 본격적인 패턴 여정이에요. 변하는 행위를 갈아 끼우는 전략, 대리자를 세우는 프록시, 호환되지 않는 걸 이어 붙이는 어댑터, 유일한 인스턴스를 보장하는 싱글톤을 지나, 템플릿 메서드와 위임, 옵저버와 데코레이터로 이어집니다. 목 객체 차시에서 테스트 가능한 구조를 만들고, AI 프렌들리 병렬개발, 팩토리 두 차시, 리팩토링 종합을 거쳐, 마지막 열여섯 번째 시간에는 리플렉션으로 프레임워크의 축소판을 직접 만드는 피날레에 도착합니다. 등산 안내도 같은 거예요. 오늘은 입구의 준비운동 광장입니다. 이 모든 정거장을 관통하는 문장이 하나 있어요. 모든 패턴은 다형성 위에 서 있다.

## 슬라이드 12 — 직접 타이핑 → ▶ Run 클릭
판서:
우측 코드에서 `Car s = new Sonata();`와 `s.run()`에 밑줄. 나중에 확인 실험할 부분 `new Sonata()`를 동그라미로 묶어 "여기만 Genesis로 바꿔 볼 것" 메모.
대본:
이제 직접 만들어 봅니다. 탐색기에서 src 폴더, 그 아래 ex01 폴더, 그 안에 Mem02.java를 만드세요. 첫 줄 package ex01 선언과 폴더 구조가 일치해야 한다는 것, 잊지 마시고요. 코드가 짧으니 복사해 붙이지 말고 한 줄씩 직접 타이핑하시길 권합니다. 악보를 눈으로 읽는 것과 직접 연주하는 건 다르거든요. 타이핑하면서 "이 줄은 약속을 정하는 줄, 이 줄은 약속을 채우는 줄, 이 줄은 부모 타입에 자식 객체를 담는 줄"이라고 속으로 말해 보면 구조가 훨씬 빨리 붙습니다. 작성이 끝나면 main 위에 뜨는 작은 Run 버튼을 누릅니다. 누르기 전에 출력이 어떻게 나올지 먼저 예측해 보세요. 예측하셨으면 실행. "소나타 달린다"와 "제네시스 달린다"가 차례로 나오면 성공입니다. 같은 모양의 run 호출 두 번이 서로 다른 문장을 냈다면, 방금 동적바인딩을 직접 증명하신 거예요.

## 슬라이드 13 — 과제 — 추상 타입 1개 + 구현 타입 2개
판서:
조건 세 개에 번호 동그라미. 세 번째 "main은 반드시 부모 타입 변수로 호출"에 굵은 밑줄과 별표(가장 흔히 틀리는 지점). 예시 구조도 Animal←Dog/Cat 화살표 덧그리기.
대본:
이제 오늘의 과제입니다. 방금 만든 자동차 예제와 똑같은 구조를, 이번에는 여러분이 고른 도메인으로 처음부터 직접 설계해 보세요. 동물이 좋다면 추상 클래스 Animal에 소리 내는 추상 메서드를 두고 Dog와 Cat이 각자 재정의하면 됩니다. 도형이면 Shape와 Circle, Rect로 넓이를 구해도 좋고, 알림이면 Notifier와 Email, Sms도 좋아요. 도메인은 자유입니다. 요리 학원에서 시범 요리를 본 다음 같은 조리법으로 재료만 바꿔 만드는 단계라고 보시면 돼요. 다만 세 조건은 꼭 지켜 주세요. 첫째, 추상 클래스에 추상 메서드 하나 이상. 둘째, 구현 클래스 두 개가 각자 다르게 재정의. 셋째, 이게 제일 중요한데, main에서 반드시 부모 타입 변수에 자식 객체를 담아 호출해야 합니다. 자식 타입 변수로 호출하면 돌아가긴 하지만 오늘 배운 다형성의 증명이 아니에요. 과제 코드는 ex01 폴더 아래 example 폴더를 만들어 그 안에, 패키지 선언은 ex01.example로 작성합니다. 시간은 30분에서 1시간 드릴게요.

## 슬라이드 14 — 상위 타입으로 다루고, 실행 시점에 선택된다
판서:
4단 요약 카드 네 개를 잇는 하단 기준선(주춧돌)에 밑줄. 마지막 문장 "모든 패턴은 다형성 위에 서 있다"에 굵은 밑줄.
대본:
오늘 내용을 정리하겠습니다. 다형성은 부모 타입 참조 변수에 자식 객체를 담아 하나의 타입으로 여러 구현을 다루는 것입니다. 추상 클래스 Car는 run이라는 약속만 정하고 스스로는 객체가 될 수 없었죠. Sonata와 Genesis는 그 약속을 각자의 내용으로 재정의했고, 재정의된 순간 그 객체 안에서 부모의 run은 무효화됩니다. 그리고 어떤 run이 실행될지는 컴파일 시점이 아니라 실행 시점에, 변수가 아니라 실제 객체를 기준으로 선택됩니다. 이게 동적바인딩이에요. 이 네 가지를 한 문장으로 줄이면 이렇게 됩니다. 상위 타입으로 다루고, 실행 시점에 선택된다. 이 문장이 이 과정 열여섯 차시 전체를 받치는 주춧돌입니다. 다음 시간에는 캡슐화와 SOLID, 특히 개방-폐쇄 원칙을 배웁니다. 오늘 과제 꼭 완성해 오시고, 가능하면 팀 코드에서 추상 타입으로 선언된 변수를 세 군데만 찾아보시길 권합니다. 수고하셨습니다.

## 슬라이드 15 — 평가하기 (사지선다)
판서:
문제의 `Car s = new Sonata(); s.run();`에 밑줄. 정답 1번 보기 앞에 동그라미. 4번 보기 "컴파일 시점"에 빗금(출력은 맞지만 이유가 틀림).
대본:
첫 번째 평가는 오늘의 핵심인 동적바인딩을 확인하는 문제입니다. 정답은 1번이에요. 부모 타입 변수 s에 Sonata 객체를 담고 run을 호출하면, 실행 시점에 실제 객체 Sonata가 재정의한 run이 선택돼 "소나타 달린다"가 출력됩니다. 2번은 틀렸습니다. 부모 타입 변수에 자식 객체를 담는 건 Java가 허용하는 다형성의 기본이에요. 3번도 틀렸어요. 변수 타입이 Car라고 추상 메서드가 호출되는 게 아니라, 실제 객체의 재정의된 메서드가 호출됩니다. 4번은 출력은 맞지만 이유가 틀렸습니다. 어떤 run을 실행할지는 컴파일 시점이 아니라 실행 시점에 실제 객체를 보고 선택됩니다. 바로 그래서 "동적" 바인딩이에요. 출력만 맞히는 게 아니라 이유까지 정확히 고르는 게 이 문제의 핵심입니다.

## 슬라이드 16 — 평가하기 (진위형: 상위 타입 참조에 하위 객체)
판서:
O 보기에 동그라미. 큰 원(Car) 안에 작은 원 둘(Sonata·Genesis)을 그려 포함 관계를 판서로 재현.
대본:
두 번째 문제는 다형성의 출발점을 확인합니다. 정답은 O입니다. 자식 클래스의 객체는 부모 타입의 일종이므로, 부모 타입의 참조 변수에 담을 수 있어요. 오늘 예제의 `Car s = new Sonata();`가 정확히 이 문장의 코드 형태입니다. 여러분이 실무에서 매일 쓰는 `List<String> list = new ArrayList<>();`도 같은 원리예요. 발레파킹 주차권에 "고객 차량"이라 적혀 있으면 소나타든 제네시스든 맡길 수 있는 것과 같습니다. 다만 반대 방향은 성립하지 않는다는 점도 함께 기억해 주세요. 자식 타입 변수에 부모 객체를 그냥 담을 수는 없습니다.

## 슬라이드 17 — 평가하기 (진위형: 컴파일 시점에 부모 메서드 확정?)
판서:
문제 문장의 "컴파일 시점에 최종 결정"에 빗금. X 보기에 동그라미. 옆에 "컴파일 = 존재 확인 / 실행 = 실제 객체 선택" 두 줄을 짧게 판서.
대본:
세 번째 문제의 정답은 X입니다. 컴파일 시점에 변수의 선언 타입으로 확인하는 건 "그 타입에 해당 메서드가 존재하는가"까지예요. 실제로 어떤 메서드가 실행될지는 실행 시점에 변수가 가리키는 실제 객체를 기준으로 선택됩니다. 자식이 재정의했다면 자식의 메서드가 실행되죠. 오늘 예제에서 s의 선언 타입은 Car였지만 실행된 건 Sonata의 run이었다는 걸 직접 확인하셨습니다. 만약 이 문장이 O라면, 그러니까 컴파일 시점에 부모 메서드로 고정된다면, 구현을 갈아 끼우는 전략 패턴도, 대리자를 끼우는 프록시 패턴도, 프레임워크가 우리 코드를 호출하는 일도 전부 불가능해집니다. 동적바인딩의 "동적"이 실행 시점을 뜻한다는 걸 기억해 주세요.
