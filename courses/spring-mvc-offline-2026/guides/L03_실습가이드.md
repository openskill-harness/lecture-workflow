# L03 실습 가이드 — 회원 가입 API를 요청 매핑부터 응답까지 직접 구현하기

> 대상: spring-mvc-offline-2026 / L03 (LAB, 85분) · 학습목표 goal[2] "기본 Controller를 직접 구현·실행"
> 힌트 수위: **B(중간)** — 무엇을·어떤 도구로 만들지는 알려주되, 어떻게 조립할지는 여러분이 결정합니다. 완성 코드는 이 가이드에 없습니다.

이 가이드는 강사 설명 없이도 혼자 읽고 시작할 수 있도록 쓰였습니다. 순서대로 따라오면 됩니다.

## 0. 시작 전에 (오리엔테이션 · 8분)

### 0-1. 환경 전제
아래가 준비되어 있어야 합니다. 없으면 강사에게 알리세요.

| 항목 | 요구 | 확인 방법 |
|---|---|---|
| JDK | **Java 21** (OpenJDK 21) | 터미널에서 `java -version` → `21` 표시 |
| IDE | **IntelliJ IDEA** | 프로젝트 열기 가능 |
| 빌드 | Gradle Wrapper 8.14.x (프로젝트에 포함, 별도 설치 불필요) | `gradlew.bat` 파일 존재 |
| 네트워크 | 최초 1회 의존성 내려받기 필요 | 배부 시 강사가 오프라인 캐시 안내 |

### 0-2. 사전 지식 (있다고 가정)
- Spring Boot로 CRUD API를 한 번이라도 만들어 봤다.
- HTTP 메서드(GET/POST)와 상태 코드(200/404/500) 개념을 안다.
- JSON 요청/응답이 무엇인지 안다.

> DispatcherServlet 내부 구조는 몰라도 됩니다. 이번 실습은 "요청이 컨트롤러 메서드에 어떻게 도착하고, 어떤 모양으로 응답이 나가는가"를 손으로 만들어 보는 것입니다.

### 0-3. 여러분이 만드는 것 / 이미 준비된 것
starter 프로젝트에는 회원 가입에 필요한 **주변 요소가 이미 배치**되어 있습니다. 여러분이 직접 타이핑하는 것은 **딱 두 개**입니다: `MemberController`, `MemberService`(+ 마지막 단계의 예외 클래스 하나).

**이미 배치됨 (열어보되 타이핑하지 않음):**
- `Member.java` — 회원 도메인(`record`). `id`는 저장 시 저장소가 채웁니다(신규 저장 전 `null`).
- `MemberRepository.java` — in-memory 저장소. `save(member)`, `existsByEmail(email)`, `findById(id)` 세 메서드 제공.
- `SignUpRequest.java` — 요청 DTO(`record`, 필드: `email`, `name`).
- `SignUpResponse.java` — 응답 DTO(`record`, 필드: `id`, `email`).
- `MemberApplication.java`, `build.gradle`, `settings.gradle`, `application.properties`(포트 8080).

**여러분이 만드는 것:**
- `MemberController.java` (Step 1~5에 걸쳐 작성·수정)
- `MemberService.java` (Step 4에서 신규)
- `DuplicateEmailException.java` (Step 5에서 신규)

패키지는 전부 `com.example.member` 입니다. 새 파일은
`src/main/java/com/example/member/` 아래에 만듭니다.

> PowerShell에서 위 curl 따옴표가 말썽이면, 요청 본문을 파일(`body.json`)로 저장하고 `-d "@body.json"` 로 보내는 방법이 가장 안전합니다.

## 2. 전체 흐름 지도

5단계는 하나의 문장을 완성해 갑니다:

```
POST /members 요청 도착
   │  (Step 1: 요청 매핑 — 이 URL이 오면 내 메서드를 실행하라)
   ▼
JSON 본문을 SignUpRequest로 받음
   │  (Step 2: DTO 바인딩 — 입구는 도메인이 아니라 요청 DTO)
   ▼
가입 규칙 판단(이메일 중복?)
   │  (Step 3: 일단 컨트롤러 안에서 — 의도적으로 "잘못된 상태")
   │  (Step 4: 규칙을 MemberService로 분리 — 변경 이유를 나눈다)
   ▼
결과를 HTTP 상태로 응답
      (Step 5: 성공 201 Created / 중복 409 Conflict + 응답 DTO)
```

각 단계 끝에는 **실행 확인(run_check)** 이 있습니다. 통과하면 손을 들어 강사 체크인을 받고 다음으로 넘어갑니다.

### Step 1 — 요청 매핑 (약 8분)
**대응 스냅샷:** `01-request-mapping/`

- **목표:** `POST /members` 요청이 여러분이 만든 자바 메서드에 도달하게 한다.
- **할 일:**
  - `MemberController` 클래스를 새로 만들고 `@RestController` 를 붙인다.
  - `@PostMapping("/members")` 메서드를 하나 만들어, 지금은 **고정 문자열**을 반환한다(본문 내용은 아직 신경 쓰지 않는다).
- **완료 기준:** `POST /members` 호출 시 **404가 아니라 200**이 나오고, 반환한 고정 문자열이 응답 본문에 보인다.
- **힌트(B):** 매핑은 "이 URL·이 메서드가 오면 이 자바 메서드를 실행하라"는 **선언**입니다. `@RestController` / `@PostMapping` **철자와 경로(`/members`)** 오타를 조심하세요 — 매핑이 안 잡히면 여전히 404입니다.
- **막히면:** 위 3분 룰 → 대조용으로 `01-request-mapping/` 열람.

---

### Step 2 — 요청/응답 데이터 흐름: DTO 바인딩 (약 14분, 가장 밀도 높음)
**대응 스냅샷:** `02-request-response-dto/`

- **목표:** JSON 본문을 요청 DTO로 받아 저장하고, 응답 DTO로 돌려준다.
- **할 일:**
  - `MemberController` 가 `MemberRepository` 를 **생성자 주입**으로 받는다.
  - `@RequestBody` 로 JSON 본문을 `SignUpRequest` 로 받는다.
  - 받은 값으로 `Member` 를 만들어 `save` 하고, 그 결과를 `SignUpResponse`(필드: `id`, `email`)로 변환해 응답한다. **도메인 `Member` 를 그대로 반환하지 않는다.**
- **완료 기준:** `{"email","name"}` JSON을 보내면 저장되고, 응답은 `{"id","email"}` 모양으로 나온다.
- **힌트(B) — 흔한 오류 3가지 경고:**
  1. **생성자 주입 누락:** 필드만 선언하고 생성자를 안 만들면 실행 시 `NullPointerException`(저장소가 `null`). 필드에 `new` 로 직접 만들지 말 것.
  2. **`@RequestBody` 누락:** 어노테이션 없이 파라미터만 선언하면 `email`/`name` 이 전부 `null` 로 들어옵니다(저장은 되는데 값이 비어 있음).
  3. **DTO/도메인 혼용:** 요청을 `Member` 로 받거나 응답으로 `Member` 를 그대로 내보내면 `name` 까지 노출되거나 클라이언트가 `id` 를 넣게 됩니다. 입구/출구는 **전용 DTO**입니다.
- **막히면:** 3분 룰 → 대조용으로 `01-request-mapping/`(직전) 또는 `02-request-response-dto/` 열람.

---

### Step 3 — 가입 규칙을 컨트롤러 안에 넣기 (의도적 fat controller, 약 10분)
**대응 스냅샷:** `03-fat-controller/`

- **목표:** 저장 전에 이메일 중복을 검사하는 규칙을 넣는다. **단, 이번엔 일부러 컨트롤러 안에** 둔다.
- **할 일:**
  - 저장 전에 `memberRepository.existsByEmail(...)` 로 중복을 검사한다.
  - 중복이면 예외를 던진다 — **이 시점엔 `IllegalStateException`**(그래서 응답은 500으로 나갑니다).
- **완료 기준:** 같은 이메일로 두 번 가입하면 두 번째는 막힌다(**단, 500** 으로 나감 — 다음 단계에서 다듬습니다).
- **왜 이렇게 하나(중요):** 지금 코드는 **동작합니다**. 그런데 컨트롤러가 "요청 수신"과 "가입 규칙 판단"을 동시에 떠안았습니다. L02에서 배운 **책임 경계가 무너진 상태**입니다. 이 단계는 다음 단계의 *before*로서 **일부러 잘못된 상태를 만드는** 것입니다.
- **힌트(B):** "동작하는데 왜 나눠요?"라는 생각이 들면 정상입니다. 지금 나누라는 게 아니라, 다음 단계에서 나눌 **이유를 몸으로 느끼는** 단계입니다. 변경 이유(웹 형식 vs 가입 규칙)가 한 클래스에 섞였다는 점만 기억하세요.
- **막히면:** 3분 룰 → 대조용으로 `03-fat-controller/` 열람.

---

### Step 4 — 책임 분리: 가입 규칙을 MemberService로 옮기기 (약 14분, 생략 불가)
**대응 스냅샷:** `04-service-extracted/`

- **목표:** 중복 검사 + 저장 로직을 `MemberService` 로 옮기고, 컨트롤러는 요청 수신·응답 변환만 하게 만든다.
- **할 일:**
  - `@Service` `MemberService` 를 새로 만들고, Step 3의 **중복 검사 + 저장 로직을 그대로 옮긴다**(복제가 아니라 **이동**).
  - 컨트롤러는 `MemberService` 를 주입받아 위임한다.
  - 컨트롤러가 **더 이상 `MemberRepository` 를 직접 알지 않게** 한다(컨트롤러에서 `existsByEmail` 호출을 지운다).
- **완료 기준:** 동작은 Step 3과 **동일**(중복이면 여전히 500). 바뀐 것은 코드의 **책임 분포**뿐이다.
- **힌트(B) — 흔한 오류 2가지 경고:**
  1. **이동이 아니라 복제:** 컨트롤러에서 로직을 **지우지 않고** 서비스에 복붙하면 검사가 이중으로 됩니다. 옮겼으면 원래 자리는 비웁니다.
  2. **Repository 잔존:** 서비스를 만들고도 컨트롤러가 `MemberRepository` 를 계속 참조하면 분리가 안 된 것입니다. 컨트롤러의 의존은 이제 `MemberService` 하나여야 합니다.
- **핵심 개념:** 분리는 파일을 늘리는 게 아니라 **변경 이유를 나누는 것**입니다. 웹 형식이 바뀌면 Controller만, 가입 규칙이 바뀌면 Service만 고칩니다.
- **막히면:** 3분 룰 → 대조용으로 `03-fat-controller/`(직전) 또는 `04-service-extracted/` 열람.

---

### Step 5 — 응답까지 완성: 성공 201 / 중복 409 (약 18분)
**대응 스냅샷:** `final/`

- **목표:** 결과의 의미를 **HTTP 상태 코드**로 담는다 — 성공은 201 Created, 중복은 409 Conflict.
- **할 일:**
  - `DuplicateEmailException`(예: `RuntimeException` 상속)을 새로 만든다.
  - 서비스가 중복 시 `IllegalStateException` 대신 **`DuplicateEmailException`** 을 던지게 바꾼다.
  - 컨트롤러가 성공을 **`ResponseEntity` 201**(`HttpStatus.CREATED`)로 응답한다.
  - 컨트롤러의 `@ExceptionHandler` 로 `DuplicateEmailException` 을 잡아 **409**(`HttpStatus.CONFLICT`)로 매핑한다.
- **완료 기준:** 신규 가입 → **201** + 응답 DTO(`{"id","email"}`) / 같은 이메일 재요청 → **409**.
- **힌트(B) — 흔한 오류 2가지 경고:**
  1. **예외 타입 불일치:** 서비스가 여전히 `IllegalStateException` 을 던지면 `@ExceptionHandler(DuplicateEmailException)` 가 **매칭되지 않아 계속 500** 입니다. 던지는 타입과 잡는 타입을 맞추세요.
  2. **상태 코드/import 혼동:** `HttpStatus.CREATED(201)` / `CONFLICT(409)` import 누락, `ResponseEntity` 미사용을 주의하세요.
- **핵심 개념:** "응답까지"의 마지막 조각은 상태 코드입니다 — 응답은 데이터만이 아니라 **결과의 의미**를 담습니다.
- **막히면:** 3분 룰 → 대조용으로 `04-service-extracted/`(직전) 또는 `final/` 열람.

## 4. 최종 실행 검증 (회고 · 8분)

앱을 다시 띄우고 아래 두 요청으로 완성을 확인합니다(검증 로그와 동일 시나리오).

```
# 1) 신규 가입 → 201 기대
curl -i -X POST http://localhost:8080/members -H "Content-Type: application/json" -d "{\"email\":\"alice@example.com\",\"name\":\"Alice\"}"

# 2) 같은 이메일 재요청 → 409 기대
curl -i -X POST http://localhost:8080/members -H "Content-Type: application/json" -d "{\"email\":\"alice@example.com\",\"name\":\"Alice2\"}"
```

기대 결과:
- 1번 → `HTTP/1.1 201`, 본문 `{"id":1,"email":"alice@example.com"}`
- 2번 → `HTTP/1.1 409`, 본문에 중복 안내 메시지

> 다른 이메일(`bob@example.com`)로 한 번 더 보내면 `201` 과 `id:2` 가 나옵니다(선택 확인).
