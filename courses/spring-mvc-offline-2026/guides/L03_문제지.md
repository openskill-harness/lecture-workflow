# L03 문제지 — 회원 가입 API 직접 구현

> 과제: starter 프로젝트에서 시작해 `MemberController` 와 `MemberService`(+ 예외 클래스)를 직접 작성하여, `POST /members` 요청이 도착해 규칙을 판단하고 HTTP 상태로 응답하기까지의 한 흐름을 완성하시오.
> 이 문제지는 **무엇을 만족해야 하는가(요구사항)** 만 규정합니다. **어떻게 조립할지는 여러분이 결정**합니다. 막히면 실습 가이드(`L03_실습가이드.md`)의 3분 룰과 스냅샷 대조를 사용하세요.

- **시작점:** `courses/spring-mvc-offline-2026/code/L03/00-starter`
- **직접 작성:** `MemberController.java`, `MemberService.java`, `DuplicateEmailException.java` (패키지 `com.example.member`)
- **사전 배치(수정·타이핑 금지):** `Member`, `MemberRepository`(`save`/`existsByEmail`/`findById`), `SignUpRequest(email,name)`, `SignUpResponse(id,email)`
- **평가:** 루브릭 **RUBRIC-L03**. 각 요구(R)는 아래 "완료 기준"으로 확인합니다.

---

## Step 1 — 요청 매핑
**요구사항**
- R1-1. `POST /members` 요청을 처리하는 컨트롤러 진입점이 존재한다.
- R1-2. 해당 진입점은 요청을 받아 응답을 반환한다(이 단계에서는 응답 본문 내용은 평가하지 않음).

**완료 기준**
- `POST /members` 호출 시 **404가 아닌 200** 이 반환된다.

---

## Step 2 — 요청/응답 데이터 흐름 (DTO 바인딩)
**요구사항**
- R2-1. JSON 요청 본문을 **`SignUpRequest`** 로 받는다.
- R2-2. 컨트롤러가 저장소 의존성을 **생성자 주입**으로 확보한다(필드 직접 생성 금지).
- R2-3. 받은 데이터를 저장한 뒤, 응답은 **`SignUpResponse`(`id`, `email`)** 로 돌려준다. 도메인 `Member` 를 입력 또는 출력에 그대로 사용하지 않는다.

**완료 기준**
- `{"email": "...", "name": "..."}` 를 보내면 저장되고, 응답이 `{"id": ..., "email": "..."}` 모양으로 반환된다(응답에 `name` 이 노출되지 않는다).

---

## Step 3 — 가입 규칙 (의도적 fat controller)
**요구사항**
- R3-1. 저장 전에 이메일 **중복 여부를 검사**한다(`existsByEmail` 활용).
- R3-2. 중복이면 예외를 던져 저장을 막는다. **이 단계에서는 규칙 로직이 컨트롤러 안에 있어도 된다**(의도된 과도기 상태).

**완료 기준**
- 같은 이메일로 두 번 가입하면 두 번째 요청은 저장되지 않고 실패한다(이 단계의 실패 응답 코드는 평가하지 않음 — 다음 단계에서 정리).

> 이 단계는 "동작하지만 책임이 섞인" 상태를 의도적으로 만드는 구간입니다. 여기서 만든 상태가 Step 4의 출발점이 됩니다.

---

## Step 4 — 책임 분리 (Service 추출)
**요구사항**
- R4-1. `MemberService` 가 존재하고, **중복 검사 + 저장** 규칙을 담당한다.
- R4-2. 규칙 로직은 컨트롤러에서 서비스로 **이동**한다(양쪽에 중복 존재 금지).
- R4-3. 컨트롤러는 `MemberService` 에만 의존하고, **`MemberRepository` 를 직접 참조하지 않는다**.

**완료 기준**
- 외부 동작(요청/응답 결과)은 Step 3과 동일하다.
- 컨트롤러 코드에 `MemberRepository` 및 `existsByEmail` 호출이 남아 있지 않다.

---

## Step 5 — 응답 완성 (201 / 409)
**요구사항**
- R5-1. **`DuplicateEmailException`** 이 존재하고, 서비스가 중복 시 이 예외를 던진다(더 이상 `IllegalStateException` 아님).
- R5-2. 성공 응답을 **201 Created** 로 반환한다(`ResponseEntity` + `HttpStatus.CREATED`).
- R5-3. 중복 예외를 처리해 **409 Conflict** 로 응답한다(`@ExceptionHandler` + `HttpStatus.CONFLICT`). 던지는 예외 타입과 처리 대상 타입이 일치한다.

**완료 기준(제출 대상)**
- 신규 가입 → **201** + 응답 DTO(`{"id","email"}`).
- 동일 이메일 재요청 → **409**.

검증 명령(가이드 §4와 동일):
```
curl -i -X POST http://localhost:8080/members -H "Content-Type: application/json" -d "{\"email\":\"alice@example.com\",\"name\":\"Alice\"}"    # 201 기대
curl -i -X POST http://localhost:8080/members -H "Content-Type: application/json" -d "{\"email\":\"alice@example.com\",\"name\":\"Alice2\"}"   # 409 기대
```

## 선택 심화 (상급자용 · 채점 대상 아님)
> 기본 요구(R1~R5)를 모두 끝낸 뒤 시간이 남으면 도전하세요.

1. **[Location 헤더]** 회원 생성 성공(201) 응답에 새 리소스 위치를 가리키는 `Location` 헤더(예: `/members/{id}`)를 추가해 보시오. 201 Created의 관례에 더 부합하는 응답이 됩니다. (힌트: `ResponseEntity.created(...)` 또는 `URI` 구성)
2. **[검증]** `SignUpRequest` 의 `email`/`name` 이 비어 있거나 형식이 틀린 요청을 400 Bad Request로 거르려면 어디에 무엇을 추가해야 할지 설계만 서술하시오(구현은 선택). 이 규칙이 컨트롤러·서비스·DTO 중 어디의 책임인지도 함께 적으시오.
