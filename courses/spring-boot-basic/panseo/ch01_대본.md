## 슬라이드 1 — 표지
판서:
브라우저 그림 옆에 화살표 → 서버 상자, 서버 상자에서 다시 화살표 → 브라우저로 돌아오는 왕복 화살표를 그린다. "요청" "응답" 두 단어만 화살표 위아래에 적는다.
대본:
오늘은 스프링 부트 기초 1차시, 서버 프로그램과 웹 애플리케이션 실행 환경을 큰 그림으로 봅니다. 아직 복잡한 코드는 없습니다. 브라우저가 요청을 보내면 어딘가의 서버 프로그램이 받아서 응답을 돌려준다 — 이 한 장의 연결선만 먼저 잡습니다. 식당에 비유하면 손님이 브라우저, 주문서가 요청, 주방이 서버 프로그램, 완성된 음식이 응답입니다. 브라우저, 서버, 응답 세 단어만 기억하면 이후 슬라이드가 하나의 흐름으로 이어집니다.

## 슬라이드 2 — 최신 이슈로 학습 열기: 전자정부 표준프레임워크도 Spring Boot 흐름을 강화하고 있다
판서:
왼쪽 카드(eGovFrame 5.0 이슈) 밑에 밑줄, 오른쪽 카드(오늘 배울 흐름) 화살표 순서(요청→내장 서버→Controller→응답)에 번호 1~4를 매겨 순서를 표시한다.
대본:
2026년 3월 전자정부 표준프레임워크 v5.0.0 공지에는 SpringBoot 3.5.6 지원과 실행환경 업그레이드가 담겨 있습니다. Spring AI RAG, 클라우드·관찰가능성 가이드까지 포함되죠. 공공 영역도 JSP 화면 중심을 넘어 API·클라우드로 넓어지고 있다는 뜻입니다. 이 흐름을 이해하려면 먼저 서버가 요청을 받고 응답을 돌려주는 구조, Spring Boot가 실행 환경을 어떻게 준비하는지부터 알아야 합니다. 오늘 실습 기준은 Spring Boot 4.1.0, JDK 21, Spring Tools 5.2.0입니다.

## 슬라이드 4 — 서버 프로그램은 요청을 받아 결과를 돌려주는 일꾼이다
판서:
손님→주문서→주방→음식 4단계 그림 밑에 "요청→처리→응답" 세 단어를 대응시켜 적는다.
대본:
서버 프로그램은 단순합니다. 요청을 받고, 처리하고, 응답을 돌려줍니다. 손님은 브라우저, 주문서는 HTTP 요청, 주방은 서버 프로그램, 완성된 음식은 HTTP 응답입니다. 앞으로 배울 Controller, Service, Repository는 모두 이 주방 안에서 각자 역할을 맡은 구성원입니다. 서버가 항상 화면만 만드는 건 아닙니다 — HTML, JSON, 파일, 저장 작업 등 다양합니다. 공통점은 "누가 요청했는가, 누가 처리했는가, 무엇을 돌려줬는가"입니다.

## 슬라이드 5 — HTTP는 브라우저와 서버가 주고받는 약속이다
판서:
브라우저 → GET /hello → 서버 → 200 OK + Hello 흐름에 화살표 두 개(요청 방향, 응답 방향)를 서로 다른 색으로 덧그린다.
개념 — HTTP:
웹에서 클라이언트와 서버가 요청·응답 메시지를 주고받기 위해 사용하는 통신 규칙.
대본:
브라우저와 서버가 아무 규칙 없이 대화하면 서로 못 알아듣습니다. 그래서 HTTP라는 약속을 씁니다. `GET /hello`는 "/hello 자원을 가져오고 싶다"는 요청이고, 서버는 처리 후 상태 코드와 함께 응답합니다. `200 OK`는 성공을 뜻합니다. 택배 운송장과 같아서, 주소·경로가 틀리면 엉뚱한 곳으로 갑니다. 요청이 먼저, 응답이 나중이라는 방향을 기억하면 뒤에서 Controller 코드가 어디 놓이는지 훨씬 쉽게 이해됩니다.

## 슬라이드 6 — HTTP 메시지는 사람이 읽을 수 있는 구조를 가진다
판서:
왼쪽 요청 코드블록에 Method/Path에 동그라미, 오른쪽 응답 코드블록에 Status Code/Body에 동그라미.
대본:
요청에는 메서드·경로·부가 정보가 담기고, 응답에는 상태 코드와 실제 내용이 담깁니다. 브라우저 개발자 도구 Network 탭을 열면 요청 URL, 메서드, 상태 코드, 응답 본문을 확인할 수 있습니다. 처음엔 메서드·경로·상태 코드만 먼저 보면 됩니다. 헤더와 본문은 필요할 때 하나씩 더 익히면 됩니다. "요청에는 목적지가 있고 응답에는 처리 결과가 있다" — 이 구조만 먼저 잡으세요.

## 슬라이드 7 — 웹 서버는 정적 파일을 빠르게 전달하는 문지기다
판서:
플로우 다이어그램의 "웹 서버" 상자를 네모로 감싸고, 그 옆에 "이미 준비된 것"이라고 적는다.
개념 — 웹 서버:
HTTP 요청을 받아 HTML/CSS/JS/이미지 같은 정적 리소스를 빠르게 제공하거나 필요한 요청을 다른 서버로 전달하는 서버.
대본:
웹 서버는 매장 입구 안내 직원과 같습니다. 메뉴판처럼 이미 준비된 건 바로 꺼내 주지만, 개인별 상담·주문 변경처럼 판단이 필요한 일은 담당 부서로 넘깁니다. 실제 서비스에는 이미지·CSS·JS처럼 안 바뀌는 파일 요청이 아주 많은데, 이런 걸 매번 애플리케이션 로직으로 처리하면 비효율적입니다. 그래서 역할을 나눕니다.

## 슬라이드 8 — WAS는 실행 중인 애플리케이션 로직을 처리한다
판서:
WAS 상자 안에 Controller/Service/Repository/DB를 작은 사각형 4개로 그려 넣는다.
개념 — WAS(Web Application Server):
요청마다 달라지는 비즈니스 로직을 실행하고 DB 같은 외부 자원과 연동해 동적 응답을 만드는 서버.
대본:
WAS는 Web Application Server의 줄임말입니다. 여기서는 애플리케이션 코드가 실제로 동작합니다 — 로그인, 게시글 등록, 주문 처리, DB 연동처럼 요청마다 결과가 달라지는 일입니다. Spring Boot 애플리케이션도 결국 이 동적 처리를 실행하는데, 다만 내장 Tomcat이 애플리케이션 안에 함께 들어와 있어서 "서버 설치"가 아니라 "애플리케이션 실행"으로 시작할 수 있습니다. 기준은 "요청마다 판단이 필요한가"입니다.

## 슬라이드 9 — 과거 방식: 서버를 따로 설치하고 애플리케이션을 올렸다
판서:
"개발 코드 → WAR → 외부 Tomcat → 실행" 흐름 밑에 X표를 작게 그려 "번거로움"을 표시.
대본:
과거 Java 웹 애플리케이션은 Tomcat을 따로 설치하고 WAR 파일로 배포하는 흐름이 많았습니다. 여전히 쓸 수 있지만 Tomcat 버전, 포트, 배포 경로, 서버 설정이 다 맞아야 해서 "내 PC에서는 되는데 다른 PC에서는 안 된다"는 문제가 생기기 쉬웠습니다. 과거 방식이 틀린 건 아닙니다 — 비교 기준으로 짚고 넘어가는 겁니다. 이걸 알아야 Spring Boot 내장 서버가 왜 편한지 더 분명해집니다.

## 슬라이드 10 — Spring Boot 방식: 애플리케이션이 서버를 품고 실행된다
판서:
"개발자 → main() → Spring 컨테이너 → 내장 Tomcat → localhost:8080" 흐름 전체를 하나의 큰 상자로 둘러싸 "한 번에 실행"이라고 적는다.
개념 — 내장 서버:
애플리케이션 안에 포함되어 함께 시작되는 웹 서버로, 별도 Tomcat 설치 없이 HTTP 요청을 받게 한다.
대본:
Spring Boot의 중요한 특징은 내장 서버입니다. `main()`이 `SpringApplication.run()`을 호출하면 Spring이 시작되고, 웹 의존성이 있으면 내장 Tomcat도 함께 뜹니다. 그래서 외부 Tomcat 없이 `localhost:8080`으로 바로 확인할 수 있습니다. 푸드트럭처럼 조리 장비를 차 안에 싣고 다니는 셈입니다. 외부 Tomcat이 사라진 게 아니라, 애플리케이션 안에 포함되어 함께 시작된다는 점이 핵심입니다.

---

## 슬라이드 11 — 자동 설정은 "상황을 보고 기본 준비를 해주는 도우미"다
판서:
플로우의 "Web MVC 스타터" 상자에서 "Spring Boot 자동 설정" 상자로 가는 화살표에 "단서"라고 적는다.
개념 — Auto-configuration:
클래스패스의 의존성·설정값·실행 환경을 보고 Spring Boot가 필요한 기본 Bean과 서버 구성을 자동으로 준비하는 기능.
대본:
자동 설정은 설정이 완전히 사라지는 게 아니라 기본 부담을 크게 줄여줍니다. 프로젝트에 어떤 스타터·라이브러리가 있는지 보고 "이건 웹 애플리케이션이겠다"고 판단해 Spring MVC·Tomcat 구성을 준비합니다. 캠핑 매니저가 텐트가 있으면 팩과 망치를, 버너가 있으면 가스를 챙겨주는 것과 같습니다. 개발자는 기본값으로 빠르게 시작하고 필요할 때 바꾸면 됩니다.

## 슬라이드 12 — 실무 중간 사례: "서버 설치부터 하라"는 말이 줄어든다
판서:
왼쪽 패널(설정 먼저) 위에 X, 오른쪽 패널(실행 먼저) 위에 체크(✓)를 크게 그린다.
대본:
Spring Boot를 쓰면 서버 설치·배포 설정부터 배우지 않고 먼저 애플리케이션을 실행해 볼 수 있습니다. 신입 개발자 민수는 Tomcat 설치로 반나절을 쓴 반면, 지연은 `Run As > Spring Boot App`으로 바로 실행합니다. "일단 실행된다"는 경험이 있어야 요청을 보내보고, 로그를 보고, 코드를 고쳐볼 수 있습니다. 오늘 실습도 바로 그 첫 실행 경험을 만드는 목적입니다.

## 슬라이드 13 — 실습 준비: 오늘 만들 가장 작은 서버 프로그램
판서:
"ch01-hello-server → /hello → Hello Spring Boot" 세 칸을 화살표로 잇고, 미션 보드처럼 체크박스 3개(프로젝트 생성/Controller/실행 확인)를 그린다.
개념 — 엔드포인트:
클라이언트가 서버 기능을 호출하기 위해 사용하는 구체적인 URL 경로.
대본:
이제 실습입니다. `/hello` 요청에 `Hello Spring Boot`를 응답하는 아주 작은 서버를 만듭니다. 처음 식당을 열 때 모든 메뉴를 만들 필요는 없죠 — 물 한 잔 주문이 제대로 나가는지 먼저 확인하는 것과 같습니다. 기능은 작지만 프로젝트 생성부터 브라우저 응답까지 서버 프로그램의 기본 생애주기를 한 번 통과하는 실습입니다.

## 슬라이드 14 — 실습 1: Spring Starter Project 만들기
판서:
IDE 캡처 옆에 Group/Artifact/Package/Spring Boot 버전을 세로로 적고 각각 밑줄.
대본:
STS4에서 Spring Starter Project를 만듭니다. Group, Artifact, Name, Package를 입력하고, 웹 애플리케이션을 만들 것이므로 Web MVC 스타터를 추가합니다. 이 스타터가 들어가면 Spring Boot가 "이 프로젝트는 웹 요청을 받는다"고 판단할 근거가 생깁니다. 빈 가게를 계약하고 업종(웹 서버)을 정하는 단계라고 보면 됩니다. 기준은 Gradle, Java 21, Spring Boot 4.1.0입니다.

## 슬라이드 15 — 실습 2: Web MVC 스타터 추가하기
판서:
"Web MVC 스타터 → Spring Boot 자동 설정 → Spring MVC / 내장 Tomcat" 미니 흐름에 밑줄 강조.
개념 — 스타터:
특정 기능을 만들 때 자주 함께 쓰는 라이브러리와 기본 설정을 묶어 제공하는 Spring Boot 의존성 묶음.
대본:
Spring Boot 4.1.0 기준 MVC 웹 실습에서는 `spring-boot-starter-webmvc`를 씁니다. 이 스타터가 들어가면 Spring MVC·내장 Tomcat 관련 라이브러리가 함께 들어오고, Spring Boot는 이걸 보고 웹 애플리케이션이라고 판단합니다. 라면 가게를 열 때 냄비·버너·물·그릇이 세트로 딸려오는 것과 같습니다. 의존성 하나가 실행 환경 전체에 영향을 준다는 걸 기억하세요.

## 슬라이드 16 — 실습 3: HelloController 작성하기
판서:
코드에서 `@RestController`, `@GetMapping("/hello")`, `return "Hello Spring Boot"` 세 줄에 각각 다른 색으로 밑줄.
개념 — Controller:
웹 요청이 애플리케이션 코드로 들어오는 입구. `@RestController`는 반환값을 응답 본문으로 직접 돌려주는 Controller.
대본:
Controller를 작성합니다. `@RestController`는 이 클래스가 웹 요청 창구라는 표시, `@GetMapping("/hello")`는 `/hello` GET 요청을 이 메서드로 연결한다는 뜻입니다. 반환 문자열은 화면 템플릿 없이 바로 응답 본문에 담겨 브라우저로 갑니다. Controller는 식당의 주문 접수 담당자입니다 — 주문 창구가 없으면 손님이 요청을 전달할 방법이 없습니다.

---

## 슬라이드 17 — 실습 4: main 메서드가 애플리케이션을 시작한다
판서:
`SpringApplication.run(...)` 줄에 굵게 원을 그리고, 옆에 "전원 스위치"라고 적는다.
개념 — main() / SpringApplication.run:
`main()`은 Java 애플리케이션의 시작점, `SpringApplication.run(...)`은 Spring Boot 애플리케이션과 실행 환경을 시작하는 호출.
대본:
`main()`이 시작점이지만 직접 서버를 만드는 게 아니라 `SpringApplication.run()`을 호출합니다. 이 한 줄이 Spring 컨테이너 시작, Bean 준비, 웹 애플리케이션이면 내장 Tomcat 시작까지 이어집니다. 가게 전원 스위치를 켜면 조명뿐 아니라 냉장고·주방 장비·주문 시스템까지 차례로 준비되는 것과 같습니다. Controller는 요청이 왔을 때 일하고, `main()`은 그 전에 실행 환경을 먼저 켭니다.

---

## 슬라이드 18 — 실습 5: Spring Boot App으로 실행하기
판서:
콘솔 로그의 "Tomcat started on port 8080" 줄에 형광펜처럼 굵은 밑줄.
대본:
`Run As > Spring Boot App`으로 실행하면 콘솔에 배너와 로그가 뜹니다. 여기서 반드시 확인할 건 시작 완료 메시지와 포트 번호(기본 8080)입니다. 포트가 열렸다는 건 브라우저나 API 도구가 요청을 보낼 수 있다는 뜻입니다. 푸드트럭 시동을 걸었다고 바로 영업 시작은 아니듯, Started 로그와 포트 확인이 영업 준비 완료 표시입니다. 브라우저로 넘어가기 전에 이 로그부터 보는 습관을 들이세요.

## 슬라이드 19 — 실습 6: 브라우저에서 `/hello` 호출하기
판서:
주소창 `localhost:8080/hello`에서 `localhost`, `8080`, `/hello` 세 부분을 각각 다른 색으로 표시하고, "결과" 아래에 화살표로 연결.
개념 — localhost / 포트:
`localhost`는 지금 내 컴퓨터를 가리키는 주소, `8080`은 Spring Boot가 기본으로 HTTP 요청을 받는 포트.
대본:
`http://localhost:8080/hello`로 접속합니다. 브라우저 요청이 우리 PC에서 실행 중인 Spring Boot 애플리케이션으로 전달되고, Controller의 `hello()`가 실행되어 `Hello Spring Boot`가 돌아옵니다. `localhost`는 이 건물, `8080`은 출입문 번호, `/hello`는 주문할 메뉴명이라고 생각하면 쉽습니다. 화면에 이 문장이 보이면 오늘의 가장 작은 서버가 성공적으로 동작한 겁니다.

## 슬라이드 20 — 요청이 코드까지 도착하는 전체 그림
판서:
5단계 플로우(브라우저→내장Tomcat→Spring MVC→HelloController→응답) 아래에 번호 1~5를 매기고, "우리가 쓴 코드"라고 HelloController 밑에만 적는다.
대본:
방금 실행한 걸 전체 흐름으로 정리합니다. 브라우저의 `/hello` 요청을 내장 Tomcat이 받고, Spring MVC로 넘기면 매핑 정보를 보고 `HelloController.hello()`를 찾아 실행합니다. 반환 문자열이 HTTP 응답이 되어 돌아갑니다. 택배가 경비실·동·층·호수를 거쳐 정확한 사람에게 가는 것과 같습니다. 이 그림에서 우리가 직접 쓴 코드는 Controller뿐이고, 나머지는 요청을 거기까지 연결해 주는 실행 환경입니다.

## 슬라이드 21 — 적용하기: 어디에서 문제가 났는지 찾아보기
판서:
"실행 로그 → URL → Controller 코드" 순서 화살표에 번호를 매기고, 각 단계 옆에 체크박스를 그린다.
대본:
`/hello`가 안 될 때 어디부터 볼까요? 첫째 서버가 실제로 실행됐는지(콘솔 Started 메시지), 둘째 URL이 맞는지(포트·경로), 셋째 Controller 매핑이 맞는지(`@GetMapping("/hello")`) 순서로 봅니다. 택배가 안 왔다고 바로 기사를 탓하지 않고 물류센터 출발→주소→수령인을 순서대로 확인하는 것과 같습니다. 정답을 외우는 게 아니라 확인 순서를 갖는 게 중요합니다.

## 슬라이드 22 — 문제풀기 준비: 핵심 흐름을 다시 보고 답한다
판서:

대본:
오늘 정리하겠습니다. 서버 프로그램은 요청을 받아 처리하고 응답을 돌려줍니다. HTTP는 그 약속이고, 웹 서버는 정적 리소스, WAS는 동적 로직을 처리합니다. Spring Boot는 내장 서버와 자동 설정으로 이걸 빠르게 실행하게 해줍니다. 우리는 `/hello` 실습으로 가장 작은 서버 프로그램을 직접 실행해 봤습니다. 문제를 풀 때는 "이 보기가 요청 흐름의 어느 지점을 말하는가"를 먼저 생각하세요.
