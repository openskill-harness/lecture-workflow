# 하네스 개입 지점 — 사용자 확정 우선 원칙과 자산 소유권

- 날짜: 2026-07-09
- 참여: 사용자 + Claude

## 배경

11단계 파이프라인의 실제 flow를 확인하던 중, 사용자가 개입하고 싶은 지점(원고, PPT프리뷰)과 하네스가 실제로 개입을 허용하는 지점이 어긋난다는 것이 드러났다.

사용자가 밝힌 하네스 운용 철학:

> 이 하네스는 내 직원이다. 원고는 하네스가 만들지만 확정은 내가 한다. PPT프리뷰도 하네스가 만들지만 확정·수정은 내가 한다. 내가 편하게 개입할 수 있는 **도구**만 있으면 된다.
>
> 원고가 조금 마음에 안 든다고 하네스를 고치지는 않는다. "이런 건 담부터 하지 마라"를 규칙으로 쌓으면 제약이 누적되어 결국 원고를 더 못 만든다. 정말 **영원히 지켜야 할 것**이 아니면 하네스를 수정하지 않는다.
>
> PPT도 마찬가지다. 여백·폰트크기·일관성·삐져나옴은 잘못 만들면 하네스를 고쳐야 한다. 하지만 "여기는 표가 나왔으면 좋았을 텐데"는 하네스를 고칠 일이 아니라, 그 자리에서 "이 부분 이 사진으로 바꿔줘"라고 지시할 일이다. "여기는 표가 나와야 해"를 규칙으로 넣는 순간 하네스가 오버피팅된다.

## 핵심 논의

### 현행 flow 확인

- 진행 판단의 유일한 입력은 `courses/{id}/status.md`다. 코드 폴더를 보고 판단하지 않는다.
- `course-pipeline`이 status.md에서 첫 ⬜/🔄 칸을 찾아 → 선행 단계 ✅ 검사 → 해당 스킬 호출 → status.md 재독 → 반복.
- 시각자산(4단계)이 ✅ 또는 `deferred`가 아니면 코드~책(5~11단계)이 전부 막히는 하드 게이트.
- 사진 교체는 프리뷰에서 불가능. `ppt-preview`는 `manifest.json`(SSOT)을 읽기만 하고, repair 규칙 첫 줄이 "원고는 불변"이다.

### 발견한 공백

1. **PPT프리뷰에 개입 도구가 없다.** 원고에는 티키타카 스킬(`manuscript-final`)이 있으나, 프리뷰에는 repair 규칙(체크리스트 실패 시 자동 수리)뿐이고 사용자 지시를 받는 통로가 없다.
2. **사용자 제공 이미지 경로가 없다.** Visual asset 하위 유형 4종(GPT image prompt / D2 / Screenshot plan / 코드 블록)에 사람이 준 파일을 가리키는 유형이 없다. `image_gen.py`는 텍스트→이미지 단방향이라 손그림 참조 입력이 불가능하다. (`edu-sim-builder`만 참고 스케치를 받는다.)
3. **프리뷰 레이아웃 검증이 육안에 의존한다.** 책에는 `pub-layout-check`(감지) + `pub-page-fit`(수정) 쌍이 있으나 프리뷰에는 대응물이 없다. 코드 무스크롤 규칙조차 "브라우저에서 스크롤바 없는지 확인"이다.
4. **시각자산 단계에 두 성격이 섞여 있다.** 개념 자산(원고 파생, 코드 불필요)과 실행 자산(코드 파생 — 코드 이미지·실행 결과 캡처)이 한 디렉터리에 있고, 후자는 "manifest 관리 대상이 아니다"라는 예외로 봉합돼 있다.

### 오버피팅의 진원지

"어떻게 보이는가"(영원한 규칙)와 "무엇을 보여주는가"(그때그때 지시)를 하네스가 섞어 놨다.

| 현행 조항 | 성격 | 처분 |
|---|---|---|
| 골든 CSS 변수·라이트 팔레트 고정 | 일관성 | 유지 |
| `.ppt-slide`/`.ppt-canvas` DOM 계약 | 하류 파싱 계약 | 유지 |
| 코드 무스크롤, 45단어, 안전 여백 `clamp()` | 삐져나옴·과밀·여백 | 유지 |
| "골든 위젯 9종 안에서만" | 내용 결정 | 완화 |
| Visual asset 하위 유형 4종 고정 | 내용 결정 | 확장 |
| "기본 주 시각자료는 GPT 이미지" | 내용 결정 | 완화 |
| repair 규칙 "원고는 불변, 캔버스 문구만 축약" | 개입 차단 | 교체 |

## 결론

### 결정 1 — 사용자 확정이 원고를 이긴다

원고는 사용자를 구속하는 계약이 아니라, 사용자가 승인한 최신 상태의 기록물이다. 원고확정(3단계) **이후** 단계에서 사용자가 다르게 확정하면 원고를 역수정한다.

- 새 발명이 아니다. `practice-code` §4가 이미 같은 패턴이다(실행 검증 결과가 원고와 다르면 사용자 승인 후 원고 역수정, 범위는 어긋난 문구 최소한). 이 통로를 시각 산출물 쪽으로 일반화한다.
- 역수정은 선택이 아니라 **stale 메커니즘의 전제조건**이다. 프리뷰에서 사진만 바꾸고 원고 프롬프트를 두면, 다음 `visual-assets` 실행 때 해시 비교에서 사용자가 고른 사진이 stale로 잡혀 옛 프롬프트로 덮어써진다.
- 개입 도구는 프리뷰 HTML을 직접 고치지 않는다. `manifest.json`을 갱신하고 해당 슬라이드만 재생성해야 책·PPTX·스토리보드가 같은 그림을 쓴다.

### 결정 2 — 자산 소유권은 `origin` 필드 하나로 표현한다

원고에 남겨야 할 것은 변경 이력이 아니라 **출처**다. "이 프롬프트는 더 이상 유효하지 않다"는 주석을 남기는 방식은 CLAUDE.md R2(old/new 공존 금지)와 R3(이력은 분리)를 어긴다. 이력은 git이 갖고 있다.

manifest 자산 블록에 `origin` 한 필드를 둔다:

| origin | 원고 Visual asset | 해시 stale | 하네스 권한 |
|---|---|---|---|
| `agent` | `GPT image prompt:` (하네스 작성) | 적용 | 자유롭게 재생성·개선 |
| `user-prompt` | `GPT image prompt:` (사용자 제시) | 적용 | 재생성만, 문구 임의 수정 금지 |
| `user-file` | `User image:` (경로) | 면제 | 덮어쓰기 금지 |

- `user-file`은 프롬프트가 없어 비교할 해시가 없다 — stale 면제가 예외 조항이 아니라 자연스러운 귀결이다.
- `user-prompt`를 `agent`와 분리하는 이유: 사용자가 준 문구를 하네스가 "더 나은 프롬프트로 다듬어" 바꾸면 안 된다. 자유도를 준 영역과 지시받은 영역의 경계가 이 필드에 담긴다.

### 이번 대화에서 다루지 않은 것 (별도 논의 필요)

- 루트 `code/design-pattern-{start,middle,end}`가 파이프라인 밖에 있다. 어떤 스킬도 읽지 않고 어떤 status.md도 가리키지 않는다. `practice-code`를 ch02 이후에 돌리면 이 코드의 존재를 모른 채 `outputs/04_코드/chNN/`에 새로 생성한다. 의도한 분리인지 통합할 중복인지 미결.
- 시각자산 단계의 두 성격(개념 자산 vs 실행 자산) 분리 여부. 현재는 예외 조항으로 봉합돼 있다.
- `courses/spring-boot-basic`(구 디렉터리 규약)과 `courses/design-pattern`(`outputs/NN_` 규약)의 배치 drift. repair 규칙이 "산출물 인덱스 실경로 1차"로 흡수하고 있다.
